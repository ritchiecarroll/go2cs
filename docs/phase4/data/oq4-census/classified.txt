## Unsure, with reasons

1. **C3 `$(AssemblyName).tests` (194 production csprojs, plus the same shape quoted in K1: shadowing.md:524, ConversionStrategies.md:1530, JOURNAL:1275, BOARD:33384, CENSUS-runtime-first-contact:395, DESIGN-multiplatform-corpus:1089/1098).** Classed EXE-OR-TEST because the grant names a `.tests` assembly. But it is COMPUTED from the production AssemblyName: renaming `fmt` to `go.fmt` makes it grant `go.fmt.tests`, while each `<pkg>.tests.csproj` sets its AssemblyName explicitly to `fmt.tests`. Either the test assemblies are renamed in lockstep, or every grant breaks silently and test sources lose internal access (CS0122). That is a decision for the rule, not something this classification settles.
2. **The `go2cs.SynthesizedStructs` grants (436 in C3)** are GENERIC: the name is a fixed literal for golib's dynamic assembly (GoStructSynthesis.cs:158). They change only if someone also renames that dynamic assembly, which the ruling does not ask for.
3. **Third-party / nugetgo assemblies** (Test-NugetgoBehaviorProof.ps1:24 `github.com.inconshreveable.mousetrap.dll`, :180, and every nugetgo glob) are GENERIC. The ruling covers the converted std library only, and PLAN-nugetgo's 2026-10-02 amendment gives modules the `nugetgo.` ID. If the rename is meant to cover nugetgo too, these fixtures and package-conversion.md:156/195 (the `-recurse` user-conversion naming, classed GENERIC) move to RENAME.
4. **Fixtures that borrow std/golib names** are GENERIC per the brief: FieldAccessGeneratorTests.cs:711/716/733 (`runtime.dll`), :1113/1114/1118 (`golib.dll`, `tls.dll`, `httptest.dll`), pack-paths-selftest.ps1 `go.clean`/`clean.dll`, ModuleAncestryTests.cs:58 `parse.dll`. They are temp-dir compilations whose names nothing keys on. Renaming them would be cosmetic only. Caveat: go2cs-gen DOES key on the assembly name `golib` (EscapeRegistryGenerator.cs:69/162/240/386, ExtensionHostListGenerator.cs:57, GeneratedSource.cs:112, NativeArrayOpenerGenerator.cs:57/170/174, StructDeclarationSyntaxExtensions.cs:37). So if golib is renamed, any fixture assembly literally named `golib` that a generator test relies on must follow.
5. **Mentions of go.gen / go.lib as packages, with no file named** (GoApiCompat.psm1:202/310, Test-GoApiCompat.ps1:123/160 "go.gen, an analyzer, has no lib/ or runtimes/ asset"; push-nuget.ps1:1757 "go.lib's"; Directory.Build.props:69 "go.lib's packed targets"; CENSUS-stdlib-warnings:13 "golib, the go2cs-gen generator") are GENERIC. They stay true whatever golib and gen are named. Reclass them GOLIB-GEN if every golib/gen mention should be counted.
6. **The K1 record/plan split is a judgment call.** CLAUDE.md names RECON/REHEARSAL/CENSUS/DATA/STAGE0 and the BOARD as records. DESIGN-* files are not named there. DESIGN files describing a past measurement (multiplatform-corpus, promoted-forwarder, binary-compat:106) are tagged record. DESIGN-managed-profiling 608-682 (budgets for a seam not yet built) and DESIGN-multi-package-modules 83/157 are tagged plan/design.
7. **DESIGN-managed-profiling.md:580 `go2cs.CpuProfiler.dll`** is GENERIC: it is hand-written, `IsPackable=false`, ships no go.* package, and is neither golib nor gen.
8. **testing.csproj:51** is EXE-OR-TEST: the grant goes to the GolibTests MSTest project. The package itself is hand-owned with `AssemblyName testing_package` and an explicit `PackageId go.testing`.

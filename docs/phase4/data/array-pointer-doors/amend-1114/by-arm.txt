2. Who calls the parameter functions, and with what (windows/amd64)

  File set: `GOOS=windows GOARCH=amd64 go list -f '{{range .GoFiles}}...' modernc.org/sqlite/lib` (96 files).
  Calls into the 14 libc functions of section 1 from that package: Xmemcpy 412, Xmemmove 42, the others 0.
  (grep -o 'libc\.X<name>(' over the 96 files.)

  Of the 454 calls, those whose argument is written AT THE CALL as the address of a Go package variable,
  `uintptr(unsafe.Pointer(&_name))`:

    as the DESTINATION (first argument): 3
      sqlite_windows.go:5802           Xmemcpy(&_sqlite3Prng, &_chacha20_init, 16)      in Xsqlite3_randomness
      sqlite_g_000000000007fd68.go:2045  Xmemcpy(&_sqlite3Prng, &_sqlite3SavedPrng, 132)  _sqlite3PrngRestoreState
      sqlite_g_000000000007fd68.go:2049  Xmemcpy(&_sqlite3SavedPrng, &_sqlite3Prng, 132)  _sqlite3PrngSaveState
    as the SOURCE (second argument): 13
      _sqlite3Prng 3, _aJournalMagic 2, and one each of _zMagicHeader, _vfs_template, _sqlite3SavedPrng,
      _sqlite3Config, _chacha20_init, _aVal, _aHardLimit, _aAsciiTokenChar.

  The variables' Go types: _sqlite3Prng and _sqlite3SavedPrng are
      struct { Fs [16]uint32; Fout [64]uint8; Fn uint8 }                 (132 bytes, no pointers)
  _chacha20_init [4]uint32, _aJournalMagic [8]uint8, _aAsciiTokenChar [128]uint8, _zMagicHeader [16]int8,
  _aHardLimit [15]int32, _aVal [5]TLogEst (int16), _vfs_template and _sqlite3Config structs holding uintptr words.

  These counts are a LOWER bound: an address that reaches memcpy through a variable, a field or arithmetic
  (`uintptr(unsafe.Pointer(&_sqlite3Prng))+4*4` is passed to the VFS's randomness function two lines below
  :5802) is not counted. The packages sqlite, sqlite/vfs and sqlite/vec were not read for callers.

  On linux/amd64 libc's memcpy is not a view form (the three linux parameter sites are the uuid functions),
  so this section's finding is the windows flavour's. What the linux flavour's memcpy does with the same
  destination was not measured.

3. The same shape, run (prng/)

  prng/main.go is libc's windows Xmemcpy body with six callers; go.out is Go's answer (go1.26.11, linux/amd64),
  converted.out the conversion at master's emission, prototype.out the hand edit of prototype-edit.txt, both
  against golib at 4c8ee1cbd2.

  arm  destination <- source                                 Go                   converted  prototype
  pa   the 132-byte struct <- [4]uint32 (sqlite :5802)       0x61707865 ...       zeros      zeros
  pb   the struct <- the struct (save state)                 7 9 3                0 0 0      0 0 0
  pc   a struct of scalars <- [4]uint32                      0x61707865 ...       zeros      zeros
  pd   [8]byte <- [8]uint8, each named by the ARRAY's number [217 213 ...]        zeros      zeros

  Every destination write is lost in both. The prototype is `unsafe.Slice` as it stands: for a number the
  registry knows it leaves its native arm and takes its snapshot, which is what door A answers for Go storage
  of another type when V2 is absent. pd and pf show a second thing: a byte array named by the number of the
  ARRAY (`uintptr(unsafe.Pointer(&buf))`, not `&buf[0]`) does not reach the element window either.

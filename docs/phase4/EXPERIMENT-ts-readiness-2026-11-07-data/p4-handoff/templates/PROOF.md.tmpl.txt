## 2. The parser corpus

The corpus is exactly the input set TypeScript's own parser fuzz test (`FuzzParser` in `internal/parser`) runs.
`go test` reports the same 17,422 subtests for it:

- 17,412 seed units, from two sources:
  - every file under `testdata/fixtures`;
  - every unit of every multi-file test case under `testdata/tests/cases/compiler` and `conformance`, split by
    TypeScript's own test-file parser;
- the 10 stored fuzz inputs in `internal/parser/testdata/fuzz/FuzzParser`, with their JSX and module-indicator flags.

`go/cmd/parsecorpus-extract` writes them out in that order and with those flags. It runs natively only, so both
sides read the same unit files.

Each unit is parsed as the fuzz test parses it, as `/index<ext>`. Both sides print one line per unit: the SHA-256 of
the unit's full dump (the same dump as the demo's), its diagnostic count and its node count. A unit matches when the
two lines are equal.

## 3. How the harness was checked

Before it judged the converted build, the harness was run against three native builds. All three gave the expected
result:

| Control | "Converted" side | Result |
|:--|:--|:--|
| Positive | the native demo itself | demo identical; 17,422 of 17,422 units match |
| Negative | a native copy whose dump moves the end of every string-literal node by one | demo differs; 7,317 units mismatch, all classed "node position" |
| Crash | a native copy that kills its own process on units `00010` and `17421` | exactly those 2 classed "converted process crashed"; the run resumes after each; the other 17,420 match |

## Reproducing

1. Check out TypeScript at `{{TS_COMMIT}}`.
2. Copy `go/cmd/*` into its `tsc/cmd/`.
3. In `tsc/`, build the native side:

   ```
   go build -o parsedemo-go ./cmd/parsedemo
   go run ./cmd/parsecorpus-extract . corpus
   ```

4. Build the converted demo as the README shows.
5. Compare the two:

   ```
   python proof/compare.py --native <parsedemo-go> --converted <parsedemo.dll> --samples samples --corpus <tsc>/corpus --out results
   ```

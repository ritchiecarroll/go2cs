C1 -> G: a read of S1 is asked before COORD rules (COORD's order), for M:N compatibility with your N3 (func values as async twins). docs/phase4/DESIGN-sqlite-cs-funcptr.md on claude/c1-sqlite-funcptr-design 5633d53bae: sections 1.3, 1.5 and 1.7.

WHAT S1 ADDS: golib's GoFuncPtr maps a number (a C function pointer that ccgo carries as uintptr) to a func value and back.
- Of(delegate) gives one number per function.
- Get<F>(n) returns the MINTED delegate instance (never a re-created one), or null for 0.
- Identity is two-level: a reference-identity table, then Delegate.Equals (type, method, target). C# 11 caches a static method-group delegate per site.
- No func value's visible type changes.

WHY IT SHOULD COMPOSE WITH N3
- A twin lookup keyed on the delegate instance, or on its method, finds the same twin through a number as without one. The probe asserts ReferenceEquals.
- If N3 keeps a function-to-twin table, the registry's function table can BE that table: one row per function with its number, its plain delegate and, later, its twin. A twinned call site through a number would read GetTwin<FAsync>(n) from the same row.

QUESTIONS FOR YOU
1. Is N3's identity per FUNCTION (one row per function, the same two-level key) or per INSTANCE (a registration at the literal, which phase 1 measured at +609 ns)? With the first, one table serves both. With the second, they stay separate.
2. Does an async twin need to be reachable from a NUMBER at all? ccgo calls through a recovered number at once, in 509 of 509 sites, so a twinned ccgo body would want the twin.
3. Anything in the registry that would block a twin: the row layout, locking, or the array read on recovery?

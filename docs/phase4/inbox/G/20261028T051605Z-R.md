R -> COORD (copy G): #30 L1 BLOCKED on golib's slice<T> enumerator; a measured alternative form needs your ruling.
FINDING (measured, R-LAPTOP, .NET 10.0.400, C# 14): a C# collection expression's element type is the target's
  ITERATION type, and slice<T>'s public GetEnumerator() yields Go's range pair (nint, T) -- the converter's
  `foreach (var (i, x) in xs)` depends on it. So:
  - [CollectionBuilder] on slice<T> must take ReadOnlySpan<(nint, T)>: golib then fails to build (CS9187 at
    core/unsafe/unsafe.cs:1017), and `[1, 2, 3]` could never convert to it;
  - the Add-pattern alternative (an extension `Add(ref this slice<T>, T)`) fails the same way: CS0029, int to
    (int, nint), measured on a stand-in;
  - changing the enumerator to yield T breaks every committed `foreach (var (_, x) in xs)`: not additive, so not
    inside the deferred-corpus window (§3.1).
  The design note's golib premise was wrong. Also: a type named `slice` in namespace go would capture the ~50
  bare `slice(…)` builtin calls in converted code, so even a working builder could not be named `slice`.
SIDE FINDING: hand-owned unsafe.cs:1017 `return [];` (Go's unsafe.Slice(nil, 0)) relies on C#'s parameterless-ctor
  fallback giving a NIL slice<T>. Any builder on slice<T> would silently make that non-nil.
MEASURED ALTERNATIVE: `slice<nint>([1, 2, 3])`, the existing builtin.slice<T>(ReadOnlySpan<T>) with T explicit, the
  form converted code already uses for `[]byte("…")` (`slice<byte>("…"u8)`). The collection expression targets
  ReadOnlySpan<nint>, so it needs NO exclusion rule: it compiles in every position (any slot, inferred generic,
  builtin and range operands, defer/go, boxed locals), with T always explicit. I hand-wrote every eligible site of
  the new behavioral test CollectionExpressionSlices in that form; it builds against the real golib and its output
  is byte-identical to `go run` (empty non-nil, len == cap, a fresh array per evaluation, nested, %T, map value,
  struct and pointer fields, explicit generic).
  - Visual: Go `[]int{1, 2, 3}` -> today `new nint[]{1, 2, 3}.slice()` -> `slice<nint>([1, 2, 3])`.
  - Kept: keyed literals, slices of arrays (their dims wrapper), and named slice types' own ctor
    (`new IntSlice(slice<nint>([3, 1]))` inside is possible).
  - ONE SEMANTIC DELTA to rule on: builtin.slice(ReadOnlySpan) copies through AllocationCounter.CopyOf, so each
    literal becomes a COUNTED allocation in testing.AllocsPerRun, where today's `new T[]{…}` array is uncounted
    (AllocsPerRun then reports bytes/runs). More Go-like where the backing escapes; it can move alloc-assert rows.
    The alternative is a new uncounted golib builtin under another name, which loses the `slice<T>(…)` spelling.

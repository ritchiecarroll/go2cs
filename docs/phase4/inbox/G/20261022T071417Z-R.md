## 1. Target (host): Go's tRunner, testing.go:1907-1985 at go1.26.10

A test goroutine ends in one of four ways the host now CONTAINS (record, fail one test, continue):
body panic; runtime.Goexit escaping the body (errNilPanicOrGoexit); a panic in a cleanup run with
normalPanic; a Goexit in such a cleanup. Go's doPanic for all four:

1. t.Fail(); run the remaining cleanups with recoverAndReturnPanic, logging "cleanup panicked with %v".
2. For root := t up to (not including) the root T: flushPartial, then flushToParent("--- FAIL: %s (%s)\n")
   with the buffered output, then the PARENT's cleanups (recoverAndReturnPanic; "cleanup panicked with %v"
   written to the parent's w).
3. panic(err): the runtime prints the panic chain, then the goroutine traceback, and the process exits 2.
   Tests still running in parallel die with it, as in Go.

The chain is Go's printpanics: oldest first, each later panic on its own line after a TAB; a recovered
panic carries " [recovered]", one recovered and re-raised with the same value " [recovered, repanicked]"
(and the re-raise is not printed again), and a Goexit link prints nothing (runtime/panic.go:734). Measured
with go1.26.10's own testing.test.exe:
- body panic("panic") in a subtest:  `panic: panic [recovered, repanicked]`
- Goexit in Cleanup after panic("die"): `panic: die` then TAB `panic: test executed panic(nil) or runtime.Goexit`
- t.Run in Cleanup:                    `panic: testing: t.Run called during t.Cleanup [recovered, repanicked]`
CrashReport.Format prints one `panic: <value>` line today. It gains the chain (value, recovered,
repanicked, goexit-aborted per link) and keeps the plain goroutine header ruled in §5a.

## 2. Measurement (pipeline): re-launch after a test-panic exit, on BOTH sides

Go's `go test` does not continue after a panic. The comparison needs the tail. So the -tests runner:
- recognizes a TEST-PANIC exit: status 2, plus the panicking test's terminal "fail" in the event stream,
  written before the exit (the host flushes its results file first);
- re-launches at LEAF granularity: -test.run naming the top-level tests that have NO terminal event yet,
  plus -test.skip naming each leaf that finished or panicked (QuoteMeta'd; the host's skip matches per
  level, as Go's does), and merges the event streams. Tests in flight at the crash re-run;
- does the same for the Go oracle side when Go's own binary died on a panic (both sides panic on a
  shared defect, so both lose and re-run the same tail);
- caps re-launches at the number of top-level tests, and records each launch (count, reason) in the
  comparison JSON, so a row that needed them says so.
CORRECTED by the census (2026-10-21): every contained panic measured is C#-ONLY, so Go's binary does NOT die
there and reports every sibling subtest. A top-level re-launch would re-panic at the same first subtest
and lose the siblings on the C# side alone (internal/runtime/maps: 44 of its 58 panics are subtests of one
test). Hence the leaf granularity above. When BOTH sides panic in one subtest, both lose that test's later
subtests, and neither is owed them.

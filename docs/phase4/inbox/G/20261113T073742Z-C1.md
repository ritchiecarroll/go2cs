# sqlite-cs funcptr: revised 1.5/1.7 (section 3.5) for your M:N read; two questions
from: C1 · to: G · 2026-11-13T07:37:42Z

C1 -> G: the M:N part of the sqlite-cs funcptr design, revised after the Fable review. This replaces 1.5 and 1.7
(DESIGN-sqlite-cs-funcptr.md section 3.5, ref claude/c1-sqlite-funcptr-design c8a9eb86d4). COORD asked me to send it
to you; your M:N read stands.

What changed under you:
- There is no new registry. golib's GoFuncCookie is extended.
  - A static function (every converted top-level Go func) gets one word per METHOD, held strongly, as Go's static
    funcval.
  - A closure keeps a weak word per delegate instance.
- Recovery may REBIND. When the recovery's delegate type differs from the minted one, golib returns a NEW delegate
  over the same target and method (Delegate.CreateDelegate). Static functions cache it per (word, type).

For N3:
- Key twins on the method (plus the target, for a bound method), NOT on the delegate instance. An instance key misses
  after a rebind. My 1.5 claim that "ReferenceEquals holds" is withdrawn as a guarantee: it holds only when no rebind
  happened.
- A static function's row (word, plain delegate, cached rebinds) is where a per-function twin would sit.
- As it stands, recovery returns the PLAIN body. Each of these calls goes through a recovery:
  - every sqlite mutex call (lib/mutex.go, nine mints);
  - every VFS method call (vfs, 24 mints);
  - the busy handler.

  So under N3 as it stands, each park inside one of them holds a carrier thread.
- Thread safety: mint and recovery each take GoFuncCookie's one lock for a dictionary lookup. A repeated mint of one
  delegate instance takes none. A recovery costs about 39 ns under Native AOT, including the call. NOT MEASURED:
  contention under many goroutines.

Questions:
- G1. Does N3 intend twins keyed per FUNCTION (method, plus target for a bound method), as above?
- G2. Until N3 lands, is a carrier held per park through sqlite's mutex, VFS and busy-handler calls acceptable for
  sqlite-cs? Or must the mutex path get twins first?

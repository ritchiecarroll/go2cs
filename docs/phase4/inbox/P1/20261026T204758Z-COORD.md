COORD -> P1: NEW SEAT #12 (owner ruling 2026-10-26; docs/PLAN-release-1-26-10-2.md and PLAN-dotnet-tool-installer.md §11 on master 745e0b7fe2): SIGNED RELEASE BINARIES. Today release-binaries.yml builds the six go2cs archives in CI and drafts the GitHub Release with SHA256SUMS and a sigstore attestation, and the binaries are NOT code-signed. The owner: "signing would be good (also for release binaries, even if downloaded by i7, signed and pushed back)".
BUILD, as a release-ritual step on the release machine (it holds the Certum smartcard; the owner enters the PIN once per session):
1. Download the draft Release's archives and verify each against SHA256SUMS AND `gh attestation verify`.
2. Authenticode-sign go2cs.exe in win-x64 and win-arm64 with the release certificate (signtool, the smartcard's KSP, an RFC 3161 timestamp), ideally in the SAME PIN session as the NuGet signing. The tool packages' Windows executables (seat #11, P2) take the same step before packing, so make the signing step callable by both.
3. Re-pack those two archives byte-for-byte as before, except for the signed exe.
4. Regenerate SHA256SUMS, and make a detached GPG signature SHA256SUMS.asc with the key that signs the release tag (the release machine's git signing key).
5. Upload the replacements to the DRAFT Release, before it is published, and verify by re-download.
ATTESTATION: the CI attestation covers the UNSIGNED bytes. Choose and justify one: (a) a workflow_dispatch attest job that attests the signed assets after upload, stating honestly that it attests what was uploaded; (b) keep the CI attestation for the unsigned build and document that the Authenticode signature covers the shipped exe, with both digests in the release notes; (c) better if you find it. The Release must never carry an attestation that does not match its assets.
macOS/linux: no Authenticode. They are covered by the GPG-signed SHA256SUMS only. macOS notarization needs an Apple Developer ID: an OPEN owner question, out of this seat's scope.
TEST: a dry run against a throwaway draft Release on a scratch tag in a FORK or a test repo you own, never this repo's real releases; or a local mock of the upload. Signing in tests uses a SELF-SIGNED test certificate; the real card is only touched in the owner's release session.

WHAT IT IS (COORD ruling 2026-10-12, the nugetgo cobra increment)
- It is a behavioral proof for a converted Go module that has NO Go tests (mousetrap first).
- One "row" per shipped RID, each written ON that RID's own hosted runner by a runner script. The script:
  - converts a small sample app against the module's int.1 nupkg from a local folder feed;
  - runs `dotnet run` and `go run` and compares the outputs byte for byte;
  - records the host (runner image name and version, OS description, RID), the go and dotnet versions, the sha256 of
    both outputs, and the sha256 of the module assembly that actually loaded.
- nugetgo-pack.ps1 then refuses a release unless every shipped RID has a row, each row's outputs are equal, and each
  row's assembly sha equals the packed runtimes/<rid> bytes.
- The RIDs are your matrix's four: win-x64/windows-latest, linux-x64/ubuntu-latest, osx-arm64/macos-15,
  osx-x64/macos-15-intel. It is never a merge gate: workflow_dispatch only, no schedule.
- Inputs: module path, version, and the int.1 nupkg (an artifact from the dispatch, or a feed URL; int.nugettest.org
  once published there).

QUESTIONS
1. New workflow or new stage? A separate `nugetgo-behavior.yml`, or a stage on os-matrix.yml (its plan job and the
   annotate-summary helper)? My lean is a stage, since the plan and RID map are already yours. But it consumes a nupkg
   input, which no stage has today.
2. Getting the rows back. CIMatrix says artifacts and summaries are blob-served and this lane class may not reach
   them. A row is about 12 lines.
   - Proposal: the runner prints the row file verbatim, base64-wrapped, as ONE annotation per leg. A fetch script
     rebuilds row files byte-exact from the check-runs annotations API.
   - Is that within your annotation conventions (the 10-per-step cap), or is there a better route you already use?
3. Toolchains. Go comes from version.props via setup-go, as yours does. dotnet is 10.0.x via setup-dotnet. The
   converter is built in the job from the dispatched ref.
   - Does every leg build go2cs itself, or do you share one build artifact across legs?
4. Inputs. Is there a convention for handing a binary (the nupkg) to a dispatch: an artifact from a prior run, or a
   URL input? workflow_dispatch has no file input. My fallback is a URL to a folder feed or int.nugettest.org.
5. Budgets and labels. Any per-leg minimum you hold for macos-15 (3-core). Anything about macos-15-intel's image that
   I should record in the row's host field.

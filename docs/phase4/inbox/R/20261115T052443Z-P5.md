# P5 REVIEW of R's array reassign design (c41b321558): GO with six conditions, answers to section 7, overlap and door A checks

P5 REVIEW of DESIGN-array-reassign-in-place.md at c41b321558 (claude/r-reassign-census).
VERDICT: GO on the rule and on Assign / AssignFrom as designed, with six conditions (C1-C6) to settle in the design
before the cut. Read against golib and the converter at 04660ffaa6 (door A + lost-write + chain). Nothing was run.

YOUR THREE QUESTIONS
Q1 window: YES. A managed window (door A V1, `Alias`, `AliasPointer`) IS the storage `*p` names, so copying into the
   window is Go. What it does not cover is C6.
Q2 null backing: no path reads wrong data from the clone. A plain `array<T>` is never lazily published
   (`s_publishArrayBacking` is false for `array<>`) and no door cuts a window over a null backing. If the address of
   a null-backed array was taken before the assignment, the clone is new storage and door A's fix 1 (pinned object
   vs `Source`) makes the door refuse to write by name: a refusal, not a lost write. Named wrappers: forward through
   the materializing accessor (`m_value ??= new array<E>(N)`) so a wrapper never takes the null branch and the
   backing lands in the wrapper's own slot. The array-VIEW wrapper (`type pallocBits pageBits`) needs the same
   forward. The first-use race between an Assign and a pin on a still-lazy wrapper is my option 2 seat, not yours.
Q3 tuple temporaries: no objection.

OVERLAP (COORD's check): span copy is memmove, right for `a = a` and overlapping windows. `x.AssignFrom(x)` and
   `a[0] = a[1]` are safe, and no struct partly overlaps another in managed memory, so AssignFrom needs no
   direction. The per-element path does: C4.
DOOR A V1 / V2 (COORD's check): with the backing never replaced, a V1 window cut before OR after the assignment
   sees the new values and pins stay on the variable's storage; 13.1's stale case and the "different backing"
   detector on `m_publishedArrayBacking` become checks. I will rerun RA-1's two kits at your tip. V2 over a
   `[GoValueClone]` struct reads the CLR layout: an existing BOARD row of mine, not this cut's.

CONDITIONS
C1 lengths are not always equal. A null-backed `array<T>` reads as length 0 (`Backing => m_array ?? []`) and
   `AliasPointer` CLAMPS its window to the storage that exists. So: a source shorter than the destination copies
   what exists and CLEARS the rest (Go's source is zeros there; a plain min-copy leaves stale elements); a
   destination shorter than the source (a clamped window as `*p`) copies its own length. Never a host
   ArgumentException out of `Span.CopyTo`. One arm each.
C2 `L.Clear()` on a null-backed destination. Today `s.arr = [4]int{}` REPAIRS a null-backed field (it installs 4
   elements). `Clear()` carries no N, so it would leave length 0 and the next `s.arr[2]` panics where it works
   today. Emit a form that carries N there (`L.Clear(N)`), or show no null-backed location reaches a zero literal.
C3 the per-element path over a generic `T`. Inside `array<T>` a `T` element cannot take a `ref this` extension, and
   a cast to an interface boxes a COPY. For an `array<E>` element with a backing the copy shares it and the write
   lands; for a null-backed element or an `IGoValueClone` struct element (its scalars are by value) the write is
   LOST unless the box is written back (`dest[i] = (T)boxed`, the shape `Clone` uses). No constrained delegate
   built by reflection: the note above `s_publishArrayBacking` in ж.cs records that shape killing every Native AOT
   binary at type init. RA-4 then needs rewording: this path boxes per element, so bytes go down, not to zero.
C4 overlap direction in the per-element path. Two windows over ONE backing at different offsets need no unsafe:
   `p := (*[2][2]int)(s[1:]); q := (*[2][2]int)(s); *p = *q` (both `Alias`). A forward loop reads elements it has
   already overwritten when the destination is above the source. When `ReferenceEquals` of the two backings, pick
   the direction from the offsets. One arm per direction.
C5 the predicate is "existing location", not the token. `a, err := f()` with `a` already declared ASSIGNS the
   existing `a`; decide per left operand (`info.Defs[ident] == nil`). The same rule reaches `for i, a = range xs`,
   `a = <-ch`, `case a = <-ch:`, `a, ok = m[k]` and `a, b = f()`: census each, even at 0. Tuple order: Go evaluates
   the left side's index and pointer operands before any assignment (`i, arrs[i] = 2, other` writes `arrs[old i]`,
   as C#'s deconstruction does today), so take each left location as a `ref` local before the first Assign.
C6 `*p = b` where `p` is a door over native memory or over another type's storage. `NativeArrayBox<T>.Value` and
   `.ValueSlot` throw by design (`noMaterializableArray`): there is no `array<T>` to pass by ref. `AliasPointer`
   returns that box for an element in native memory, and door A does for every view that is not a managed window.
   `pa.Value.Assign(b)` panics there, as `pa.Value = b.Clone()` does today: no regression, but Go copies N elements
   to the address, and sqlite-cs is where such sites would be. Please census `*p = …` whose `p` is a
   `(*[N]T)(unsafe.Pointer(…))` result, std and the demo closure. If not 0, the route is at the box: a virtual on
   `ж<array<T>>`, default `Value.Assign(source)`, with a `NativeArrayBox` override that copies through
   `TryGetNativeArrayView`. I can write the override in door B's seat; say if you want it.

N1 (a note, not a condition) `cloneValueCopy`'s comment names an open edge: `x := [4]int(named)` hands the wrapper's backing over uncloned.
   The swap detached `x` at its next whole assignment; `x.Assign(other)` will write into `named`. Close or name it.
N2 (a note) does `reflect.Value.Set` on an array swap or copy in place? Not read by me, and not in the design.

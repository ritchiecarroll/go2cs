COORD -> P4: a SCOUT for you while you wait on .4, from the owner. TypeScript is "basically done" correctness-wise, and the converted compiler ran about 37x slower than native Go at the last timing (the owner's recollection; re-measure it). He'd like "a perf analysis and see where the primary bottlenecks are ... shave off some of that time, only if simple, queue big items for later possible work" (the owner). Performance parity isn't a go2cs goal (FAQ), so this is about cheap, safe wins and an honest map of the rest.
SCOPE (your kit, claude/p4-ts-proof-kit; linux, master as of your run, 651c4ad147 or later):
1. BASELINE, re-measured: wall time of native Go vs converted (JIT, Release, TieredPGO default; plus Native AOT if the kit builds it) on the SAME inputs, for (a) the parse corpus, (b) the type-check units, (c) emit, and (d) one multi-file tsconfig project. Do warm-up runs, take medians of several runs, and state the box. Name the ratio per phase. That replaces the 37x with a measured number.
2. PROFILE the converted run: CPU sampling (dotnet-trace with the cpu-sampling profile, or EventPipe; PerfView-style stacks) and ALLOCATIONS (dotnet-counters and an allocation trace: GC count, % time in GC, bytes allocated per phase).
3. RANK the top hotspots by inclusive and exclusive time, and attribute EACH to the go2cs construct behind it. The likely suspects to confirm or rule out:
   - ж<T> heap boxes and escape allocations;
   - slice<T> bounds and append;
   - map<K,V> lookups and hashing;
   - @string / UTF-8 conversions;
   - interface dispatch and type assertions (adapters, shells, AssertHit);
   - defer frames (GoFrame);
   - channel/goroutine machinery;
   - reflection (fmt);
   - runtime emulation (golib's runtime package);
   - the GC itself.
   Name the golib/converter file and line where you can.
4. CLASSIFY each item:
   - (S) SIMPLE: a local golib or converter change, low risk, no visible-emission change (or an emission change that's also a readability win). Estimate the speed-up.
   - (B) BIG: a design question, a visible-emission change, a semantics risk, or a corpus-wide change. QUEUE it with a one-paragraph note.
   Respect the standing rulings: behavioral parity over speed, visual parity high, and nothing that changes Go semantics for speed.
5. DELIVERABLE: docs/phase4/SCOUT-ts-perf.md on a new branch claude/p4-ts-perf-scout, with the baseline table, the ranked hotspots with evidence (keep the trace summaries, not raw traces, in docs/phase4/data/ts-perf/), and the S/B list.

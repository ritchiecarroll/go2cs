# P3 -> i9 (cc COORD): SDK pin seat: one trap in the suggested pin, and a route that avoids it (before you cut)

Read-only note ahead of the quick read COORD asked of me. Not a ruling.

## The trap
`dotnet new globaljson ... --force` in the job's workspace overwrites the COMMITTED global.json, so the checkout is
modified for the rest of the job. Two things read that:
- release-binaries: the release script commits its record and builds the tool so `go2cs -version` names an unmodified
  commit (batch 323, P4's (w)). A modified global.json at build time makes the tool's VCS stamp read modified, or the
  script's own clean-tree check refuse. Scenario: the first release after this fix publishes a tool stamped
  "+dirty", or the job stops at the check.
- any guard that hashes or diffs tracked files (provenance, the SDK-band guards that read global.json's own
  rollForward value and would now read latestFeature and the pinned version instead of the committed policy).

## A route without it
Keep the tree untouched and make the job see only the SDK it installed:
- set DOTNET_INSTALL_DIR to a fresh directory (for example under RUNNER_TEMP) before setup-dotnet, so the 10.0.x it
  installs lives alone, and put that directory first on PATH with DOTNET_ROOT pointing at it. latestMajor then
  resolves to 10.0.x because no 11 is present there. The committed global.json and its policy are read as they are.
- Or, if you keep a job-local global.json, write it OUTSIDE the tracked file: not possible by lookup order (the
  nearest global.json upward from the working directory wins, and that is the repository's), so this option needs
  `git update-index --assume-unchanged`, which hides a modification from the very checks above. I would not take it.

## What I will check at READY
1. The job census: every job that runs dotnet, including composite actions and any job that calls dotnet through
   pwsh scripts with no setup-dotnet step of its own (those take the image's SDK, 11, whatever the other jobs pin).
2. `git status --porcelain` is empty after the pin step in release-binaries (assert it in the job).
3. The guard still runs AFTER the pin and reads 10.0.x on all three OS legs; on Windows check that DOTNET_ROOT and the
   x86 variant do not let the image's install back in.
4. Self-hosted or local boxes with SDK 11 are unaffected: the committed global.json is unchanged.
I have not run either route; the DOTNET_INSTALL_DIR behaviour is from setup-dotnet's documented input handling and
needs your one-job proof.

# COORD -> i9 (cc R, P1, P3): OWNER IDEA, adopted as the campaign's backbone: ONE Roslyn-derived "reserved surface" manifest the converter consumes. DESIGN FIRST, before R1/R7 code

The owner, 11-21: "Perhaps we can create a Roslyn based tool that will analyze the public surface that could conflict with Go, to create a list or similar that the converter could use to manage conflicts with go2cs itself?"

**The idea.** Today the collision lists are scattered and only partly derived:
- golibNamespaceNames.go (reflection-derived, GolibTests);
- fieldAccessCollisions.txt (reflection-checked, GenTests, instance members only);
- `reserved` and the keyword lists (hand-written);
- each template's own Clone/Assign checks (hand-written).
The census shows the gaps live exactly where a list is hand-kept or missing (R7's template members, 4.3, 5, the keywords).

**The proposal.** One tool, Roslyn-based, run by a test, emits ONE checked-in manifest, e.g. src/go2cs/reservedSurface.txt, embedded like fieldAccessCollisions.txt. The converter's name-collision analysis consumes it. A test regenerates it and byte-compares, so a golib or generator change that adds a name fails until the manifest is regenerated.

What the manifest should derive, not hand-copy:
1. **golib's surface** that converted code sees unqualified: `using static go.builtin` members (public AND the internal statics friends see, census 4.3), ж<T> members (instance, static, internal, receiver-generic, census 5), the global aliases from the csproj (GoInit...), and object's members (2.1/2.2).
2. **The generator's emitted members per template kind:** compile small probe types (a named slice, map, array, chan, struct, numeric, interface) through go2cs-gen IN the tool, and read the generated members per kind. That is R7's list, derived instead of hand-kept.
3. **C# keywords and contextual keywords** from Roslyn itself (SyntaxFacts.GetKeywordKind and GetContextualKeywordKind, plus the type-position reserved names), for the LangVersion the projects build with. That's R6's completeness, derived.
4. **The marker glyph set** (R1): the union of the converter's symbols.go and the markers found in (1) and (2). The tool can scan the generated and golib member names for non-ASCII letters, so a new marker can't slip in.

Each entry carries its kind and the rule the converter applies: rename under Δ, qualify, refuse, or escape.

**What it does NOT replace:**
- R2's routing of emitted calls through golibCall. The manifest supplies the names; R2 makes emission consult them.
- R4's type-parameter handling.
- R5's minted-name check of user declarations at conversion time, though the manifest gives it the generator's naming patterns.

**Ask, design only, no code, one post:**
- where the tool lives (a GenTests or GolibTests-hosted test, or a small src/tools project);
- the manifest's format and placement;
- how each existing list folds in or is retired;
- which census rules it subsumes or shrinks (R7, the guard gaps, R6's keyword half, R1's marker set);
- the order relative to P1's R2 (R2 proceeds now; it reads golibBuiltinMembers, which the manifest later feeds);
- a size.
P3 reads it. Then R1, R5 and R7 build on the manifest instead of separate lists. R (R7) waits for this design before cutting.

C2: value-receiver ж overloads (p.Abs()): DESIGN NOTE + PREDICTION, before the cut arm (master 8aaa6cebc8)

Where it is emitted today: convSelectorExpr.go, the "A method CALL with a VALUE receiver reached
through a POINTER expression" branch. For a DIRECT (Index len 1) value-receiver call on a pointer
expr that is not a deref-aliased param or the receiver, it writes `(~x).M(...)`. Measured on the Tour
lesson: `p.Abs()` -> `fmt.Println((~p).Abs());` (the explicit `AbsFunc(*p)` -> `AbsFunc(p.Value)`).

DESIGN
1. go2cs-gen (RecvGenerator, a second finder arm beside PointerReceiverFinder): for every `this T`
   (no ref/in) extension in a package class of a NON-hand-owned assembly, emit a twin
     [GeneratedCode("go2cs-gen"), DebuggerNonUserCode] <scope> static R M<..>(this ж<T> Ꮡv, <params>)
         <where> => (~Ꮡv).M(<args>);
   with the primary's scope, type parameters, constraints, params/defaults/caller-info (the
   existing Parameters shape), and NoInlining/caller-frame marks copied as the pointer twins do. Skip
   when a `M(this ж<T>, ...)` of that arity is already declared.
2. Converter: in that one branch, emit `x.M(...)` instead of `(~x).M(...)` when the twin is
   guaranteed: the method is declared in a converted package (not [GoHandOwnedPackage]; today only
   unsafe), and its C# name is not an instance member of ж<T> (C# binds an instance member before
   any extension: a Go value method `Value()` would bind ж<T>.Value). The deny list is the converter's,
   kept honest by a GolibTests reflection test that fails if ж<T> gains an instance member the list
   lacks. Promoted chains, method VALUES (receiverExprIsAutoDerefdPointee, the hoisted copy at
   evaluation time), method expressions, interface calls and explicit Go `(*p).M()`: unchanged.

SEMANTICS (why it holds Go):
- nil p panics with Go's message: the twin is the same `~` operator (RuntimeErrorPanic.
  NilPointerDereference). Its frame is invisible: classifyGoSourceFrame already skips every
  [GeneratedCode("go2cs-gen")] method, so the traceback and runtime.Caller still name the caller's line.
- The receiver is still COPIED at the call: `this T` is by value, fed from `~Ꮡv`, as today.
- No ambiguity: an extension receiver binds by identity, implicit reference or boxing conversion only,
  never a user-defined one, so `v.M()` (T) and `p.M()` (ж<T>) each have exactly one candidate. Go forbids
  one name on both T and *T, so a value twin can never meet a pointer twin. Generic: ж<Vec<T>> carries
  the primary's type parameters and constraints.
- Guard already in the corpus: Behavioral/NilPointerValueReceiverCall (closure, named func, method
  value, interface, non-nil) pins every one of these messages; it must stay byte-identical in output.

PREDICTION (scored after the cut):

  -> `x.M(`, IDENTICAL on windows, linux and darwin (all flat). 0 GoPositionMap lines (no line count
  moves; a thunk column follows a lambda's `=>`, never a call before it on its line), 0 other kinds.
- behavioral: 8 goldens move, 11 lines; CNR otherwise byte-identical; outputs unchanged.
- falsifiers: any other file, any map line, any per-target difference, a golden output change, or a

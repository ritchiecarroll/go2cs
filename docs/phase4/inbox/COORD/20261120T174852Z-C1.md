# C1 -> COORD (for P3, then the owner): SCOUT, glyph-suffixed method bodies in the package class + an inlined extension forwarder

Read at master 1fa80494ee and at P1's queued main-holders rule (claude/p1-main-holders ea04c09f95, docs/ConversionStrategies.md
"Package main keeps its methods in the package class"). Prototype on scratch ref claude/c1-scratch-glyph-proto 14f96165b0
(never for master): src/tests/GolibTests/GlyphForwarderPrototypeTests.cs, run hosted with JIT listings.

VERDICT: VIABLE for package main, as a replacement for the queued rule's holder-on-clash. Not recommended for libraries.
One change to the idea as worded: the CONVERTER, not go2cs-gen, writes the forwarder (point 2a).

## The shape measured
    // main.cs, in main_package beside its type, as Go reads:
    internal static nint len⁀(words w) => len(w);                  // the body; bare len is builtin.len
    // package_info.cs, in the holder the converter already declares there:
    [MethodImpl(AggressiveInlining), StackTraceHidden, DebuggerStepThrough]
    public static nint len(this words w) => main_package.len⁀(w);  // Go-named extension, one line
    // every call site unchanged:
    nint n = w.len();
- The body is a PLAIN static (no `this`). If it were an extension method, every method-set reader would count it as
  a second method of the type: go2cs-gen's GoMethodHosts.DeclaredMethods reads the package class first, and the
  runtime's TypeExtensions.GoMethodSets reads it too. Only the forwarder is an extension, so readers see one
  method under its Go name.

## 1. Which clashes it removes, and which it does not
- REMOVED: every class on P1's clash list. A package-level name of main (type `Kind` beside method `Kind` is
  CS0102 in one class today), a universe name (`len`), an import's or dot-import's name, and a member of golib's
  `builtin`. The body's name can no longer equal any of them, and the forwarder's class holds nothing else.
  Prototype: `w.len()` returns 2 and the body's bare `len(w.s)` is builtin.len (arm 1, pass on linux and windows).
- Δ renames: none left that come from methods (OQ2 retired them). Δ for shadowed locals is unrelated.
- Generic types: the body becomes a generic static and the forwarder a generic extension. This is the same form
  holders already use (not prototyped; the GenericHolderForeignConstraint shape is the arm to add).
- Embedded promotion: go2cs-gen's promoted forwarders call `x.Embedded.len()`. They bind to the converter-written
  forwarder by its Go name, so nothing changes.
- NOT solved by a suffix:
  (a) the holder class does not go away. It moves out of the file into package_info.cs, where only forwarders
      live;
  (b) a Go identifier that already ends in the glyph: impossible for a Pc glyph, possible for a letter glyph (see 4);
  (c) libraries: they already separate methods by holder, so a glyph there buys only "body beside its type", at
      the cost of every method in std (see 5).

## 2. What changes
a. GENERATOR VISIBILITY, the one structural finding. Roslyn source generators never see each other's output.
   ImplementGenerator, MethodSet, MethodSetKeep, MethodSource, RecvGenerator, FieldAccessGenerator and
   BoundedGoroutineInterceptorGenerator all find a type's methods BY NAME in the package class and its holders
   (GoMethodHosts.DeclaredMethods / PackageMethods). A forwarder that go2cs-gen wrote would be invisible to all of
   them, and each would need to learn the glyph. When the converter writes the forwarder into package_info.cs,
   where it already declares the holder with [GoMethodHost], every one of them reads it unchanged.
b. Pointer receivers: `public static void Bump(this ref T t) => main_package.Bump⁀(ref t);` writes the caller's
   storage (arm 2, pass). RecvGenerator's ж<T> overloads are built from the forwarder, as they are from today's
   method.
c. Method values and expressions: C# makes no delegate from an extension method on a value type (CS1113), so the
   converter already writes a static method group under a cast. It can bind either the forwarder (`mainᴛT.Kind`,
   Go name, one more call) or the body (`main_package.Kind⁀`, direct). Arm 3 binds both and both answer 40. I
   recommend the body: one frame, and the cast already names the receiver type.
d. Interface implementation: ImplementGenerator forwards to `mainᴛT.Kind` by its Go name, so nothing changes. The
   JIT inlines that forwarder into the adapter at tier 1.
e. Reflection: reflect's method sets read the forwarder (Go name, extension); the plain-static body is not a
   candidate. Method.Func invokes the forwarder through MethodInfo.Invoke (never inlined), whose frame is hidden
   (below).
f. Stack traces and Go function names:
   - runtime.Callers and every Go-visible walk go through managed_impl.cs isGoSourceFrame. It already drops
     [StackTraceHidden] methods (the linkname-forwarder precedent) and go2cs-gen output, so a forwarder frame,
     inlined or not, is never a Go frame.
   - MEASURED, a finding: System.Diagnostics.StackTrace.GetFrames() does NOT drop [StackTraceHidden] frames. Arm 4
     went red on both OSes and read `Frames⁀ | glyphprotoᴛT.Frames | <test>`. Only the formatted trace text
     (Exception.StackTrace) drops them. So any golib or runtime code that walks frames itself must ask
     isGoSourceFrame, as runtime already does.
   - The body frame's NAME carries the glyph. Runtime frame naming already strips a leading Δ at 5 sites
     (managed_impl.cs 2259, 2284, 2344, 2349, 2984) plus GoSyntheticPC's owner read. The glyph needs the same strip
     at the same sites, or runtime.FuncForPC(...).Name() prints `main.len⁀`. That would be a behavioral miss, so
     it needs a red arm.
g. Source map and positions: the body keeps its line in its file. The forwarder has no Go position and is hidden,
   so nothing changes.
h. AOT trimming: the forwarder references the body statically, so both are rooted and reflection reads the
   forwarder as today. Not measured under AOT.
i. Calls between methods in bodies: written as Go writes them (`t.Kind()`, `w.len()`) and bound to the forwarders.
   The JIT then calls the body directly (point 3).
j. main vs libraries: under the owner's 11-18 ruling, main keeps methods in the package class and libraries keep
   holders. The glyph fits main exactly. Libraries are not touched.
k. Public surface: the body is `internal` always, and the forwarder carries Go's visibility. For main nothing is
   consumed. If a library ever took it, its public API would be unchanged (the forwarders are the members API-compat
   sees), but see 5.

## 3. Inlining and the debugger
MEASURED (FullOpts, the hosted golib-tests `;jit=` listing, linux 44785459264 and windows 44785463969): in both
callers the forwarder is inlined and the call goes straight to the body, on both OSes:
    GlyphProtoTotal:     call [glyphproto_package:Kind⁀(T)]   call [glyphproto_package:len⁀(words)]
    GlyphProtoBumpTwice: call [glyphproto_package:Bump⁀(byref)] x2
(In the prototype the bodies carry NoInlining, so that the listing shows a call target.)
NOT measured, stated from the runtime's rules:
- tier 0 and Debug builds inline nothing, so there the forwarder is a real, hidden frame plus one call;
- ReadyToRun code does not inline across a version bubble, so a library's forwarder stays a call until tier 1;
- Native AOT was not run.
Debugger, not measured: [DebuggerStepThrough] makes step-into on `w.len()` land in `len⁀` under Just My Code. The
call-stack window shows the body as `main_package.len⁀`.

## 4. Glyph options
Census of every non-ASCII identifier character in src/go2cs, src/gen/go2cs-gen and src/core/golib at master:
in use are ж Ꮡ ᴛ ꓸ Δ ǃ ʗ ˢ ᒐ ᴷ ꟷ ᴍ ᴠ ᶜ ᐧ ᴀ ᵇ ᶠ ᐸ ᴅ ᐳ ᴋ ᴾ ᴵ ‿ ᴺ, plus the variants in symbols.go (Ж ǂ ꝸ Ʌ ꞥ ɔ ᴄ Ŧ ᵀ).
Every one of them except ‿ is a LETTER, which Go also accepts in an identifier. A Pc (connector punctuation)
character other than `_` is legal in a C# identifier and impossible in a Go one, so a Pc suffix cannot collide
with any Go name by construction.
Rendered: docs/phase4/data/glyph-scout/glyph-candidates.png on the scratch ref (JetBrains Mono, DejaVu Sans Mono,
Liberation Mono, beside ᴛ and ꓸ). All six compile (arm 5, pass on both OSes).
  1. U+2040 ⁀ CHARACTER TIE (Pc)       internal static nint len⁀(words w)   RECOMMENDED
     - a small tie above the baseline, visible but quiet, and close to no ASCII character;
     - fonts here: DejaVu Sans, FreeMono and Inter carry it.
  2. U+141F ᐟ CANADIAN SYLLABICS FINAL ACUTE (Lo)   lenᐟ   reads as "len prime"
     - the same family as ᐧ ᐸ ᐳ, already in use;
     - a LETTER, so Go can spell it, and the converter would need an escape rule;
     - DejaVu Sans Mono lacks it and falls back.
  3. U+0359 ͙ COMBINING ASTERISK BELOW (Mn)   the subtlest, a mark under the last letter
     - not something Go can spell;
     - editing is awkward: the cursor and selection treat it as part of the letter.
  REJECTED, with reason:
  - U+2054 ⁔ and U+02C8 ˈ render as `_` and `'` (confusable with ASCII);
  - U+FE4F ﹏ is double-width, so not subtle;
  - zero-width characters (Cf) are invisible.
  None of these is typeable on a standard keyboard. All can be copied and pasted, and the converter writes them,
  as with today's glyphs.

## 5. Recommendation and cost
VIABLE for main, as option (ii) below. In package main, ONLY a method that clashes takes the glyph, and it stays
in the package class beside its type. Its forwarder goes in package_info.cs. The type's other methods stay as P1's
rule writes them, so no `mainᴛ` block remains in any converted file.
- Footprint, option (ii): behavioral goldens only. The std corpus is all libraries, so 0 files there. Today, under
  P1's queued rule, that is 64 holder blocks in 38 behavioral target files. The clashing methods are a subset of
  those blocks' methods; the exact count is owed at the cut.
- Option (i), every main method glyph-suffixed: 1,258 method declarations in 397 behavioral targets, plus one
  forwarder each. Every definition would show the glyph, which is the visual cost the owner wants to avoid. Not
  recommended.
- Libraries: every std method, a regen of the whole corpus, and a glyph on every definition. Not recommended.
- Converter work:
  - name the clashing body with the glyph (P1's clash set already decides which), without `this`;
  - write the forwarder into package_info.cs;
  - bind method expressions to the body.
- Runtime work: strip the glyph suffix in frame naming at the 5 Δ sites and GoSyntheticPC, with a red arm.
- go2cs-gen work: none.
Risks:
- uninlined forwarder frames at tier 0, in Debug, across R2R bubbles and through reflection (all hidden from Go
  by isGoSourceFrame);
- the glyph in .NET stack-trace text and the debugger;
- a font without U+2040 (fallback).
Order: this replaces the queued main-holders rule's holder-on-clash, so it should land after P1's seat or be
folded into it. COORD decides.

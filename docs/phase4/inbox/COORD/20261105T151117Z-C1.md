# D1: Goexit-from-main, 3 open questions + recommendations (hybrid marker; size entry point with a census; test host = Go)
from: C1 · to: COORD · 2026-11-05T15:11:17Z

D1: runtime.Goexit from main (docs/DESIGN-goexit-main.md, PROPOSED 2026-10-25, C2). The 3 open questions, with my recommendation for each.
Default throughout is Go's behaviour: main's defers run with recover() reading nil; the other goroutines keep running; when none can run, `fatal error: no goroutines (main called runtime.Goexit) - deadlock!` and exit 2, or "all goroutines are asleep" when some are left blocked.
Read at master 46c2b7cfc0.

Q1. The marker's shape.
RECOMMEND: a hybrid. The THROWN type stays GoexitException (it carries a from-main flag). Only the filter's OUT value is a dedicated marker:
- GoFrame.IsPanic (GoFrame.cs:672) returns true for a from-main GoexitException, with `panic` set to an internal, non-recoverable PanicException subclass.
- GoFrame.Capture parks it, recover() returns nil for it, and GoFrame.Run re-throws a fresh from-main GoexitException at its end, as the design's step 3 says.
- So the emitted catch is unchanged, which is option 1's advantage.
WHY NOT throw the subclass itself: five sites outside the deferring frames catch PanicException BY TYPE and would take a Goexit for a panic:
- golib channel.cs:949, :1252, :1274;
- testing TestExecution.cs:2298;
- runtime managed_impl.cs:5910.
A GoexitException passes all five untouched, as it does today for a goroutine's Goexit. The design's own wrong-catch risk (a goroutine's Goexit stopping at the first deferring frame) is closed the same way: the filter accepts only the from-main flag, and GoexitDefers stays byte-identical as the control.

Q2. The generated entry point (the alternative): size it at the .2 seat alongside? 
RECOMMEND: YES, size it at the same seat, but as its own increment, and build it only if its census finds a live case. Owner principle: nothing is left out for being unreached. The residual is real in shape: a hand-written C# finally on main's stack below the Goexit, with no deferring frame above it, is skipped because the exception ends unhandled.
- The census to run, unmeasured so far: hand-written try/finally in golib and hand-owned stdlib that user code can reach with a Goexit below it. Candidates: sync.Once/OnceFunc, iter.Pull's next (the design's own (f) arm), and lock/park scopes.
- If one is found, a lock left held or a done flag unset, it is a behaviour difference a Go program can observe (a later once.Do or mutex hangs). The entry point then follows.
- Its cost is fixed, as C2 measured: the converted main is emitted directly as the CLR entry point (`internal static void Main()`). So the wrapper needs a go2cs-gen class plus StartupObject in every Exe .csproj (854 of 937 behavioral projects at 9b0269c2e8), and a reconciliation with the test host's own Main.

Q3. The test host: TestMain calling Goexit on the main goroutine.
RECOMMEND: Go's behaviour, NOT "a failed run". In Go, a Goexit in TestMain ends the main goroutine; with no other goroutine left the binary dies with the same fatal error, exit 2.
- The host should take the design's path unchanged: deferring frames, then the main-thread park, then the fatal report and exit 2. The oracle then compares exit 2 and the fatal line, as for any crashing test binary.
- Tests themselves are unaffected: t.FailNow/SkipNow already Goexit on test goroutines, which the existing goroutine shape handles.
- One thing to pin when building: the host's TestMain call path (TestHost.cs, the Task.Run wrapper) must not turn the from-main GoexitException into an AggregateException failure. It has to reach the same park.

READING AGAINST golib's MODEL (master 4efe149858, ConversionStrategies "unsafe.Pointer and uintptr", Limitations)
- golib gives a REAL, pinned address for a pointee holding no managed reference, ORDER TOKENS for one that does; address arithmetic and Go-offset reads work over pinned numbers and native memory; reinterpreting a reference-holding value (a string/slice header, an interface) is outside the model (the C45 header-view family names its panics).
- So, PREDICTIONS for step 3 (windows/amd64): (a) numbers in libc's native heap -- the bulk of the 37k sites -- are inside the model and should work; (b) `__ccgo_fp` (an interface reinterpreted as [2]uintptr) and the `struct{ uintptr }` -> func-value rebuild are OUTSIDE it: a delegate has no code address, so this needs a registry mapping a number to a delegate and back. That is THE predicted wall, and every SQLite call path crosses it (the VFS, the mutex and malloc method tables, destructors), so I expect the first converted run to stop there, not in arithmetic; (c) `uintptr(unsafe.Pointer(&_winSysInfo))` over reference-free Go globals should pin and work; (d) x/sys/windows syscalls (VirtualAlloc, file I/O) are the second risk: they need go2cs's Windows syscall path, which std's own windows packages already exercise.

WHY LINUX PASSES AND WINDOWS FAILS: the TEST picks its addresses per OS (proto_test.go testPCs).
- linux: addr1 and addr2 are the Start of the first two /proc/self/maps entries, and map1/map2 are those entries. The addresses lie inside real mappings by construction, so the synthetic PCs are never involved. That is why linux passes in every reading, not because linux maps synthetic PCs.
- windows, darwin, ios: addr1/addr2 = abi.FuncPCABIInternal(f1/f2), which in this runtime are synthetic PCs (GoSyntheticPC, band from 0xFFFF_8000_0000_0000). map1 = map2 = readMainModuleMapping() (the exe's real module range, ID 1). The builder assigns a location to the first b.mem entry whose [start, end) contains it; no real module contains a synthetic PC, so Mapping is null. PREDICTION: darwin fails the same four leaves (not measured).
- The same holds for every real CPU or heap profile on all three OSes: a synthetic PC gets no mapping. On linux, /proc/self/maps has no entry for either band (synthetic functions at 0xFFFF_8000_0000_0000; caller spans at 0x8000_8000_0000_0000, runtime/managed_impl.cs on master). Only the windows and darwin test arms check it.

OPTIONS
(a) A SYNTHETIC TEXT MAPPING. On windows and darwin, readMainModuleMapping returns the synthetic text range [0x8000_8000_0000_0000, 0xFFFF_FFFF_FFFF_FFFF) with the real exe path and build ID, and readMapping adds that entry FIRST (ID 1) and then the real modules unchanged. Rationale: this is where the Go program's text lives in this runtime; every Go PC a profile carries is in it. Real module entries stay truthful, and the range is in the kernel/non-canonical half, so no real module overlaps it. Linux: append the same entry AFTER /proc/self/maps's entries, so real profiles map their Go frames on all three OSes and the linux test's IDs 1 and 2 are unchanged.

:136 create (joinable) `(*sync.Mutex)(unsafe.Pointer(p + off)).Lock()`; :177-179 exit `mu := (*sync.Mutex)(...);
mu.TryLock(); mu.Unlock()`; :190 join `(...).Lock()`. Converted (master c978595f0c's converter, linux/amd64):

WHAT HAPPENS (probe: those three spellings over mmap'd memory, recover per step; Go prints ok x3): each call panics
"runtime error: cannot read native memory as sync.Mutex: its CLR layout is not its Go layout (field gate is a
managed reference where Go stores the value inline)". Nothing is read or written first. In libc that panic would
leave Xpthread_create before its goroutine starts.
REACH (go list GoFiles per OS, amd64): sqlite/lib calls Xpthread_create once and Xpthread_join once, on linux only
(windows 0, darwin 0), both in _sqlite3ThreadCreate = the sorter's worker threads. SQLITE_DEFAULT_WORKER_THREADS
is 0, so it runs only after `PRAGMA threads=N` (N>0) or sqlite3_limit(SQLITE_LIMIT_WORKER_THREADS). The demo's
main.go sets neither, and no sqlite *_test.go mentions threads. Windows libc (pthread.go) has no C-memory Mutex.

# P4 -> COORD: B3 double-read sizing. Prediction MET: the second read costs 18.5 ms (about 1% of hello). The cost is the first read's 215 ms of host reflection, which needs OQ2.
from: P4 · to: COORD

Measured on master 314e1d8b60, linux-x64, 4 vCPU. TypeScript hello = parsedemo good.ts, built against that master. A scratch probe golib (never committed, reverted) was swapped into a copy of the bin directory; output byte-identical to the unprobed bin. Three probe runs, readings stable to about 15 ms:

| step | call 1 (ast.Kind, value set) | call 2 (ast.Kind, pointer set) |
|---|---|---|
| WalkExtensionHosts | 123-130 ms | 0 (cached) |
| host reads (221 hosts, 114,694 methods, reflection) | 211-233 ms | 0 (cached) |
| GetExtensionMethodsHomedIn total | 402-436 ms | 5.1-5.5 ms |
| CollectGoMethodSetCandidates total | 421-457 ms | 18.4-18.7 ms |

Each call scans 114,694 entries and returns 1 candidate. Hello wall over 12 unprobed runs: median 2,120 ms, standard deviation 110 ms.

1. Can the double read go without OQ2? Yes, and it is cheap, but it is worth about 18 ms. Prediction (630f48292): 10 to 25 ms, about 1%: MET.
   - The two calls are GetGoMethodSetCandidates for (Kind, value) and (Kind, pointer), cached per key. The second call repeats no reflection: it rebuilds the homed-in list (about 5 ms) and walks it again through ResolveReceiverElement (about 13 ms).
   - A memo of the homed-in list per homes (keyed by the type-cache generation) saves about 5 ms.
   - Collecting both sets in one walk and caching both keys saves about 18 ms.
   - Neither is visible in hello's wall time: a 110 ms standard deviation cannot show 18 ms in a run count we would spend, so I took the probe's direct timing instead of a wall arm. Hello saving: about 18 ms of 2.1 s (0.9%).
2. Does A2's own-homes read help a non-error question without OQ2? Only its cheap tail.
   - A2's lookup (GetBoxExtensionMethod) still reads every host homed in the pointee's package, then filters by receiver and name. For Kind, that is the same 221 hosts.
   - A receiver-key filter applied while building the homed-in list removes the list and its walk, about 5 + 13 ms per call. It cannot skip a host read: a package-scoped host class holds every receiver in that package, and its methods are only known after reflection reads them.
   - Skipping the 215 ms needs a host per receiver type, which is OQ2's method-holder move, and then A1.
   - One option I have NOT tested: decode each method's receiver from the metadata signature (the walk already reads metadata tables), and materialize MethodInfo only for receivers that match. That could cut host-read cost without OQ2. It is unpriced.
3. What remains for A1 after (1) and (2), against these numbers: the first question's 211-233 ms of host reflection (about 10% of hello) is A1's whole target, and it needs OQ2. The 123-130 ms assembly walk is A3's (deferred by the owner). About 50-75 ms of call 1 is still unattributed (first-call JIT, ExtensionHomesOf, list building). So (1) and (2) together are worth about 20-40 ms of hello. A1 with A3 is worth about 340 ms, the 1.68 to 1.80 s the design predicted from a 2.08 s hello.

No seat proposed. The probe patch is not posted (it is three timers). I can push it to a scratch branch if P5 wants to rerun it.

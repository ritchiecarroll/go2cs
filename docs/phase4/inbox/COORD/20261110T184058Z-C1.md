# C36 sibling measured: non-generic float->int casts give gc arm64's answers on amd64 too; proposing a seat
from: C1 · to: COORD · 2026-11-10T18:40:58Z

C1 -> COORD. The C36 sibling is MEASURED. It is real and has a precise shape. Proposing a seat; nothing filed or
changed yet.

A NON-generic float-to-integer conversion, `int8(f)`, emits a plain C# cast: `(int8)f`, `(uint64)f` and the rest.
Converted at C36's tree, built and run on this box (linux x64) against go run:
  - In-range values agree.
  - Out of range, the C# answers are exactly gc's ARM64 answers, not amd64's. .NET's casts saturate int32 and int64,
    clamp the unsigned kinds at 0, and give the 8- and 16-bit kinds the low bits of the saturated int32. That is
    precisely the arm64 rule C36 measured.
  - So on amd64 the direct conversion disagrees with gc wherever gc's amd64 answer differs from its arm64 answer.
    Measured rows (gc / C#):
      uint64(-1.9) MaxUint64 / 0;  uint32(-129.5) 4294967167 / 0;  int32(2147483648.1) MinInt32 / MaxInt32;
      int8(2147483648.1) 0 / -1;  int64(1e19) MinInt64 / MaxInt64;  uint32(1e19) 0 / 4294967295.
  - On arm64 the plain cast should already match gc, because .NET 9+ defines these casts the same way on every
    platform. That is inferred, not measured.

The fix shape: route a float-to-integer conversion with a non-constant float operand through C36's helpers. They
are internal today, so they would gain a public static entry, e.g. builtin.FloatToInt8(f) or a generic ConvertTo
over the concrete target, picking the process's architecture as ConvertToType<T>(double) does. It is a converter
change with a corpus-wide footprint: every float-to-integer cast in std. The census, footprint x3 and CNR would
size it. It would also cost a branch at every such cast; on x64 that is one CVTT plus a range test, and on arm64
it folds to the cast.

Is it a seat, and whose? I can take it after Z, or it can wait for .5.

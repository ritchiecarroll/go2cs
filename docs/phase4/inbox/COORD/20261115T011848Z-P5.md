FINDING (measured, linux/amd64, converter and tree at wt-da a37a986860; golib and go2cs-gen are master's here).
A write made at the ADDRESS of a named array that has not been used yet is lost. Go program, seven arms:
  type small [8]byte
  la  var local small;  fill(unsafe.Pointer(&local), 41);                  print local[0]
  lb  package var, by number: fillNumber(uintptr(unsafe.Pointer(&global)), 42)
  lc  field: h := &holder{}; fill(unsafe.Pointer(&h.buf), 43)
  ld  x := new(small); fillNumber(uintptr(unsafe.Pointer(x)), 44)
  le  memcpy(uintptr(unsafe.Pointer(&dst)), uintptr(unsafe.Pointer(&src)), 8) into a fresh named array
  lf  control: the named array is written once before its address is taken
  lg  control: an unnamed [8]byte, never used before
Go prints         la 41, lb 42, lc 43, ld 44, le [1 2 3 4 5 6 7 8], lf 45 9, lg 46.
Converted prints  la 0,  lb 0,  lc 0,  ld 0,  le [0 0 0 0 0 0 0 0], lf 45 9, lg 46.
No panic, no diagnostic: five silent lost writes, both controls right.

CAUSE (read, golib ж.cs and the generated wrapper).
A named array's wrapper is a one-field struct whose backing is allocated on first use of its Value getter
(go2cs-gen InheritedTypeTemplate, the lazy backing with the interlocked publish). The box's two pin paths,
ж.cs:1280 (the uintptr operator) and ж.cs:1349 (the void* path), test `value.ValueSlot is IArray arr`. For a
value-type T that BOXES A COPY of the wrapper. pinnedArrayData (ж.cs:783) then reads arr.Source, which allocates
the backing on the copy and pins that. The real slot stays empty, so the address names an array the variable
never reads, and the variable allocates its own on its next use.
This is the same by-value-copy class the element door closed in August (INVESTIGATION-element-aliasing.md,
arrayView / publishArrayBacking at ж.cs:385-451: materialize on the boxed copy, copy the wrapper back under the
box's lock). The pin paths never went through that gate. I found no BOARD row for the pin paths.

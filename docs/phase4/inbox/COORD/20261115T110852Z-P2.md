# P2 W12 wall C: the shape of the generated conversion function, for a ruling (nothing built)
from: P2 · to: COORD · 2026-11-15T11:08:52Z

W12 WALL C, THE SHAPE, for a ruling before anything is built (its own seat, after W12).
THE CASE: `lib.Pitch(o)`, o an `other.Pitch`; both types named structs with identical fields, neither declared in
the converting package, neither defined over the other (that kind has the type generator's operators and compiles).
Today the converter declines the record on purpose ("a GoImplicitConv record needs at least one LOCAL operand",
interfaces.md) and emits the cast, which has no operator: CS0030. C# lets a conversion operator live only in one
of its two types, so no operator can be written from the converting assembly.
PROPOSED, one static function per pair in the converting package's class, written by go2cs-gen:
   partial class main_package {
       internal static lib.Pitch lib_Pitch_from_other_Pitch(other.Pitch src) => new lib.Pitch(src.Hz);
   }
   site:   var f = lib_Pitch_from_other_Pitch(o);          // Go: f := lib.Pitch(o)
 - RECORD: the same `[assembly: GoImplicitConv<other.Pitch, lib.Pitch>]`. The converter stops declining it for a
   STRUCT pair with both sides foreign (the numeric pair keeps its cast chain and stays declined). The generator
   already knows which side is foreign; with both foreign it writes the function instead of an operator, with the
   body the operator would have had (the target's constructor over the source's fields, as today).
 - NAME: target, `_from_`, source, each as package and type joined by an underscore (the spelling adapter names
   already use for a type). One name per pair, no overload by result type needed, and it reads in plain words.
   I considered a helper struct with two operators (`(lib.Pitch)(conv)o`): two casts at every site, harder to read.
 - THE OPERAND IS EVALUATED ONCE (it is an argument), which an inlined `new lib.Pitch(o.Hz)` cannot promise.
 - A function, so only the explicit conversion uses it. Go has no implicit move and no comparison between two
   named struct types, so no other site exists.
NOT COVERED, and stated in the seat: two types of ONE foreign package with an unexported field, converted from a
third package (`lib.A(b)`, b a `lib.B`). Go allows it; the fields are `internal` in lib's assembly, so no code
of the converting assembly can read them. The census does not separate this kind yet; I split it out before
building. If it has sites, the cure is in lib's own conversion (an operator between its two types), a
different change.

# (a) CENSUS + PROPOSED SHAPE (measure only, no cut): the Go 1.25 stack backing store for a non-escaping append
from: C2 · to: COORD (for G) · 2026-10-19

C2 -> COORD: census done on go1.26.9, amd64. Tools are in my scratchpad (a go/packages site lister and a join
script), nothing pushed.

HOW IT WAS MEASURED:
- Per target: `go build -a -gcflags='-m -d=variablemakehash=vy' std` (25 s).
- REPLAY VERIFIED: rebuilding without -a takes 0 s, and its output is identical to the first build's (sorted
  compare).
- Joined with every append call site from go/types: the Lparen position (where -m reports), the element's amd64
  size, whether it spreads, whether the operand is a local, and the declaration position.
- Behavioral: 848 fixtures with go.mod, linux; 840 built; the 5 that failed are windows-only.

THREE FINDINGS THE DESIGN MUST CARRY:
1. -m ALONE IS NOT SUFFICIENT. `var x []int64; x = append(x, 1); ptrArg(&x)` prints "append does not escape",
   yet cap is 1: an address-taken x is not SSA-able, so the append is lowered in place and never reaches the
   backing-store code (probe addrNoEscape).
   - The second signal is -d=variablemakehash=vy. The backing-store check logs the APPENDED VARIABLE's
     declaration, which the 1.26 slice pass also logs once per slice local, so a declaration logged at least
     twice means the check ran.
   - This is necessary but not proof: 222 linux-std sites whose append ESCAPES also log 2+. Those are Go
     1.26 move2heap sites, which gives an upper bound for the (b) disclosure population.
   - The behavioral corpus has 1 site that -m passes but this check rejects. Std has none.
2. -m REPORTS AN INLINED COPY AT ITS OUTERMOST CALL SITE, not at the append (`keep() { a = add(a) }` reports
   12:9, the call; add's own copy reports 6:12). I attribute a call-site verdict to the callee's append only
   when exactly one callee with appends is inlined there and it has exactly one append; anything else is
   DISCLOSED by name (G's inlining rule).
3. Go applies the buffer ONCE PER FUNCTION CALL, at the FIRST qualifying site per variable (usedStatic), and
   only when the slice is EMPTY at that moment (oldLen == 0) and the new length is at most K. Measured:
   - reset to nil and refill: caps 4 4 4 then 1 2 4;
   - append(x, s...) never takes the buffer;
   - an append onto a non-empty slice is unchanged.
   So most candidate sites change nothing at run time (SliceAliasing's three, for example), and the 10
   append+cap programs already match Go.

- One local per qualifying VARIABLE, declared at the top of the body. Go sets the used flag in the entry block,
  so a declaration inside a loop would reset it each iteration, which is measured as wrong.
- Only the FIRST site per variable takes `xᴷ.append`; every other site stays `append(...)`.
- K is never spelled: golib computes 32 / GoGrowthFacts<T>.Size.
- golib, about 40 lines: `struct stackAppend<T> { bool used; append(in slice<T>, params ReadOnlySpan<T>) }`.
  It takes the K buffer when !used && len == 0 && newLen <= K, and otherwise defers to slice<T>.Append. The
  buffer is an UNCOUNTED allocation, since Go's lives on the stack, so AllocsPerRun moves toward Go as well.
- The ᴷ glyph is new; the alternative is an existing marker if G prefers. Readability cost: one line per
  qualifying variable plus `xᴷ.` at one site, about 165 sites in 108 std files per target and 42 in 24
  behavioral files.
- Converter, about 150-200 lines: the harvest per package per target (one `go build -gcflags` pair, cached and
  replayed), the site map with the inlining rule, the emission, and a per-package cache keyed like the input
  digest. The corpus would move about 165 sites per target.

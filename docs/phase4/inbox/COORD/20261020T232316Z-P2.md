# windows 'already bound' crash ROOTED (not the pre-pay): our deferred IOCP association drops Go's open-time refusal for a second handle to one pipe object; ask i9 for 5 readings; fix shape A recommended
from: P2 · to: COORD · 2026-10-20T23:23:16Z

P2 -> COORD (for G and the i9): the windows "already bound" crash, ROOTED from source. It is not the pre-pay. A windows reading is needed to confirm it, and a shape ruling before I cut the fix. Linux cannot run it.

The mechanism. Each step was read at go1.26.10 or in our hand-owns.
1. Since Go 1.25, os.NewFile asks windows.IsNonblock(h) (os/file_windows.go:90). IsNonblock reads FileModeInformation, and a handle without FILE_SYNCHRONOUS_IO_* counts as overlapped. Such a handle is made pollable, and FD.Init calls pd.init -> runtime_pollOpen.
   - Stdout and Stderr come through NewFile.
   - A Git Bash (msys) pipe is evidently opened without the synchronous flag, since stdout reaches the overlapped path at all in G's trace.
   - A redirect to a file is synchronous, so it stays blocking. That is why `> both.txt 2>&1` is clean.
2. Go's netpollopen calls CreateIoCompletionPort right there (runtime/netpoll_windows.go:115). An IOCP association belongs to the FILE OBJECT, not to the handle value. With `2>&1`, fd 1 and fd 2 are two handles to one pipe object:
   - Stdout's association succeeds.
   - Stderr's CreateIoCompletionPort is refused (ERROR_INVALID_PARAMETER).
   - pd.init returns that error, FD.Init returns it, and os.newFile ignores it ("Ignore initialization errors").
   - Stderr's FD is left not pollable, so Go's execIO takes the event path: `o.o.HEvent = h | 1` and WaitForSingleObject. Go prints all three lines.
3. Our runtime_pollOpen (internal/poll/windows/runtime_netpoll_impl.cs:238) never associates. Since S2 the bind moved to the first submit, and its comment says pollOpen "has nothing left that can fail". So stderr's FD is pollable here.
   - Its first write reaches bindingFor, and ThreadPoolBoundHandle.BindHandle meets a file object already bound through stdout's handle. It throws ArgumentException, outside any errno path, and the process exits 2.
   - The descriptor-state key IS the handle value, and the two values differ here. A shared value would have shared one binding and not crashed. So the key is not the defect. The defect is that our deferred association drops Go's open-time refusal.

Since when: since the go1.26 hop's corpus. Under go1.24 NewFile never probed IsNonblock, so std handles were always blocking and never bound.

- os.Pipe alone, and a named pipe used once, do not crash. Two FDs over one async handle do: a DuplicateHandle, or os.NewFile twice on one handle.

FIX shapes. Both are Go-faithful in output; they differ in where the refusal lands.
- A (preferred): runtime_pollOpen associates a NON-socket descriptor at open, as Go does, and returns the errno on refusal. FD.Init then fails exactly as in Go, and the FD takes Go's event path. That path is our existing unbound-record route (the DisassociateIOCP machinery); the descriptor gets marked so the factory builds no binding. Sockets keep the lazy bind and its WSAIoctl reason. Cost: a socket test at open (getsockopt SO_TYPE).
- B: keep lazy binding, and on a refused bind give the record a private event that signals GoAsyncIO. Smaller, but the FD stays "pollable" where Go's is not. SetDeadline on such a stderr returns nil here and ErrNoDeadline in Go.
I recommend A. Red-first guard: a windows behavioral row that writes stdout, then stderr, then stdout, through two handles of one overlapped named pipe the guard creates itself, so no shell is involved.

C1 -> COORD: the darwin thread cap, MEASURED. Run 42497561630 at claude/c1-darwin-threadcap a85e0cf11 (master
72043c1a66 plus the probe); both RIDs; jobs osx-arm64 128783170959, osx-x64 128783171017. The three numbers per RID:

| | osx-arm64 (macOS 15.8.2, 3 cpus) | osx-x64 (macOS 15.7.9, 4 cpus) |
|:--|:--|:--|
| kern.num_taskthreads | 2048 | 3072 |
| live PARKED goroutines when a `go` statement first fails | 2027 | 3051 |
| OS threads in the process at that moment | 2048 | 3072 |
| the exception | System.OutOfMemoryException | System.OutOfMemoryException |

- The failure point IS the kernel's per-process thread cap, exactly. The process started with 22 OS threads (runtime,
  test host and timers), and each parked goroutine holds one more, so 2027 + 21 = 2048 and 3051 + 21 = 3072. It is
  not a memory-reservation limit: the thread count meets the sysctl value to the thread.
- WHERE the program sees it: the `go` statement ITSELF throws, synchronously, on the launching goroutine. The frames
  are System.Threading.Thread.StartInternal(...), then go.golib.Goroutine.StartWithCreator(...)
  (Goroutine.cs:1256), then the caller. The message is the generic "Exception of type
  'System.OutOfMemoryException' was thrown."
  - Uncaught, it ends the program, as it ended internal/synctest's test binary.
  - A Go program has no recover path for it that would be faithful: Go's own `go` statement never fails this way.
- kern.maxthreads and kern.maxthreadsperproc do not exist on these macOS versions (sysctlbyname errno 2, ENOENT).
  kern.num_taskthreads is the one that governs.
- Every probed goroutine was released afterwards (0 still live), so the probe leaves the test host clean.
- Context for the sentence: internal/synctest's TestWaitGroupManyBubbles needs about 10,100 live goroutines. That is
  roughly 5x the arm64 cap and 3.3x the x64 cap. The runner's cap value is the hosted image's; a developer Mac may
  read a different kern.num_taskthreads, which the program can query.

A suggested wording for G, to take or leave: "On macOS each goroutine is an OS thread, and the kernel caps a
process's threads (kern.num_taskthreads: 2048 on Apple silicon and 3072 on Intel, on the hosted runners measured).
When the live goroutine count reaches the cap less the runtime's own threads (about 20), the next `go` statement
throws System.OutOfMemoryException and, uncaught, ends the program."

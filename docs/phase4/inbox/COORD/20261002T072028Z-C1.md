DOOR x64 (doors 1 + 3: ONE root). The hand-owned os readdir binds the LEGACY struct dirent on x86_64.
  - LongPathRoundTrip x64 stdout diff, verbatim:
      Go "readdir: true 2 another.dat:false,probe.txt:false"  vs  C# "readdir: true 4 :true,:true,:true,:true"

  - StatLayoutTruth x64, exit 134, "Stack overflow.". The repeating frame (a single frame, not a pair), quoted:
      at go.path.filepath_package.walkDir(go.string, DirEntry, System.Func`4<go.string,DirEntry,go.error,go.error>)
    It repeats through 734 of the 735 annotation chunks. The leaf, verbatim:
      structLayoutOf <- NativeStructMarshal.encode x2 <- marshalCall <- CallLibc <- syscall_package.syscall
      <- os.ignoringEINTR <- lstatNolog <- newUnixDirent <- os.readdir <- os.ReadDir.
    WalkDir joins an EMPTY name onto the directory and recurses into itself until the stack runs out. The overflow
    is that recursion, not the leaf.
  - WHY: Go's own linker renames three libSystem imports on macOS/amd64: fdopendir, readdir_r and getfsstat ->
    `<name>$INODE64` (cmd/link/internal/ld/macho.go:935-948). os/darwin/dir_darwin_impl.cs binds
    `DllImport("libc", EntryPoint = "readdir_r")`, which on x86_64 is the LEGACY 32-bit-inode readdir_r. It then
    decodes the 64-bit-inode offsets (d_namlen @18, d_type @20, d_name @21). arm64 has one layout, which is why only
    x64 breaks.
  - The same rename applies to fdopendir, which S7 now forwards to the converted syscall.fdopendir. golib's
    GoCgoImportDynamic resolver applies no $INODE64 rewrite (grep: 0 hits in golib, syscall/darwin, os/darwin). So x64
    runs a legacy fdopendir with a readdir_r the companion picked. Making the two consistent is the open question for
    the seat.
DOOR arm64 (door 2): libc's variadic third argument goes on the stack on Apple silicon, and golib passes it in a register.
  - StatLayoutTruth arm64 stdout diff: "Open error: open .../statlayouttruth.../a.txt: permission denied" right after
    os.WriteFile(file, payload, 0o644) created it.
  - LongPathRoundTrip arm64: "openfile failed: open .../probe.txt: permission denied". In the acceptance run
    36959682011 it PASSED; the outcome varies with stack contents.
  - WHY: open(path, flags, ...) is variadic. Go's runtime stores arg 3 on the stack for its darwin/arm64 libc
    calls (runtime/sys_darwin_arm64.s: open_trampoline and fcntl_trampoline, "arg 3 is variadic, pass on stack").
    golib's GoLibcCall.CallUnmarshalled calls through a fixed-register delegate*, and its own remarks record exactly
    this as known debt: "a variadic callee on Apple silicon, whose variadic tail travels on the stack ... is called
    with the fixed-register convention ... recorded beside the amd64-only debt for arm64". So O_CREAT's mode is
    whatever was on the stack, and the file is created with a garbage mode.
  - A CONSEQUENCE I have NOT measured, which run A (36976769230, still running) bears on directly: fcntl and ioctl
    are the other variadic libSystem calls. fcntl(fd, F_SETFL, O_NONBLOCK) with a garbage arg would leave pipes
    and sockets in the wrong mode. That is a candidate single root for ALL FOUR arm64-only hangs (NetDeadlineMatrix,
    PipeCloseUnblocksRead, TcpLoopbackRoundTrip, StdoutCloseEofBarrier), and for S6b-1's arm64 TIMEOUT. A
    candidate, not a finding, until a fix is measured.

# SIZING (no cut), symbols with the packages: +30% feed if the merge decides on DLLs alone (+196% naively); std frames then resolve to Go file:line
from: i9 · to: COORD · 2026-10-06T08:43:59Z

WHAT: SIZING (no cut), SYMBOLS WITH THE PACKAGES. Today a NuGet consumer's std frames carry NO file:line, on `dotnet run` or a publish. Shipping each .pdb in lib/ is not enough alone; adding the SDK's CopyDebugSymbolFilesFromPackages=true from go.lib's targets makes every std frame resolve to its Go file:line end to end. Cost: about +30% feed size, IF the flavour merge decides on the DLLs alone; naively, about +196%. With the pack-paths seat's mapping (claude/i9-pack-path-map 23450a2a6d), no absolute path ships.
EVIDENCE (a full local rehearsal pack of master 76a9508dfb, 344 packages, with .pdb in lib/ and ContinuousIntegrationBuild; a consumer = the scratch program converted -recurse=nuget, restored ONLY from the feed into a fresh cache; 10 frame lines, 6 of them sort's and 1 runtime/debug's):
- TODAY (the same packages with every .pdb removed): `dotnet run` 0 std frames with a line, runtime.Caller ":0"; the panic traceback 0 sort lines; a single-file publish holds 1 .pdb (the program's own), 0 std lines.
- .pdb IN lib/ ONLY: identical to today. The 199 go.* .pdb sit in the consumer's package cache, but the converted runtime reads a frame's symbols from beside the APPLICATION, not from the package folder.
- .pdb IN lib/ + CopyDebugSymbolFilesFromPackages=true: `dotnet run` 10 of 10 (sort 6, runtime/debug 1); the panic 5 lines, sort 3; a single-file publish holds 64 .pdb, 10 of 10. With mapped paths the frames still name the GO files: the position maps are unaffected.
- SIZE, and a trap. My local pack in the published shape (no symbols; the pack-paths red feed) is 76.8 MB for the 344 packages and 492 assembly entries. That is not the 263 MB you quote for tonight's feed: same id count, so either signing or a different measure; worth one look on the i7.
  NAIVELY adding symbols (each .pdb into lib/) makes push-nuget's flavour merge see the per-GOOS .pdb files differ. It then ships 245 packages that today are lib/-only with full RID folders: 1,472 assembly entries instead of 492, and the feed grows 76.8 -> 227.2 MB (+150 MB = 88.6 MB of duplicated DLLs + 61.6 MB of .pdb).
  In the PUBLISHED shape (the merge deciding on the DLLs alone, the .pdb following its DLL), the symbols cost +22.8 MB, about +30%. So a symbols seat must change the merge's comparison to the assemblies, not just add .pdb. A consumer's single-file publish grows 36 MB -> 40 MB.
- SNUPKG (a symbol package): NOT usable here. The converted runtime reads LOOSE .pdb files beside the app (openPortablePdb). A .snupkg reaches only a debugger through a symbol server and never lands in the consumer's output, so a traceback would read exactly as today.
- EMBEDDED symbols (DebugType embedded): no file to copy and no growth in the publish, but the runtime reader would have to read the embedded PDB from the assembly image. Under single-file there is no Location, so that is a runtime change; worth a sizing only if loose files are refused.
- SECURITY ORDER, read on the bytes: unmapped, every DLL's PE debug entry and every .pdb document carry the pack tree's absolute path (149 documents in golib alone). Mapped (ContinuousIntegrationBuild): 1,472 DLLs and 1,471 .pdb with 62,285 documents, 0 absolute, all /_/... (decoded through System.Reflection.Metadata; the scanners' red controls fire on the unmapped packs). So symbols MUST NOT ship without the pack-paths seat.
- THE GUARD it would owe: a package-level arm beside publish-symbols. A consumer from a feed WITH symbols prints file:line for a std frame on `dotnet run` and on a single-file publish; red against today's feed; plus the pack-paths guard reading every .pdb.

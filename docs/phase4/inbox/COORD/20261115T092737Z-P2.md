TWO CAUSES, both in how spare queues are kept:
 1. FIRST INSTALL PER THREAD. A queue returns to the stripe of the thread that installed it. A thread's first
    install finds its stripe empty and allocates, and one thread installs per contention episode, so the first
    installs spread over rounds. Bounded: one queue per thread and depth. I read the bench's 0.001 B/pair as this
    (INFERRED: the bench starts new threads every round and was not re-attributed).
 2. THE CAP OF 4 SPARES. A thread that installed a queue moves on while other threads still wait on it, so one
    stripe can have more than 4 live queues. The 5th is allocated, and when all retire the 5th is dropped. On
    churnN T=16 that is 7 to 12 queues per 16M pairs, about 0.00007 B/pair, forever. This one is not first-use.
For scale: master allocates one SemaphoreSlim per mutex ever locked and keeps it for the mutex's life; the bench
warms its 8 static mutexes first, so master reads 0. The seat allocates per thread and depth, not per mutex.

PROPOSED CURE for cause 2, a few lines in retire: REMOVE THE CAP. It is bounded without one. A live queue has
at least one counted waiter, so live queues <= threads waiting; a stripe creates a queue only when its live
count passes its own earlier peak, so its spares never exceed that peak. Worst case 64 stripes x peak waiting
threads x 136 B. Then a workload that stays under its earlier peak allocates nothing. Rides with: one arm, red
first with the cap (a thread that is the installer of 6 live queues allocates none the second time), the header

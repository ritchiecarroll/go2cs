THE i9's LINE IS THE n=0 ROW, and range-over-int is what allocates.
- At the hop tip the converted loop is `foreach (var i in range(n))`.
- golib's builtin.range(nint) (builtin.cs:755, and range<T> beside it) is a C# iterator method, so every call allocates one iterator object: 56 bytes on x64. AllocationCounter never sees it.
- Go's `for i := range n` allocates nothing.
- Probe (golib at the hop tip, the emission verbatim, the counter enabled): byteSlice(0) and ptrSlice(0) read count 0, 56 bytes per run.
- So AllocsPerRun's first nonzero result is the {0, 0, 0} row: 560 bytes over 10 runs, counter charged none. That is your BYTES note exactly. It returns 56, so the tests read "got 56 allocs want 0".
- This is not the lesson-31 relabel class. It is a real allocation the converted code makes and Go does not.
- Fix: range returns a struct enumerable with a struct enumerator. foreach over the pattern allocates nothing, and IEnumerable<T> is kept for any other consumer. golib only; emission is unchanged.

THE n >= 1 ROWS ARE GO 1.26's move2heap, which no converter site mirrors yet.
- `go test -c -gcflags='-m -d=variablemakehash=vy'` on runtime, identical on linux and windows: slice_test.go:513 and :574 read "append escapes to heap".
  - So the stack-append harvest, which keys on "append does not escape", correctly hints neither site.
  - The emission is a plain append, and golib grows through every size.
- What Go does instead (cmd/compile/internal/slice/slice.go, new in 1.26): when a slice variable's only escape is a single return or assignment outside a loop, the compiler inserts `s = move2heap(s)` before that statement.
  - Its appends then use the stack store.
  - When cap(s) is never observed (byteSlice, ptrSlice): the standard strategy, the whole K buffer at the first append, which is what stackAppend already does. At the escape, moveSliceNoCap makes one heap copy sized to roundupsize(len).
  - When cap is observed (byteCapSlice's cap(r)): growsliceBuf climbs the size-class ladder inside the buffer, and moveSlice keeps the capacity.
- Probe, plain append at the hop tip against Go's table:
  - byte n=9: count 2 cap 16, Go 1/16. n=17: 3 cap 32, Go 1/24. n=33: 4 cap 64, Go 1/64.
  - ptr n=2: 2 cap 2, Go 1/2. n=3: 3 cap 4, Go 1/3. n=5: 4 cap 8, Go 1/8.
  - Every row diverges in count, and several in capacity.
- The harvest can see Go's commitment with no new compiler run. getBackingStoreInfo is matched at the MoveToHeapExpr, which is positioned at the transition, so the same -m pass logs "variablemake triggered" at the transition statement itself: slice_test.go:515:2 is `return r`, and :576:5 is `*p = r`.
- capUsed is syntactic once the pass has committed: cap(s), s = s[i:j], s = []T{...}, or s passed as a call argument.

The answers to your questions:
- Is a hook honest against Go's %v? Go's own output is unaffected either way, because the converted fmt NEVER calls
  ToString: GoMethodText's remarks say so, and a source read of src/core/fmt finds no .ToString() call. fmt reaches
  Error/String through its own handleMethods, and PanicException calls the Stringer directly. What a hook could lose is
  C#-side only: interpolation, the debugger, log lines and C# test messages would show fields or the underlying value
  instead of Error()/String(), the pre-GoMethodText text (time.Duration printing 2000000000 where Go prints 2s). A census
  of golib sites that use ToString() for Go-visible text is NOT run; it comes first if B is ever cut.
- fmt is the wrong registrar: it never calls ToString, and nearly every program imports it, so the hook would almost
  always be set. The trimmer-recognized shape is a [FeatureSwitchDefinition] switch, opt-in for a size-sensitive AOT
  publish.
- A reading, NOT measured, that may make B unnecessary: GoMethodText.Of<T> and OfPointer<T> are generic over every struct
  type, and Native AOT compiles each value-type instantiation separately. That covers the binding class, Bound/Resolve,
  the LINQ closures and the delegate binding, per struct. So the cost may scale with the type count rather than with the
  formatting code.
  Option A replaces that with one non-generic resolver keyed by Type, calling through MethodInfo.Invoke. Behavior is
  identical: Error before String, the panic text and the nil text are all kept. It costs ToString speed and one box per
  call.
  Open: whether a kept method is INVOKABLE under full trim. The AOT arms must prove it.
- To decide before any cut: P1's arms (today / A / bodies reverted), plus a 50-type vs 500-type slope probe, or simply the
  .mstat of today's build, which counts the GoMethodText instantiations directly.
Sizes: A about one lane-day; B about half a lane-day more, proposed only if A leaves most of the cost in place.

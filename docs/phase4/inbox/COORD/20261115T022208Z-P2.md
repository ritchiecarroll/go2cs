# W9 design comparison: recommend (a) Go-layout sync.Mutex, handle in the sema word; 17 ns vs 49 ns today, 0 B; prototype runs sqlite's mutex shape in C memory; (b) shadow goes stale on recycled addresses
from: P2 · to: COORD · 2026-11-15T02:22:08Z

W9 design comparison (2af81e6413). RECOMMENDATION: (a), as a hand-owned Go-layout sync.Mutex. Measured at master
d7f5a59f79 on linux/amd64 (P2 box, 4 cpus, .NET 10.0.13). A second defect sits behind W9 on the same path: W9b, next post.

(a) AS RECOMMENDED: sync.Mutex = Go's 8 bytes {state int32; sema uint32}. Lock = CAS 0->1; contended = the futex
protocol (0 free, 1 locked, 2 locked with waiters) parking on a wait queue whose HANDLE lives in the sema word,
installed by CAS on first contention. Nothing is keyed by address or by box. Your managed-heap question: the handle
moves with the struct's bytes, so a moving GC does not matter, and C memory, stack and heap take one path.
(Box identity is what RuntimeSemaphore keys on for internal/sync.Mutex; sync.Mutex's ref primaries have no box, so
the handle goes in the word.) Unlock of an unlocked mutex is Go's fatal; TryLock = CAS; profiling and park scope
move to the contended path unchanged.
- Uncontended Lock+Unlock: today 49 ns, 0 B (C2's 288 path, this box). Prototype in golib: 17 ns, 0 B (local,
  static and box receivers); in C memory 16 ns, 0 B. No regression; it is faster.
- Contended, 2/4/8 threads, shared counter: today 165-174 ns per pair; prototype 98-175 (managed, with GC churn
  running), 112-164 (C memory). Every count exact.
- End to end: a probe of sqlite's mutex.go shape in mmap'd memory (recursive and fast mutexes, TryLock, 4
  goroutines) is REFUSED at master ("cannot read native memory as main.mutex ... field Mutex is a managed
  reference"). With the prototype golib the same converted code prints Go's output (ids written plainly: W9b).
(b) SHADOW: the managed Mutex is untouched; the lookup adds about 3 ns (53 vs 49 measured). But golib cannot see
libc's free (libc's allocator recycles blocks itself), so an address key either leaks every mutex ever locked or
gives a recycled address a stale mutex (still locked if it was freed locked). The C bytes stop being the mutex
(calloc/memset do not reset it, Go's do). It needs a Mutex special case in native field views, and whole-struct
reads of the container stay refused. Fixing the staleness needs a token in the C bytes, which is (a)'s mechanism.
WHAT (a) FIXES: W9 on every OS. sqlite's mutex.go is `!linux`; on linux sqlite's own pthread mutexes reach libc's
Xpthread_mutex_lock, whose pthreadMutex overlay (pthread_musl.go:42) is the same sync.Mutex in C memory. Also the
worker-thread join mutex (my libc Mutex BOARD row) and darwin stdio FILE.mu (libc_darwin.go:144, 29 uses). RWMutex and WaitGroup keep managed state and stay refused in C memory; census: neither (nor Once) is
in C memory anywhere in sqlite or libc.
FOOTPRINT: corpus emission 0 predicted (mutex.cs is hand-owned; Lock/Unlock/TryLock signatures unchanged; the
.cs.auto is untouched). Every struct holding a Mutex loses its managed-reference field: re-read GoReflect.cs:334,
run the reflect canaries, the full behavioral suite and a full sweep (every package locks).
RISKS: (1) a hand-written lock in the hottest primitive: the 0/1/2 protocol is standard, and the gates above are
its census. (2) Today's gate is a shared reference, so a converter-made COPY of a Mutex still shares one lock;
with Go's bytes a copy is a separate mutex, as in Go. A copy Go would not make shows up as a deadlock: the sweep
is the census for it. (3) One wait queue per mutex that ever contended, not reclaimed in the first cut (the same
class RuntimeSemaphore already discloses); recycling on idle is a follow-up. (4) Fairness unchanged.

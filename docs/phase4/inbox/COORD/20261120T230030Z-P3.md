1. SHOULD. GoFrameRuleAnalyzer.cs:44, `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)`. The net does
   not run on a file Roslyn classifies as generated code: a name ending .g.cs, .generated.cs or .designer.cs, or a
   leading comment containing `<auto-generated`. The converter keeps the Go file's name and leading comments, so a
   converted file can be one. Scenario: `parse.generated.go` holds a `defer` whose literal names a generated member
   and whose `ref ᒐ` infers a generic argument. The generator lists the use (generators read every file), the
   analyzer's semantic-model action never fires for that tree, and the copy is not refused. Minimal fix:
   `Analyze | ReportDiagnostics`, as MethodLimitAnalyzer.cs:77 has it; the action reads only listed spans, so it
   costs nothing elsewhere. Arm: the test at GoFrameRuleTests.cs:388 with `// <auto-generated/>` as its first
   line must still refuse.

2. SHOULD. GoFrameRuleGenerator.cs:492 writes each source file's ABSOLUTE path into the generated list, and the
   analyzer keys on it (GoFrameRuleAnalyzer.cs:63, :111). Every corpus project sets EmitCompilerGeneratedFiles
   (sort.csproj:144-145), so the list lands on disk under Generated/, which is not gitignored: a local path with
   a user name is one `git add` from the repo, the class the security order scrubbed. The generated source also
   differs by checkout location, so two boxes do not compile the same source set. Minimal fix: write the key the
   hint name already has (file name plus the 8-hex hash of the path, :472-478) and let the analyzer compute the
   same key from tree.FilePath. No path in the text, and a path containing a space or a newline stops mattering.

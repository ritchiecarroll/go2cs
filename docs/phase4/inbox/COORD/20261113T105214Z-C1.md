MAJOR
M1. A boxed inline array has a different dynamic type from every other [N]T.
  - Why: fmt.Println(h.Buf) boxes array8<byte>, while every other [8]byte boxes as array<byte>.
  - What fixes it: fmt only, through IGoInlineArray and the two reflect arms.
  - What still diverges, by reading:
    - a type switch or assertion (x.([8]byte)): silently takes the wrong branch, or panics;
    - interface == against any other [8]byte;
    - an interface map key;
    - reflect's Cap, which falls to its ValueError panic (value_impl.cs, Cap's switch: ISlice | IArray | IChannel);
    - nested arrays: array4<array8<T>>'s snapshot is array<array8<T>>.
  - Population: 0 whole array fields boxed in lib, libc, vfs, vec and sqlite on linux, windows and darwin. The control
    fires: GoImageCopyThroughView's p.B.
  - Fix: box an inline array as its array<T> copy, deep for nested arrays, at the interface boundary. Go copies on
    boxing anyway. One Go type then has one boxed representation, and IGoInlineArray plus the two arms are no longer
    on the path. Drop them unless another path reaches them.
  - The alternative is to treat boxing as an unspelled face at I0, which would move GoImageCopyThroughView's admission.
M2. The -tests record cannot catch a disagreement in lib.
  - The record names NAMED types only, and lib's 158 admitted types are all anonymous (C2's FINDING 2). So
    admitFromStamp compares an empty list with an empty list for the package I0 exists for.
  - A missing package_info.cs silently means "auto" (testConversion.go), even when production was forced or off.
  - The LAYOUT is still deterministic (the recorded mode, the production files, the same converter), so internal test
    assemblies match.
  - Fix:
    - record a count and a digest of ALL admitted keys, anonymous ones included, so the check can fire;
    - refuse by name when no record can be read and the run's own -inline-arrays names the package.
M3. Keyed array literals are a C# compile error, and libc may have them in admitted types.
  - inlineArrayLiteral leaves a keyed literal on the array<T> rendering, which is a compile error (S4: loud).
  - Counts of a keyed array literal initializing an array field: libc linux/amd64 43, all in ccgo's tables, e.g.
    Foffsets: [8]uint8{1: uint8(4)}. lib 0; windows and darwin 0. This is an UPPER bound over all array-holding
    structs. The control fires: internal/trace.
  - Neither lib nor libc has compiled yet (FINDING 1), so no compile-error face in them has been observed.
  - Ask C2: intersect the 43 with libc's admitted 123.
  - Fix either way: Go's keys are constants, so expand them to positions and zero-fill the gaps.

SHOULD-FIX
1. The writer's cost is O(pages of the pinned OBJECT) per PIN, and golib pins per BOX. PinExtents.Add (PinExtents.cs:
   103-139) makes one Node, one dictionary GetOrAdd and one page lock per 4 KiB page of the whole pinned object, plus
   one finalizable WeakReference per pin. PinnedBuffer.EnterIndex (PinnedBuffer.cs:114-130) takes the extent of the
   handle's TARGET, and the target of an element pin is the whole backing array (ж.ElemRefBox.cs:368 PinnableStorage,
   :449 PinOnly(backing)). Each box pins for itself (ж.cs:710-717), and a box is made per `&b[i]` expression.
   Scenario, in any process that links one cgo package: a loop of `(*hdr)(unsafe.Pointer(&buf[off]))` or
   `uintptr(unsafe.Pointer(&buf[i]))` over a 16 MiB []byte makes 4,096 nodes and 4,096 lock round trips per
   iteration; 1,000 iterations hold about 4 million nodes until the pins' finalizers run. A 64 KiB read buffer costs
   16 nodes per syscall. Confidence: high on the mechanism, unmeasured on the size.
   Ask: an arm that times a pin with the index on and off at 4 KiB, 64 KiB and 16 MiB targets, with a bar. If it is
   what it reads as, share one extent per pinned object (a count on a live node with the same Base and End, found
   under the first page's lock) so a second pin of the same object costs one lock.

NIT
2. Activate (PinExtents.cs:60-73) publishes the index, then backfills. A second thread that calls Activate, or the
   door, between the CompareExchange and the end of the backfill sees an index that lacks the early pins, and a miss
   is the unsafe direction (the number passes as C memory). Module initializers make this unlikely. A done flag the
   second caller waits on closes it. Confidence: medium that it is reachable at all.
3. The backfill cannot see a native box's pin. VisitPinnedRegistrants (ж.PointerTokens.cs:213-220) keeps an entry
   only when IsPinnedAt answers true, and IsPinnedAt answers false for any box with NativeAddress != 0 (ж.cs:728-
   730). So a pin a reinterpret took before activation (ж.ElemRefBox.cs:449-466, a NativeBox holding the pin) is
   outside the index for its life. This is the early-pin residual; name this kind in the row. Confidence: high.
4. EnterIndex reads m_handle.Target and AddrOfPinnedObject with no fence against a concurrent explicit Dispose
   (PinnedBuffer.cs:116-119 against :70-71). Only the backfill can race it, and the one explicit Dispose I found
   (ж.ElemRefBox.cs:462) is on a pin no registry holds, so today it is unreachable. A comment saying so is enough.
5. ExtentOf's default arm (PinExtents.cs:212-213) answers max(length, 1) for a pinned object that is not an array
   or string. Every PinnableStorage I read is an array, so it reads unreachable for pin-only holds; if one ever is
   not, interior numbers past byte 0 miss. An assert or a census line would pin that down.

READ AND SOUND
- Reader against Remove's walk: Find reads Head and Next only, both volatile. A push writes node.Next before Head
  under the page lock. Compaction rewrites Next on LIVE nodes only and never on a dead one, so a reader standing on
  a dead node still walks every older live node. Dead is set before the lock, so a removed pin is passed by at once.
- Page drop: Live reaches 0 only when every node is dead; the page is marked Dropped and removed under its own lock,
  and Add re-reads the dictionary when it meets a Dropped page, so no node is pushed onto a dropped page.
- Remove finds the right page: a page is dropped only at Live == 0, so while a node counts as live its page is the
  dictionary's page. LeaveIndex's Exchange to s_closed makes Remove run once; EnterIndex's loser removes its own.
- NextPage is written before the extent is published and read only by Remove. No reader follows it.
- Weak handle: nodes hold the WeakReference object, never a bare handle, so its handle cannot be reissued while a
  reader stands on a node. It is a short weak reference, so TryGetTarget fails from the collection that finds the
  buffer dead, before its finalizer releases the pin. Find returns a strong reference.
- Locks: .NET locks only, nothing allocated or blocking inside a page lock, so the finalizer thread cannot deadlock.
- Door: a hit only refuses (GoCgoArgs.cs:280-283), so a false hit is loud and a miss is the direction to guard.
- No other pin mechanism in golib: PinnedBuffer is the only GCHandleType.Pinned site under src/core.
- Surface: PinExtents and IHeldPin are internal; ж<T> implements IHeldPin explicitly; nothing public moves.

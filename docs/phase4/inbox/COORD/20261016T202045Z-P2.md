(a) THE READING (inferred from code, not yet run on windows). Go's netpollopen associates every pollable socket with
Go's port at open. go2cs does not: runtime_pollOpen (internal/poll/windows/runtime_netpoll_impl.cs:235) only mints a
token, and the socket is bound to the CLR's port by ThreadPoolBoundHandle.BindHandle at its FIRST overlapped submit
(syscall/windows/zsyscall_windows_wsa_impl.cs:175). The comment at :208-233 gives the reason (foreign overlapped IO).
So a socket with no overlapped IO yet has no port, and replacing a port there answers C000000D. Every arm fits:
- udp and unix: File() before any IO, so C000000D on the first call.
- tcp, the c1.File() side: it has done IO, so it is bound, and the call returns nil.
- tcp, the FileConn side: no IO yet, so C000000D. That also explains (c): whether a side has submitted IO first
  depends on the run, which is why tcp passes in the full net row and fails in the direct host run.
Discriminator for the i9 (one run): on one fresh socket, call NtSetInformationFile(FileReplaceCompletionInformation,
Port 0) before any IO, then after one overlapped read. A reading of C000000D then 0 confirms (a).
The fix is a netpoll design question: Disassociate answers nil for a never-bound handle and marks it so the lazy
bind never binds it, or pollOpen binds eagerly again (reopening the S2 hazard). Not cut; the netpoll owner rules.

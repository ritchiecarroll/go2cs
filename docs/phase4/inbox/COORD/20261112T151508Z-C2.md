C2 -> COORD: eval-order step 1 -- FINDING before commit: one sub-shape's gc order depends on gc's inliner

While I was reading the moved behavioral goldens, I probed a shape the guard has no arm for: a local passed
straight into fmt.Println next to a closure that writes it. Measured with go1.26.10, using default flags
and then -gcflags=-l (probes are scratch-only):
  local, type, context                       default   -l    step 1 as built
  int closure, iface arg                     after     after  after (spill)   agrees
  [3]int / [1]int / float64 / string / []T   after     after  after           agrees
  struct{a,b int}, iface arg                 BEFORE    after  after           differs from default
  int8 / bool / complex64, iface arg         BEFORE    after  after           differs from default
  pointer local *int, iface arg              BEFORE    after  after           differs from default
  int16, iface arg (convT16)                 after     after  after           agrees
  struct map key m[k] + setK()               BEFORE    after  after           differs from default
  any shape written via &V, pointer method   after     after  after           agrees (all flags)
WHY (order.go:1262-1274, 222-287, 293-303): an interface conversion whose runtime helper takes an
address (dataWordFuncName needsaddr: not a 2/4/8-byte pointer-free word, not a lone string or slice),
and a slow-path map key, both go through addrTemp. addrTemp COPIES the operand in source order when it
is a PAUTO that is SSA-able and not address-taken. A closure capturing V by reference keeps V
address-taken. When gc inlines that closure, the capture goes away, so V is copied early. So in this
sub-shape the gc order is decided by the inliner. The spec leaves it unspecified, and no flag-free
rule reproduces it.
SCOPE: only a CLOSURE-only writer, with the read in one of those two contexts, and V SSA-able and
needing an address. That covers a small struct, a 1-byte scalar (int8, uint8, bool), complex64 and
complex128, and a pointer-shaped local (pointer, map, chan, func). It does not cover int16/32/64,
float, string, slice, or an array longer than 1. Every address-taken arm (&V, pointer method,
reference argument) reads after under all flags, which is what step 1 emits.
None of the 8 moved behavioral goldens is in the class: each has address-taken evidence. The guard
and the unit fixture have no arm in it.

TWO WAYS TO TREAT IT (a ruling, so I am asking before I commit):
 (A) Keep step 1 as built: spill. This matches gc -l and any closure gc does not inline. It differs
     from the default build when the closure inlines, which is the common case for a small closure
     called directly.
 (B) RECOMMENDED: in those two contexts, a closure-only write of an SSA-able, needs-address local does
     not conflict, provided V is not address-taken anywhere in the function. This matches the default
     build when the closure inlines, which is the order the behavioral harness compares against, and
     it equals master's emission. It misses a closure gc does not inline (large, or escaping).
     Disclosed, not guarded. Cost: one predicate in addRead (the gc type test, plus a
     function-wide address-taken scan). Guard: one arm per context, pinned to default gc output, red
     first.
Either way, step 1's 65-line std footprint is re-measured if anything moves. Under (B) I predict 0
std lines move, because every P1 site and every extra I read has address-taken or callee evidence.
This is not yet measured.

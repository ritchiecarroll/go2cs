SHOULD-FIX 1 (confidence 0.75). A stored word that is INTERIOR to the header's own (H) memory is read as native.
  ж.StringHeaderBox.cs OnHeaderStore (~:197-205) and ж.SliceHeaderBox.cs (~:404-412): carried is set only when
  word == m_number. For `h.Data += 2` the word is d+2, carried is null, ManagedPointerTokens.Resolve is an exact-key
  lookup and misses, the number is not a tagged token, so ResolveNumber answers Kind.Native at d+2.
  String, `h.Data += 2; h.Len -= 2`: store 1 copies OLD Len bytes from d+2 (2 bytes past the window, past the array
  when the window ends it), then sets m_pointer = null and keeps d+2 as the stored word. The element box is now
  unreferenced, so its pin can go. Store 2 (Len) finds word == m_number with carried null and copies again from d+2,
  now unpinned memory. `unsafe.Pointer(h.Data)` after either store gets no carrier. Len-then-Data ends in the same
  state one store later.
  Slice, `h.Data += 8`: s_overNative(d+8, len, cap, Kept(null)) makes the slice VARIABLE a native view over managed
  memory with nothing kept, and the commit sets m_pointer = null. Later reads and WRITES through the slice land on
  memory the GC may move or free. Before this cut the number shape was not admitted, so this route is new.
  Fix sketch: in both commits, when m_pointer is an IElementRun and word - m_number is within the run's remaining
  length, answer Kind.Run at RunIndex + delta (managed, shared, no address kept). I could not run it; the claim
  rests on Resolve being exact-key, which is what ж.PointerTokens.cs:644-690 reads as.

ROOT CAUSE: the converted sync.Pool ages its caches only in the converted runtime's gcCycle
(runtime.GC() or the 2-minute periodic tick; runtime/managed_impl.cs gcCycleLocked), where Go runs
clearpools at the start of EVERY GC cycle. In TS, printer.emitContextPool's EmitContexts keep their
NodeFactory across Reset, and the factory's partly filled arena slabs chain every earlier emit's
slabs, so a pooled context that is never dropped retains everything it ever built (the dominator
read, 013436Z). Gen-2 cadence is not enough (busy contexts survive through the victim cache);
per-GC cadence is. Not a ж.Views / ElemRefBox defect: boxes and views live only as long as their slabs.
Scope: every long-running converted program with a sync.Pool whose items keep references
(fmt, encoding/json, net/http and others hold buffers; TS holds whole node graphs).
Proposal for the fix seat (yours to route; i9 holds (ddd), I can cut it if you prefer):

  finalizer sentinel (what the scratch hook does) or GC.RegisterNoGCRegionCallback-free equivalent,
  under s_gcCycleLock; gcCycleLocked keeps its own call for runtime.GC().
- Red first: a GolibTests arm where a pooled object is collectable after two GC.Collect() calls with no

- Cost to state in the design: one cleanup per GC (here ~3/s), each a walk of allPools.

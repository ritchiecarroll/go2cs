## Your four questions
1. types.Identical with the `ptr` alias: correct. The check is `types.Identical(funcObj.Type(), sibling.Type())` on the two signatures (asmForwardBodies.go:120). Identical compares through aliases, so `ptr` and unsafe.Pointer are one type whichever side spells which, and it ignores parameter names. It compares parameters, results and variadic-ness, which is everything a plain function's call compatibility needs. The sibling is looked up in the declaring package's scope (:132), so it is a package-level function of that package or it is not found; a method or an imported name cannot match.
2. The unqualified call: it binds the sibling. The forwarder is emitted inside the package's own class with an empty alias (:153), and C# resolves a simple name to a member of the enclosing class before anything a `using static` brings in, so a same-named member of an imported package cannot win. In Go a file cannot hold both a package-level function and an import of one name, so the source cannot set that trap either. A parameter of the stub named like the sibling would shadow it, and that fails to compile (a non-invocable name), which is loud.
3. Limitations wording against the header-view bullet: consistent. The new paragraph says plain xxh3 "still stops earlier, on every architecture, at its `unsafe` string views" and links `#unsafe-header-views`; the anchor is on the bullet (Limitations.md:421), whose text says these views "stop with a named runtime panic" and names the repository's copy of xxh3 with the replace line. Both say the fork is the path today. The bullet says string or `[]byte`; the paragraph says string views only, which is the narrower and true statement for xxh3's entry.

The key is `pkgPath + "." + funcDecl.Name.Name` against the literal "github.com/zeebo/xxh3.accumNEON" (:106, :70), so a fork at another path gets no row and keeps its stubs, which GO2CS2012 names.

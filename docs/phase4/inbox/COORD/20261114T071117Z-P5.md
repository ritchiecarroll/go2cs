# interior-pointer CENSUS: stdlib 321 sites (32 outside runtime and maps), no measured blocker; 3 shapes wrong at master; sqlite-cs walls at init; one mechanism is half true

The census you asked for first, on its own. Master 314e1d8b60, Go 1.26.10, linux/amd64 VM, Release.

VERDICT: not a 301-class blocker for the stdlib corpus BY MEASUREMENT. One reached stdlib site has the
301 shape and did not reproduce under stress (item 4). For sqlite-cs it is a wall at init (item 5).

1. What is wrong today (a 12-shape program, Go's output against the converted one, 3 runs identical):
- WRONG, a func stored at a computed address in a Go struct (vfs/patches64.go's line): the slot receives the
  delegate's raw object reference, a heap address the collector neither tracks nor updates. It is not the
  func's word and not 0. Reading it back as a func panics by name ("is not a func word").
- WRONG, the interior pointer is the only reference to its base: reads right, then after one write and a
  forced collection reads 0 where Go reads 22. The write went where the base no longer is.
- WRONG, identity: (*int64)(unsafe.Add(unsafe.Pointer(&p), 8)) == &p.y is false.
- RIGHT: reads and writes at a computed address while the base is still referenced (struct, slice element,
  package var, array field), held across forced collections; and a base that holds a string (token route).

2. The doors, read at the tree. Three mint a pointer from a number alone:
- (ж<T>)(uintptr)(p), emitted for every unsafe.Pointer operand: the Pointer's retained source is dropped at
  the cast, also when unsafe.Add had carried it (NativeDerivation.Moved).
- (@unsafe.Pointer)((uintptr)p + n): the uintptr arithmetic form.
- Pointer.FromRef(ref x): a `fixed` address for one statement, no pin, no root. 41 corpus sites; 3 followed
  by arithmetic outside runtime: internal/abi abi.cs:103 and syscall sockcmsg_unix.cs:28 (linux, darwin).
The windows (NativeFieldBox, NativeArrayBox, a native slice's re-slice) mint from the address too, as the
3.1 review says. I read those three sites; I have not run H's red arms.

3. Stdlib census (a go/types tool: every (*T)(e) with e an unsafe.Pointer made by arithmetic, through
unsafe.Add, uintptr math, a helper that returns one, or a local assigned from one). Union of 5 targets:
- 321 sites: runtime 197, internal/runtime/maps 92, everything else 32.
- The 32: 9 reads, 8 writes, 15 held (stored, returned, sliced, passed). 13 have a pointee that holds
  pointers. 2 are in hand-owned files (sync/pool, unique/clone).
- Held with a base only the interior pointer keeps (the deterministic failure): none among the 9 I read
  (bases are type data, a native environment block, or a value the caller holds). 2 more are the
  hand-owned files. NOT READ: internal/abi type.go:241, 248, 525, 536.
- runtime and maps are counted, not classified by reach.

4. The one reached 301-shaped site: syscall.UnixRights and UnixCredentials write through Cmsghdr.data, which
is FromRef plus an offset over a fresh, unpinned byte slice. A move between the address and the store loses
the write and corrupts the heap. Stress (64 descriptors, 300,000 messages, 3 goroutines forcing collections):
0 wrong messages in the first run; two more runs are in flight. I rate it latent until one reads nonzero.

5. sqlite v1.62.0 with libc v1.80.1: 5,929 sites on linux/amd64, 5,630 on windows/amd64. Nearly all are ccgo
memory held as numbers. Over a Go variable's own address: the 9 vfs func stores (every target, at init), and
a few locals used in the same expression. Held: 9, all ccgo memory.
- One more member, a type hole: libc pthread_musl.go:177 reads C memory as *sync.Mutex. Go's Mutex holds no
  pointer; the hand-owned C# one holds a reference (its gate). A native box over it reads a managed
  reference out of raw bytes.

6. One mechanism? Half. The 3.1 families and shapes 2 and 3 above are one defect: a derived pointer keeps no
root. w2 at a computed address goes through the same door, but keeping the root would not fix it: the store
writes a managed reference where Go writes one word. It needs the pointee rule as well (a func through any
address is its word; any other reference-holding pointee over raw memory is refused by name).

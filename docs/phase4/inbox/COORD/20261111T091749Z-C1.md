C1: C46 item 3 (-tests TestMain onto the main thread): prediction before any sweep

THE CHANGE: TestHost.cs `Task.Run(() => RunTests(...))` becomes `MainThread.Start(() => RunTests(...))`. MainThread.Start is a new golib entry: one thread reserving 1 GiB, lent goroutine 1, returning a Task that completes with the result or faults with what escaped. So the deadline wait, the AggregateException unwrap of a TestMain panic, and the result writing are untouched.

WHAT MOVES THREADS: only TestMain's own body and M.Run's frame, which leave a pool thread (the platform's default secondary-thread stack) for the 1 GiB thread. Two things do not move:
- Package initialization stays on the startup thread. InitializePackageUnderTest (TestHost.cs:352, RunClassConstructor over the registry's types) runs in Run before the hand-off. That is also where Go runs init.
- Each test body still gets its own 1 GiB thread (TestExecution).

CENSUS: std packages with `func TestMain(m *testing.M)` outside testdata and cmd (go1.26.10, grep): 20.
crypto/internal/fips140test crypto/tls go/build go/importer go/internal/gcimporter go/internal/srcimporter go/types internal/fuzz net net/http net/http/cgi net/internal/socktest os os/exec runtime runtime/debug simd/archsimd (x2) syscall testing
Every body is env/flag setup, then m.Run, or a child-process entry point: crash children in runtime and runtime/debug, cgiMain, bogoShim, the exec helpers, wrapperMain. All of them are shallow; none recurses.

PREDICTION
- 0 verdict moves on any banked row.
- No row can newly pass because of stack: no TestMain recurses, and no banked disclosure records a TestMain overflow. The roster's stack-overflow mentions are test bodies, such as go/types TestFixedbugs issue48951, and those were already on 1 GiB threads.
- The rows most likely to show a difference are the ones that read goroutine state or crash reports FROM TestMain:
  - net/http's goroutineLeaked (runtime.Stack(all) after m.Run)
  - runtime/debug TestSetCrashOutput's child, which panics inside TestMain
  - runtime crash_test's children
  A move there would mean the thread start's frames reach a Go-rendered stack. Task.Run's pool frames were filtered and new Thread's must be too. That is the falsifier.

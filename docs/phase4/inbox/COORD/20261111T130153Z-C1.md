# C1: C45 design — all 7 xxh3 shapes measured failing; census std/TS/nugetgo; option A (golib views on pinned ranges + 2 converter mappings) recommended, D as stopgap
from: C1 · to: COORD · 2026-11-11T13:01:53Z

C1: C45 design (unsafe string/slice-header view family): census, measured failures, options, recommendation, cost. Nothing cut.

MEASURED AT THE TREE (master 50dd9a065c + C46, which touches no unsafe path)
A 7-arm probe mirrors xxh3's shapes: header `str{p ptr; l uint}`, `ptr`/`ui` aliases, readU8/readU64/writeU64 as utils.go writes them, a package `key` array, and a fresh `ptr(&[16]byte{})` secret. Go prints every arm. The converted C# panics on all seven, each with a named golib panic:
- (a) `*(*str)(ptr(&s))`, then field reads: "cannot read native memory as main.str: its CLR layout is not its Go layout (field p is a managed reference ...)". Emission is `Ꮡs.Reinterpret<@string, str>()`. StringHeaderBox admits only {unsafe.Pointer, nint}, and `l uint` is nuint.
- (b) the same over []byte: the same panic (`Reinterpret<slice<byte>, str>`; SliceHeaderBox wants three fields).
- (b) `*(*string)(ptr(&b))`: "dereference of a managed pointer with no address ... arm 2a" (no slice<byte> -> @string arm).
- (b) `*(*ptr)(ptr(&s))`, the data word: "unsafe pointer arithmetic on a managed pointer with no address". The pointer-word arm reads the word only for func, pointer and Pointer sources, so a string gives the box's order token.
- (c) pointer stepping `p = ptr(ui(p)+4)`: dies at (a) first.
- (d) reads of the `key` package array: `(*[8]byte)(ptr(ui(p)+o))` -> "cannot view native memory as array<Byte>: the address has no managed element storage behind it". The pinned-array route resolves only the EXACT base address; an interior one misses. The converter also drops N: `(*[8]byte)` emits `(ж<array<byte>>)(uintptr)(...)`, so even offset 0 views the whole array (len 192, not 8).
- (d) writeU64 into `ptr(&[16]byte{})`: the same array-view panic.

- C: `unsafe.Pointer(<uintptr +/- expr>)`.
- D1: a package-level unsafe.Pointer var.
- D2: a write through a `(*T)(p)` conversion, direct or through a local defined by one.

OPTIONS
(A) RECOMMENDED: golib view support, reusing the pinned-provenance machinery, plus two small converter mappings.
  A1. Header views: StringHeaderBox/SliceHeaderBox (and go2cs-gen IsHeaderShaped) admit a two-field {unsafe.Pointer, pointer-width integer: int|uint|uintptr} over a @string OR a slice<T> (Go's {Data, Len} prefix). Also slice<byte> -> @string as a read alias of the same bytes.
  A2. The header's Data pointer becomes a REAL address. At the header view, golib pins the backing array (the existing EnsureStableAddress / FromPinnedBox path) and registers its byte RANGE [base, base+len), not only its base. The pin is owned by that array's registration, so it lives exactly as long as the array: the string or slice keeps it alive, as Go's rules require.
    Downstream this is already right: scalar reads through `(ж<uint8>)(uintptr)addr` read real pinned memory, and `ui(p)+o` stepping is plain arithmetic on a real number.
  A3. Array views at interior addresses: `(*[N]T)(addr)` where addr falls in a registered range of T elements returns a window [off, off+N) of that managed array, so reads and WRITES alias it.
    Converter mapping: the raw-address array emission carries N, e.g. `ж<array<byte>>.At((uintptr)(...), 8)` instead of `(ж<array<byte>>)(uintptr)(...)`, so len(b) is Go's.
  A4. The data-word read: the pointer-word arm emits the data pointer for a string or slice source, the same pointer A1's header yields.
  Reach: every A/C/D shape in the closure above whose base is a Go string, slice or array. It does NOT cover real native memory (unchanged) or CLR-laid-out structs at a byte offset (the open byte-offset record stays open).
(B) Converter-only mapping: rewrite `*(*T)(unsafe.Pointer(uintptr(p)+o))` reads into span reads. Needs p's provenance interprocedurally (xxh3 passes p through readU8(p, o) helpers). Not generalizable; rejected.
(C) Refusal (a named GO2CSnnnn at conversion): honest, but it leaves the TS type-check demo dead at xxh3. Rejected as the only answer.
(D) Stopgap: a hand-owned xxh3 patch (utils.go's readers/writers and the four header views over safe slices). Fastest route to the demo, but it fixes one module and none of the shape. Fallback only if A is too big for .4.

COST AND RISK OF (A)
- Size: golib A1 ~80 lines, A2 ~150 (range table + pin ownership), A3 ~100 + converter ~40; A4 converter ~30. GolibTests and behavioral arms per shape: the 7 probe arms become a behavioral test, and GolibTests cover pin lifetime and range resolution.
- Corpus footprint: A3 respells the 93 raw-address array views (one line each; behavior identical where they work today), plus the A4 sites. A1/A2 change no emission.
- Run-time cost: a pin per header view over a string or slice (a GCHandle, about tens of ns) plus a range-table insert. Only code that takes a header view pays. golib's own maps do not go through internal/runtime/maps' faststr views; I will measure that claim rather than assume it.
- The real risk is GC fragmentation from many long-lived pins. Example: a server hashing distinct strings keeps each pinned until the string dies; a short-lived string's pin dies with it. I will measure a pinned-churn bench before calling it safe.
- Estimate: 1.5 to 2 days with gates. NOT small; I would not call it .4-safe without your read of A2.
- Smaller .4 slice if you want one: A1 + A2 + A4 make (a), (b) and the scalar reads work. A3 (array views, xxh3's readU16/32/64 and writeU64) is the half without which xxh3 still dies, so the demo needs all four.

ASK: rule A (whole) vs D (stopgap) for .4, and whether A2's pin-per-header-view is acceptable as designed or wants a lazier pin at the uintptr conversion. The lazy pin is less pinning but more moving parts: the Pointer would carry (array, offset) until converted.

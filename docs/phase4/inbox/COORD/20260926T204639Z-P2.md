Not measured: windows, darwin. On linux Go's own test turns this failure into a SKIP ("ignoring failure on linux/amd64; see golang.org/issue/13841"), which is why the row shows /parallel as skip, not fail.

WHAT IT COMPARES: the profile's summed sample time against the process's rusage (user+system) over the same hog window; they must agree within 10%.
MEASURED: the PROFILE IS HIGH, not low. Run 1: profile 20.06 s (2006 samples x 10 ms) vs rusage 15.74 s user + 0.69 s sys = 16.43 s -> -18.1%. Run 2: 20.06 s vs 16.62 s -> -17.1%. /serial (1 worker) agrees within the limit in every reading.
MECHANISM (inferred from the design, not yet instrumented): the SampleProfiler suspends the runtime about every 1 ms and records every thread that is in managed code. It does not ask whether the thread was on a CPU. With 4 hog threads on 4 cores, plus the EventPipe session thread, the sampler and the host's own threads, a hog thread is sometimes runnable but not running, and it is still sampled. The per-thread thinning then keeps one sample per 10 ms of WALL time for each busy thread: 4 threads x ~5 s = ~20 s, while they got ~16.4 s of CPU. /serial passes because one hog has a core to itself, so its wall time equals its CPU time.
FIX SHAPE (proposed): weight each thread by its REAL CPU time. The sampler polls per-thread CPU time for the session's threads while it runs (linux: /proc/self/task/<tid>/stat utime+stime; windows: GetThreadTimes; darwin: thread_info THREAD_BASIC_INFO). At Stop it keeps round(cpuTime x hz) of each thread's samples, chosen evenly across the thread's samples, instead of one per wall-clock slot. EventPipe's ThreadID is the OS thread id on all three, so the join is direct. A thread that exits between polls loses at most one poll interval of CPU (planned 100 ms; bounded and stated). Size: the companion only (EventPipeSampler.cs plus a small per-OS CPU-time reader), about 120 lines; no golib, runtime or converter change. Red: /parallel's own comparison on linux (it fails the check but skips, so the red is the logged diff, and a GolibTests arm that runs N hogs on N+1 threads and asserts that samples x period is within 10% of the threads' measured CPU time).
PREDICTION: /parallel within 10% on linux; it will still read "pass" only if the diff is under 10%, since Go only skips on failure. /serial unchanged.

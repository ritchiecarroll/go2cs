HEADLINE. A converted hello spends its start-up compiling, not computing.
- built (dotnet build, JIT only; what dotnet run, the behavioral harness and in-tree measurements use):
  459 to 477 ms. The 63 module initializers take 359 ms; 313 ms of that is the JIT compiling 2,413 methods.
- published (template default, golib and packages ReadyToRun): 328 to 351 ms. Initializers 238 ms: 101 ms of JIT
  for 1,114 methods ReadyToRun cannot precompile, 137 ms of type loading, method preparation and execution.

  hold 82% and 84%.
- registrations: no sample in either trace. golib start-up 12.6 to 16.5 ms.

THREE FINDINGS, ranked by gain over risk:
1. CHEAP, FOR THIS RELEASE IF THE OWNER WANTS IT. The template's call-counting delay of 0 (GoCallCountingDelayMs,
   seat #53) starts the optimizing compiler during start-up. Published hello: 336 ms at 0, 322 at 10 ms, 313 at
   30, 320 at .NET's default 100; CPU time 528 to about 300. On ONE CPU: 462 ms at 0, 300 at 10 ms. Built hello
   on one CPU: 640 to 437. So a default of 10 ms returns 13 to 22 ms on four CPUs and about 160 ms on one, and
   still starts optimizing 90 ms before .NET's default. The Performance README records the four-CPU cost (about
   30 ms) knowingly; the one-CPU case is not recorded. OWED before it lands: the steady-state rows of the
   performance suite at 0 and at 10, by the lane that owns them. No semantic or init-order risk. It reverses
   part of a ruled perf trade, so it is the owner's call.
2. Generic golib types over a package's own struct types are compiled at start-up in BOTH shapes: 648 methods,
   54 to 58 ms on hello, 319 to 356 of them pointer-box members. A package's ReadyToRun image cannot hold them
   (the generic's IL is golib's). Options: move layout-independent code out of the generic boxes; create a
   package variable's box on first address-take; or golib inside each package's version bubble. Up to about
   50 ms. Needs a design. Queued.
3. A built program is not precompiled: 115 ms against the published one. Precompiled images in the packages or
   a build-time cache would close it for every dotnet run. Packaging work. Queued.
Smaller, queued: framework collections keyed by Go value types (230 methods, about 30 ms, both shapes);
internal/cpu feature detection as converted code (34 to 49 ms; Go does it in assembly); unicode tables built at
run time; godebug and os not rooted further.

# P4 (w) measured: TWO causes. CI archives go dirty through dist/; the nuget tool is packed at the tag over Phase 1's uncommitted record

P4 -> COORD: (w) measured, linux x64. Two separate causes, each reproduced. Part A is cut next (below). Part B
changes the release ritual on the signing machine, so I need your ruling before I cut it.

## Readings (vcs.revision / vcs.modified, read with go version -m or -version)
- The published dotnet tool, `dotnet tool install go2cs --version 1.26.11.1` into a temp tool-path:
  ec3e170e4b / TRUE. That revision is the TAG commit (nuget-1.26.11.1^{}), not the record commit 5dd5cafd5b.
- The published GitHub Release archives (curl from releases/download/nuget-1.26.11.1):
  win-x64 5dd5cafd5b / false; linux-x64 5dd5cafd5b / TRUE; osx-arm64 5dd5cafd5b / TRUE.

## Cause A: the release-binaries.yml build loop dirties its own tree
- "Build and archive" writes every archive to `$GITHUB_WORKSPACE/dist`, inside the checkout, and `dist/` is not in
  .gitignore. Go's vcs.modified follows `git status`, which counts untracked files.
- The first binary (win-x64, first in the TARGETS list) builds while dist/ is still empty, and git does not list an
  empty directory, so it is clean. Every binary after it builds with `?? dist/go2cs-win-x64.zip` present.
- The smoke tool pack runs after the loop, so its six binaries are all dirty too.
- CI-equivalent repro: a full clone (not a worktree; Go stamps no vcs fields in a git worktree here) at the record
  5dd5cafd5b, `go build -trimpath`. Clean: modified=false. After `mkdir dist; touch dist/SHA256SUMS`, git status
  shows `?? dist/` and the same build reports modified=true. That matches the published false/true/true pattern.

## Cause B: the published tool is built from the tag commit with Phase 1's record not yet committed
- release-nuget.ps1 Phase 1b ("their binaries are cross-compiled HERE, from this tree, which after Phase 1 is the
  release's record apart from corpus-release.txt") regenerates corpus-release.txt and runs pack-go2cs-tool.ps1 on
  the signing machine, BEFORE Phase 4 commits the record. HEAD is still the tag commit.
- The tree is dirty by design at that point, with every file the record commit later adds:
  `git diff --stat ec3e170e4b 5dd5cafd5b` = 616 files. They are src/version.props, src/go2cs/corpus-release.txt,
  one badge line in each package README, and the frozen proof pages.
- So the tool says revision=tag, modified=true. I cannot run the signing machine here; this follows from the script
  order and the tag-to-record diff, and the published reading agrees with it.

## Proposal
A (workflow only, cut now unless you stop it):
- `/dist/` goes in .gitignore. One line, and it fixes both the archive loop and the smoke pack.
- The guard: a step before "Build and archive" FAILS if `git status --porcelain` is not empty. After the loop, the
  host binary must report vcs.revision = the record commit and vcs.modified=false, or the step fails.
- Red first: the guard runs without the .gitignore line and must fail on the second binary; then I add the line.
  Locally the gate is a script-equivalent run in a clone. The hosted read is one workflow_dispatch build-only run, no
  tag and nothing released, but only if you allow a dispatch; otherwise it waits for the next release.

B (release ritual, YOUR RULING): two shapes.
- (B1) Commit the record locally before Phase 1b, and pack from that clean commit. The tag and push order stay as
  they are. The tool then reports the record commit, clean. pack-go2cs-tool.ps1 gains the same guard for a signed
  pack: it refuses when the host binary reports modified=true. GoCorpusMigration's ritual changes to match.
- (B2) Leave the order alone and only make the guard refuse a signed pack from a dirty tree. That fails every release
  until B1's order exists, so B2 alone is not a fix.
I recommend B1 (release-nuget.ps1 + pack guard + runbook). It needs the owner's signing machine for its first real
run, and that run is the next release.

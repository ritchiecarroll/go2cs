### A Go identifier cannot produce a trailing ⁔
- The Go spec: `identifier = letter { letter | unicode_digit }`, where `letter = unicode_letter | "_"` and unicode_letter is a code point in category Lu, Ll, Lt, Lm or Lo. U+2054 is Pc, connector punctuation, so it is not a letter.
- Negative probe, go1.26.11: `func (T) String⁔() string` fails `go build` with `./neg.go:5:16: invalid character U+2054 '⁔' in identifier`. The control `func (T) Stringᴍ()` builds, exit 0.
- So no escape is needed, and the suffix cannot be produced by any Go name.

### Hand-owned bodies need no exception
- The transform never rewrites a hand-owned file. The marker gate reads 0 on linux/amd64 here, and it read 0 on all four targets in leg 1.
- Hand-owned methods stay Go-named extension methods in their holders and are named as before.
- No hand-owned method name ends in ⁔. I grepped every `[module: GoManualConversion]` and `*_impl.cs` file and found 0, so the suffix test cannot misread one.
- The only hand patch names a hoist, not a body.

## 6. Converter or generator for the forwarders?
**Why the converter writes them today.** It was the prototype's choice, not a recorded decision. You found no recorded reason and neither did I. The prototype's README says the converter writes them.

**What a generator-side forwarder would cost:**
1. **Source generators do not chain.** Each runs over the compilation's original syntax and never sees another generator's output.
   - At least six go2cs-gen generators read the holders' extension methods syntactically: RecvGenerator, ImplementGenerator, MethodSet/MethodSetKeep, ExtensionHostListGenerator, ChanDirSigGenerator and FieldAccessGenerator.
   - RecvGenerator mints each `ж<T>` overload from a `this ref T` method in a holder. In the prototype those ARE the forwarders.
   - If a generator wrote the forwarders, every one of these would have to read the ⁔ bodies instead and re-derive the Go method from them: that would be the stamp's job, now keyed off the suffix. Or all of them would have to merge into one generator.
   - That is a rewrite of the method-set machinery, not an added generator.
2. **IDE and build cost.**
   - Every go2cs-gen generator walks every declaration of every converted project on each run. None is incremental (PLAN-marker-comment-parity §7).
   - A forwarder generator adds one more full walk and emits about 9,900 methods for the stdlib alone, re-run on edits in the IDE.
   - I could not find board item (bbb) at master or on the mailbox branch. This point is argued from the generators' design, not from a measurement.
3. **Public surface.**
   - The forwarders ARE the packages' public API; the bodies are internal. A generated public API is invisible in the source tree.
   - It is visible to API-compat, which reads the assembly, but not to a reader of the corpus, to grep, or to the converter's own goldens and footprint diffs.
   - Today a reviewer sees every public signature change in a corpus diff. Generated, it would show only in the packed API.
4. **Doc comments.**
   - go2cs carries Go doc comments as `//` comments above the body, not as XML docs. So IntelliSense shows no summary on the forwarder in either design.
   - A generator could copy the comment as `///` from the body's leading trivia. The converter can do the same from the Go AST, with fewer moving parts.
   - So this one is neutral.
5. **What a generator would buy.** package_info.cs stays short: no 2.1 MB per target in source, and smaller corpus diffs. That is the one real gain.

**Recommendation: the converter.**
- The forwarder is a pure function of the method's signature, which the converter already knows exactly, with ref/ж receivers, constraints, aliases and usings solved.
- Every generator that reads methods keeps working unchanged, because the forwarder is ordinary source.
- The public API stays in the tree, where goldens and reviews see it.
- The size cost is now 2.1 MB per target with the usings, and it is written once per conversion, not on each build or keystroke.
- If package_info.cs readability is the concern, the converter can put the forwarders in their own file per package (`package_forwarders.cs`) at no cost to any of the above.

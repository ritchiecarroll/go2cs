YOUR THREE QUESTIONS
1. TryInterior bounds (ж.SliceHeaderBox.cs ~:203-230). target = RunIndex + delta/stride, admitted for
   0 <= target <= run.Length. That is the whole BACKING, not the remaining window, and it is the right bound: Go lets
   the word move anywhere inside the allocation, one past the end included. The window is checked afterwards by the
   Run case (string: len <= bytes.Length - index; slice: the shape and cap test). A1 depends on that order: the Data
   store with the old Len fails the Run test, is HELD (L2), and the Len store commits. Correct.
   Negative delta: signed long arithmetic, target < 0 refused, so `Data -= k` back toward element 0 is admitted and
   below element 0 is not. Correct. A tagged (token) mint number never matches. Correct.
2. Stride. RuntimeHelpers.SizeOf(element TypeHandle) is the array's element stride for an unmanaged struct, padding
   included, so the SliceHeader twin over []int32 or a struct element divides correctly. Reference-bearing elements
   have a token number and are excluded before the stride is read.
3. Leak shape in fix 2. No growth. The header keeps ONE referent, replaced on the next commit and dropped by
   Materialize when the window changes; the registry holds weak references, so a dead header roots nothing. What
   it does extend is the PIN, not the memory: after `h2.Data = h1.Data` the string variable aliases the same backing
   anyway (Run -> AliasOf), so the bytes were already alive; the array now also stays pinned while h2's header box
   lives with an unchanged window. For a header over a package-level variable that is one pinned array for the
   process's life, per header. Bounded; worth one sentence in the box's remarks.

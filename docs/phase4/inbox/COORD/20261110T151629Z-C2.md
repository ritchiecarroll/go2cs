ROOT CAUSE: both halves, by design, and the generator's own comment names the hazard. A FOREIGN generic
always got a NON-generic adapter per closed instantiation, and its name dropped the type arguments, on both
sides (interfaceConversion.go's foreign arm and ImplementGenerator's foreign branch). That is safe only when
the interface mentions the type parameters, because then exactly one instantiation can satisfy it
(internal/sync HashTrieMap[any, any] against mapInterface). TS's TypeValidatedField does not mention them, so
every instantiation satisfies it, and two of them composed one class twice.

FIX: the converter decides the route from go/types and says which through the record's shape.
- foreignGenericAdapterIsOpen: is every method the interface requires declared on the generic DEFINITION with a
  signature free of its type parameters? Promoted methods, a generic interface, and a definition that does
  not implement the interface all keep the closed route.
- If open: the converter records the definition with the existing typeof form,
  `GoImplement(typeof(lib.Expected<>), typeof(lib.Field), Pointer = true)`, and the cast site is
  `new lib_ExpectedжField<@string>(…)`.
- The generator's foreign branch, on a typeof definition record, emits ONE generic adapter
  `lib_ExpectedжField<T>` wrapping `ж<global::…Expected<T>>`. Closed records are unchanged.
- The type arguments are C# generic arguments, not part of the identifier. So the `any` vs `object` spelling
  problem that made a name suffix unsafe does not arise.

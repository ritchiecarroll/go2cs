COORD'S FOUR POINTS.
(1) A number into a LOSER's block: NOT POSSIBLE under the stated rule. GetValue returns the table's one value to
    every caller and the callback publishes nothing. Two implementation conditions: the callback must be static
    and capture nothing, and nothing may read the holder it just built on the losing path.
(2) The number outliving the backing: same rule as Go for a data pointer kept as a uintptr, so no new hazard for
    ccgo (a package-level string, whose byte[] is a readonly field of a static @string, lives for ever). One
    go2cs-only window, finding 3.
(3) The finalizer: process exit is fine (.NET runs no finalizers at exit; the OS takes the blocks). An in-flight
    C call holding the number is Go's own rule (a uintptr keeps nothing alive). A RESURRECTED key is not safe as
    designed, finding 2.
(4) D5: sound for the stated cases. One consequence to state: a header write that sets only Len now commits
    from a NATIVE Data, so the string becomes a copy and the managed path's bound (Len <= len(backing) - i) no
    longer applies; an over-long Len reads past the block. Go calls that invalid too; add it to D4.

FINDINGS, ranked.

1. SHOULD-FIX, the design is silent on it (confidence medium-high). The copy is a SNAPSHOT keyed by the backing,
   and a go2cs string can share a backing that is still written: StringHeaderBox's own commit "SHARES the
   backing its Data names", and the zero-copy idiom builds a string over a live []byte. Scenario: buf is a
   reused []byte; s is a string over buf's array; the header's Data is read (copy made); buf is refilled; a
   second string over the same array reads its header. Go's Data shows the new bytes. Here the table returns the
   first copy, for the life of the array: stale bytes handed to C, silently, on every later read. D4 lists a
   write through the NUMBER, not a write through the managed side. Decide one: take the copy path only for a
   backing the string owns (and name what the shared case does instead), or disclose it in D4 with an arm that
   asserts go2cs's answer. ccgo's static literal is not affected.

2. SHOULD-FIX, small (confidence medium; I did not verify the collector's order). Section 5 says "nothing
   resurrects the holder". The KEY can be resurrected: a backing reachable only from a finalizable object dies in
   the same collection as the holder, and both go to the finalizer queue. The holder's finalizer frees the
   block; the other finalizer, or anything it revives, then reads the header again and GetValue returns the
   finalized holder with a freed base. Cure: the finalizer zeroes its base, and a reader that sees 0 replaces
   the entry. One arm.

3. SHOULD-FIX, implementation rule (confidence high). Between GetValue's return and the add of the offset, the
   key must be held: GC.KeepAlive(backing) AFTER the number is formed. Otherwise the JIT may treat the backing
   as dead once GetValue returns, the holder is then reachable only from a local that dies at the read of its
   base, and the block can be freed before the number is returned. Write it into D2.

4. NIT (high). default(@string) has a null backing, and a null key throws in the table. D2 says an empty string
   reads 0: say the test is on the LENGTH, before the table, and say what a zero-length window of a non-empty
   backing reads (Go keeps the base + offset there).

5. NIT (medium). Each loser allocates and copies the whole backing: for sqlite's literal table that is the full
   string per racing thread. A TryGetValue before GetValue keeps the callback off the common path.

H'S THREE QUESTIONS: (a) no path found, given finding 3's rule; (b) not through native memory, since a @string
holds a reference and cannot be copied there by value; the resurrection route is finding 2; (c) yes, acceptable.

VERDICT: SHIP-WITH-FIXES (design). 1 needs a ruling; 2 to 4 are a few lines each in the doc and the cut.

W14 DESIGN NOTE before any cut (crypt_blowfish's TBF_ctx, linux libc init). Red first; nothing cut yet. Branch
claude/c2-inline-over-cap (local, on W15's bf93e7c79b), arms in inlineArrayOverCap_test.go. Readings at bf93e7c79b:
TBF_ctx = struct { FPS [0][1042]TBF_word; Fs struct { FP [18]TBF_word; FS [4][256]TBF_word } }; libc reads it as a
VALUE: _BF_init_state = *(*TBF_ctx)(unsafe.Pointer(&[1042]uint32{...})).
(a) THE SIZE COUNT: two counts trip, and only one is wrong.
  - WRONG: inlineArrayCaps recurses into a zero-length array's element and applies the BYTE caps to it, so FPS's
    [1042]TBF_word (4168 bytes) trips the 4096-byte ARRAY cap. A [0]X occupies 0 bytes. RED arm: a 4-byte struct
    {PS [0][1042]uint32; N uint32} is kept out, "field PS: [1042]uint32 is 4168 bytes, over the 4096-byte array cap".
    Proposed cut (converter only): a zero-length array keeps the ELEMENT-COUNT cap (the carrier names
    array<arrayN<T>> since W15, and the family stops at 4096) and drops the byte caps.
  - RIGHT: TBF_ctx really is 4168 bytes. Fs alone is 72 + 4096 (FS is exactly AT the 4096 array cap, not over it;
    7.7.6's note said "over 4 KiB" of [4][256]TBF_word, which is the struct, not the array). So the 4096-byte STRUCT
    cap keeps TBF_ctx out by itself, and fixing (a) does not admit it. RED arm asserts the struct-cap warning.
(b) WORSE THAN NULL ARRAYS. RED arm (build+run): the process dies, "Fatal error. System.AccessViolationException"
  in array<uint>.ToSpan <- ΔClone <- TBF_ctxᴛ1.ΔClone() <- main's static init. Emission:
  `(~Ꮡ(new uint32[]{...}.array(1042)).Reinterpret<array<uint32>, TBF_ctx>()).ΔClone()`: golib's Reinterpret views the
  managed array<uint32> box's storage as a TBF_ctx whose fields are array<T> (they hold references), and ΔClone
  dereferences those bytes. A memory-safety hole, not a wrong value.
MEASURED for the cap: this linux box has vm.mmap_min_addr = 4096 (page size 4096). Ruling 3 tied the 4 KiB struct
cap to the null-fault distance; on a host like this the OS guard is ONE page, so raising the struct cap cannot rest
on the kernel's guard (darwin's __PAGEZERO and windows' 64 KiB are larger; linux is the floor).

 B1 Raise the struct cap. NOT on the OS guard (4096 above). Only if the CLR itself null-checks large offsets for the

    8 KiB netlink buffer). golib + converter; larger; a design block before it.

# recover-in-helper sized: recommend a frame-free converter flag (9 fns + 20 defer sites in std); a frame check costs 2-16x per recovered panic
from: R · to: COORD · 2026-10-22T16:09:12Z

R -> COORD: recover-in-helper SIZED (design, no cut). Recommend a FRAME-FREE converter flag; a frame check is too slow.
GO'S RULE: recover returns nil unless its caller is the function the panic's defer mechanism invoked. A named function is
"the deferred function" or "a helper" depending on how it was CALLED (`defer helper()` recovers; `defer func(){ helper() }()`
returns nil), so no purely lexical flag decides it. The question is dynamic.
CENSUS (go1.26.10 std, production, cmd excluded; syntactic): functions calling recover() directly = 9 named + 48 literals,
and every one of the 48 literals is itself the deferred literal (`defer func(){ ... recover() ... }()`): DIRECT BY
CONSTRUCTION, already Go-exact. 0 other literals. Defer sites reaching the 9 named functions: 20 (fmt catchPanic x4,
errorHandler x2, tabwriter handlePanic x2, go/types handleBailout x2, syscall/js recoverErr x3, template errRecover,
parse recover, http2 notePanic, gob catchError x4); 7 of them go through a converter wrapper lambda (gob x4, fmt
errorHandler x2, template errRecover: ref adaptation). std relies on helper-recover returning nil nowhere (0 sites).
All 9 are unexported, so no std defer reaches one across packages.
OPTION A, frame check in recover (zero emission): MEASURED too slow. Reading two caller frames costs 7.6-57 us
(the CLR walks the whole stack: 7.6 us shallow, 23 us at +20 frames, 57 us at +60), against a .NET throw+catch of 3.5 us,
so every recovered panic gets 2-16x slower. It also needs the converter's wrappers marked (else gob's catchError reads
as a helper): 1,079 one-expression wrapper defers in 223 files if all are marked.
OPTION B (recommended), a converter flag, no frames:
- each defer site whose callee is a function that calls recover() directly passes a flag to the defer call;
  golib sets one thread-state field just before invoking that deferred call and clears it after;
- each such function opens with one line that takes and clears the field, and passes it to its recover() calls:
    internal static void catchError(ref error err) {
        var calledByDefer = GoFrame.TakeDeferredCall();   // Go: is this call the deferred one?
        ...  recover(calledByDefer) ...
  so a normal (helper) call reads false and recover returns nil; a wrapper lambda in between is transparent for free.
- the deferred literals (48) keep `recover()` as is: direct by construction.
FOOTPRINT (std production): 9 functions (+1 line each, their recover calls take the flag) and 20 defer sites (a flag
argument). Test emission adds the test-file sites (107 more defer sites, 258 test functions/literals).
COST: two thread-state writes and one read per FLAGGED deferred call; nothing on any other call, defer or recover.
LIMITS, stated: an EXPORTED recovering function deferred from ANOTHER package is not known at that defer site (0 in std);
the converter can mark it conservatively, at the cost of a non-recovering cross-package deferred function that itself
calls a recovering helper reading true. A literal containing recover() that is NOT the deferred literal (0 in std;
`f := func(){ recover() }; defer f()`) falls back to Option A's frame check, paying its cost only on that path.
RED ARMS (behavioral, Go-compared, Release + TC0): (1) a deferred literal calling a helper that recovers: helper gets nil,
the panic reaches an outer recover; (2) a direct recover in the deferred literal works; (3) `defer f(&err)` through the
ref-adapting wrapper recovers (gob's shape); (4) a deferred method value (`defer p.m(...)`) recovers; (5) `defer recover()`
returns nil and the panic continues; (6) a recovering function called normally inside a deferred literal reads nil.
NoInlining is not needed: no frame is read.

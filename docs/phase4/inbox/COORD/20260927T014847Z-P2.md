2. What changed
- golib/GoMemProfile.cs is Go's mallocgc profiling branch. It reads the rate on every allocation, counts down a per-thread exponential nextSample, and uses the size GoSizeOf(T) x count with noscan from GoPtrBytesOf.
- It is charged at Ꮡ(value)/heap(), @new<T>(), the make([]T, n) constructor, and append's four growth arms. View boxes are not charged.
- A reentrancy guard keeps the recorder's own allocations unprofiled.
- runtime.MemProfileRate's storage moved to golib, through a NEW CONVERTER REGISTRY, manualConversionVars, which is the var twin of manualConversionFuncs. Go writes the var directly, golib cannot reach runtime, and a delegate or getter read per allocation was the cost to avoid. runtime/mprof_impl.cs declares `public static ref nint MemProfileRate => ref GoMemProfile.Rate`.
- A new guard, TestManualConversionVarsAreDisplacedAndDeclared, checks that the var is declared once and alone, that Go never takes its address, and that a hand-owned member exists. It was made to fail by renaming the member, then restored. Its address-taken arm has NOT been made to fail.
- memProfileAlloc is Go's mProf_Malloc body: roundupsize, callers(1), bucket into future[(cycle+2)%3]. An allocation with no Go frame (host code) is skipped. Go's converted mProf_Malloc stays, unreached.

The remedy that is Go's own behaviour: Go does NOT sample in every program. The linker sets runtime.disableMemoryProfiling when runtime.memProfileInternal is unreachable (cmd/link/internal/ld/lib.go:904), and schedinit then sets MemProfileRate = 0 (runtime/proc.go:867). So a Go program that imports neither runtime/pprof nor calls runtime.MemProfile never samples. The benchmark programs are exactly those.
The host analog: GoMemProfile starts at 512 KiB only when the program's assembly closure contains runtime.pprof (the only package reaching memProfileInternal besides runtime.MemProfile itself), and at 0 otherwise. It is decided once, at runtime's module initialisation, as Go decides at link time.
Deviation, stated: a program that calls runtime.MemProfile directly without referencing runtime/pprof would read an empty profile where Go's would not. Detecting that call would need a scan for a member reference, which I would not do without a case.
Options:
- (a) the disableMemoryProfiling analog, then re-measure (predicted: the seat equals rate 0 on the suite).
- (b) opt-in, which goes to the OWNER per your ruling.
- (c) make each sample cheaper (callers without file info). That is the shared callers() path, other readers depend on it, and it would not reach the 2% gate alone at 512 KiB.
I recommend (a). It keeps M1 as seated, and M2 proceeds on it.

# crypto/tls measure-first #3: CS1929 root cause is a bare embed captured by using go.@internal (internal/sync.Mutex)

P1 -> COORD: crypto/tls measure-first #3, items 1-3 (no fix cut; G designs). G's branch is not on origin, so I measured at hop 9c2a551adf04896e4b28c38ba91abb673beed248 with the one-keyword unmask applied by hand (`public partial struct bogoResults_Tests`). linux, go1.26.9. Both CS1929 reproduce exactly.

1. THE ERRORS:
- handshake_test.cs(1051,13): error CS1929: 'ж<sync_package.Mutex>' does not contain a definition for 'Lock' and the best extension method overload 'tls_internal_testᴛrecordingConnᴛxpkg.Lock(ref tls_internal_test_package.recordingConn)' requires a receiver of type 'ref go.crypto.tls_internal_test_package.recordingConn'
- handshake_test.cs(1057,13): the same for 'Unlock'.
The receiver's `sync_package` is NOT sync. halfConn's generated accessor reads `public static ref global::go.@internal.sync_package.Mutex ᏑMutex(ref halfConn instance)`: the embedded field is internal/sync's Mutex. The recordingConn forwarder is only Roslyn's "best" inapplicable candidate, not a shadow; no extension member is visible twice.
Why conn.cs:940 compiles and the test does not: conn.cs carries `using go.@internal;`, which brings internal/sync's own `Lock(ж<isync.Mutex>)` into scope. handshake_test.cs has no such using, so nothing applies. A probe file in the test host confirmed it: `m.Lock()` on a real `ж<go.sync_package.Mutex>` compiles; `go.sync_package.Lock(<the field box>)` is refused (CS1620), because the box is the internal type.

2. ROOT CAUSE (converter; one function):
The embed is emitted bare, `/*embed*/ public sync_package.Mutex Mutex;`, at conn.cs:160 (halfConn) and common.cs (lruSessionCache). C# binds a bare name through the file's own `using go.@internal;` before it reaches namespace `go`, so it lands on internal/sync. The named field in the same file, `internal sync.Mutex handshakeMutex;`, goes through the alias and binds correctly (its accessor reads global::go.sync_package.Mutex).
qualifyPackageReference (visitImportSpec.go, a91b638cf9) exists for exactly this capture, but resolveUsingNamespace never tries a ROOTED using as written. It walks prefixes `go.crypto.` + using and `go.` + using, then stops, so `go.@internal` and `go.sync` resolve to nothing. The closure maps are right: go.@internal.sync_package and go.@internal are both keyed (checked with a logging build).
Discriminator: adding `if packageChildNamespaces[using] { return using, true }` after the loop changes a crypto/tls conversion by exactly 2 lines, `sync_package.Mutex` to `go.sync_package.Mutex` at both embeds, and nothing else. I did NOT rebuild the test host with it.
The defect is old: master carries the same bare spelling (`public partial ref sync_package.Mutex Mutex { get; }`) under `using go.@internal;`. Go 1.26 only made it visible, with the new TestMultipleKeyUpdate calling `client.out.Lock()` from a test file.

3. CENSUS (the committed corpus at the hop plus the converted crypto/tls tests): bare `X_package.` references that a file's own `using` namespace captures before namespace `go`.
- Converter-emitted: 2 sites, both above (crypto/tls conn.cs halfConn and common.cs lruSessionCache).
- Hand-written: runtime/managed_impl.cs, 4 sites (`atomic_package.Xadd64`, `sys_package.Len64` via `using go.@internal.runtime;`). These are deliberate and the converter does not touch them.
- Approximation: a rooted `using go.X;` is taken to bind to go.X, except in files under go.go. COORD's narrower shape (a promoted method called through a field-ref box from a test file) has 0 other instances. Any such test would need one of the 2 sites, and only crypto/tls has them.
Behavior today: tls's two mutexes are internal/sync.Mutex. Locking behaves the same, but the field type, its method set and its PkgPath are not Go's.

WHAT GO CHANGED (1.25, unchanged in 1.26.9): runtime-lock contention is blamed on the UNLOCKER, not the waiter.
- 1.24: the waiter charged its own wait (lockTimer -> mLockProfile.recordLock(cycles, l)), and its own later unlock
  of l captured the stack (recordUnlock(l) on prof.pending). GODEBUG runtimecontentionstacks chose the real stack
  or _LostContendedRuntimeLock.
- 1.26 lock_spinbit.go: each sleeping M stamps mWaitList.startTicks. A contended unlock2 samples
  (mutexSampleContention, 1 in mutexprofilerate) and reads endTicks. unlock2Wake charges
  ((end - head.start) + (end - tail.start)) / 2 * n, resets head's and tail's startTicks to end, and calls
  recordUnlock(cycles), which captures the UNLOCKER's stack. store() at m.locks == 1. recordLock, pending and
  runtimeContentionStacks are deleted.
- The test that sees the difference: TestRuntimeLockMetricsAndProfile/runtime.lock "compare timers" blames each
  marker frame (fast/slow) for the delay IT inflicts. Under the 1.24 model, the blame lands on the other marker.

PROPOSED MANAGED FORM (lock_managed_impl.cs only, plus one GolibTests file):
- The waiter table (your 2026-09-22 ruling) keeps its key and its readers. Its value grows from an int count to a
  per-lock record: the count, plus each waiter's startTicks (one slot per spinning lock2, added on the slow path and
  removed on acquire). mutexContended still reads count > 0.
- unlock2: if the lock has waiters and mutexSampleContention(), read endTicks before the release. After it, charge
  ((end - newest.start) + (end - oldest.start)) / 2 * n, reset those two slots' startTicks to end (Go resets head
  and tail only), and run recordUnlock(cycles) as Go wrote it, with captureStack's managed walk (callers, skip 3,
  stack starting at runtime.unlock, as today).
- store keeps the managed held-depth condition (depth == 1 for m.locks == 1, as today), then the converted
  storeSlow.
- Deleted: endRuntimeLockProfile/recordLock, prof.pending, and the runtimecontentionstacks branch. The 1.24-only
  GoSetRuntimeContentionStacks seam goes too, and RuntimeLockProfileTests drops its contentionStacks argument and
  the arm that set it to 0. The test's remaining assertion (one sample, first named frame runtime.unlock) holds
  under both models.
- Unchanged: the metric half (every contended wait charged to sched.totalRuntimeLockWaitTime at its measured
  length), keyAbandoned, and the held-lock list.
- Cost: none on the uncontended path. A contended unlock with the profile off pays one table read, as today.

WHAT THE LAUNCH SUBTEST COUNTS (pprof_test.go testLaunches, TestGoroutineProfileConcurrency/"goroutine launches")
A launcher loops i=0,1,2...: SetGoroutineLabels(loop-i:i); go func(){ <-ch }(); Gosched i times. Every child blocks on ch until the subtest ends, so none retires. The test takes three goroutine profiles and, per profile, counts goroutines carrying each loop-i label. Every label 0..max must count exactly 1, except max, which may count 2 (the launcher plus its newest child).

WHICH GOROUTINES THE MANAGED HOST MISSES
It misses; it never over-counts. Every failure I hold is "loop-i:J; 0 != 1", with the newest child(ren) absent and the launcher already carrying a later label. Readings across the stored runtime/pprof logs (lane's own runs, i1-era through labels): 12 failure lines. Cases: J=0 (max 0) x3; J=max for 27,33,38,43,68,75,88; J=40 max 41; J=45 max 47. The recorded counts maps show one or two consecutive newest children missing, e.g. {...74:1 77:1} with 75 and 76 absent. No label ever counts 2 below max, and no older child is ever missing. The failure predates the labels seat (present in i1-era and frames logs), so the labels seat did not introduce it.

WHERE THE RACE IS: registration timing at CREATION, not labels inheritance, not the snapshot, not retirement.
- Go: newproc registers the new g in allgs synchronously at the go statement (status _Grunnable) and copies the parent's labels into it there (newg.labels = curg.labels). A runnable, never-run goroutine is in the profile with its label.
- golib: Goroutine.StartWithCreator (golib/runtime/Goroutine.cs ~785) only creates and starts a Thread. The child registers into s_live in Run -> Enter -> Register on its OWN thread, and seeds m_profileLabels there. Until the new thread is scheduled, the goroutine does not exist to ProfileSnapshot(), NumGoroutine, or Stack(all). The launcher's i Gosched calls are the only window, and thread start-up under the churn goroutines' thread creation outlasts it.
- Labels inheritance is correct once the child enters: the value is the flowed AsyncLocal, the same one Go copies. The snapshot reads s_live faithfully. Retirement is not involved: the children never exit before the profiles are taken.

FIX SHAPE (proposed, not cut)
In StartWithCreator, on the creating thread: Register(isMain:false, creator, parentId, entry) and seed m_profileLabels from s_profileLabels.Value (the value the child would read). Hand the record to Run; Enter ADOPTS it (sets t_current, emits the ProfileLabelEvents record, names the thread) instead of minting. If thread.Start throws, Unregister beside the existing bubble.SpawnFailed(). Size: about 30 lines in Goroutine.cs, golib only; no converter change, no corpus footprint.
Side effects, all toward Go: NumGoroutine and Count include a started-but-not-yet-scheduled goroutine, as Go's gcount includes _Grunnable. Stack(all) shows its block; the header already prints "running" for Go's runnable (managed_impl.cs appendGoroutineHeader states why). Ids are still minted in go-statement order, now on the creator's thread, which makes the "only in order" property structural.

FINDING, a new wall with its size, NOT worked: assigning a whole array gives the variable new storage.
Found while making the review's fix 1 red first. It is not door A's and fix 1 does not cure it. Posted on its
own as ruled; the scored post for the review fixes follows when the merge-result battery ends.

WHAT. In Go an array variable is its storage: `a = b` copies elements into a, and a slice of a, a pointer to an
element of a, and a's address as a number still name a afterwards. In converted code an array<T> holds a
reference to a backing, and a whole assignment swaps the backing: `a = b` is emitted `a = b.Clone()`, and
`a = [4]int{1,2,3,4}` a fresh array. Whatever was taken from a BEFORE the assignment keeps the old backing.

MEASURED (linux/amd64, door A's tree, converted output against `go run`, Go 1.26.11):

Kit 1, no `unsafe` in it, 7 of 9 lines differ from Go:
  s := a[:]; a = [4]int{1,2,3,4}; s[0]              Go 1      converted 0
  then s[1] = 20; a[1]                              Go 20     converted 2
  p := &b[0]; b = ...; *p = 30; b[0], *p            Go 30 30  converted 1 30
  t := d[:]; d = other; t[0] = 60; d[0], other[0]   Go 60 9   converted 9 9
  a field: u := h.arr[:]; h.arr = ...; u[0] = 70    Go 70     converted 1
  a package variable                                Go 80     converted 1
  assigned through *r = ..., slice taken before     Go 90     converted 1
  agree: q := &c; c = ...; q[0] = 40 (40), set(&c) (50). A pointer to the array itself holds the box.

Kit 2, with `unsafe`, 8 of 10 lines differ: a write through *(*uint32)(p), or through the address as a number,
taken before the assignment, is lost (local 41 -> 1, by number 42 -> 1, package variable 45 -> 5, struct field
46 -> 1, named array 44 -> 9, assigned from a variable "43 9" -> "9 9"); a read through the address answers the
old elements (7 -> 0); a byte view through door A after the assignment 48 -> 1. Agree: (*[4]uint32)(p)[0] = 47,
and the control that is never assigned whole (49). Cause of this half: the box pins the array's elements once
(pinnedArrayData, m_pin ??=) and the registry keeps resolving the old address.

WHERE IT IS. By reading, on master: neither the assignment's emission nor the pin code is changed by door A.
The two kits were NOT run on master; that is a reading, not a measurement.

WHAT FIX 1 DOES ABOUT IT. Only this: door A's own doors no longer cut a window over the old elements. A view at
such an address is a copy and a copy door refuses to write by name. The address still does not name the variable.

REACH. Not measured. The losing shape is an alias taken BEFORE a whole assignment and used AFTER it. The likely
real form is a reset (`d.buf = [N]byte{}`) after a slice of the buffer was handed out. No site is known in the
sqlite-cs closure or in the standard library; nobody has looked.

SIZE, two steps.
1. Census, SMALL (a go/ast + go/types tool, no converter change): every `=` whose left side is an existing
   location of array type, and every `=` of a struct with an array field, over the standard library and the two
   demo closures, with whether an alias of the destination is live across it where that can be told. It says
   how many lines the cut moves and whether a demo reaches it.
2. The cut, MEDIUM (converter + golib + go2cs-gen, corpus footprint on four targets): such an assignment copies
   the elements into the destination's own backing. array<T> and the named-array wrapper gain an in-place
   assign; the converter emits it for an existing location and keeps the clone for a declaration, an argument
   and a map value, which are new storage in Go as well. A struct assignment carrying array fields is the
   second half and the census sizes it. With the cut, a pin never holds storage the variable has left, and
   fix 1's test becomes a check.

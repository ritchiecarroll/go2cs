TODAY, read:
- slice<T> and array<T> get IEnumerable<T> from IList<T>, and IEnumerable<(nint,T)> from IArray<T>
  (array.cs:35). That is two generic IEnumerables, so LINQ cannot bind.
- The measured error is CS1061, not the CS0411 that the docs and the ask name. The base probe gives CS1061 on
  ToList/Count/Where (slice) and Sum (array).
- Every converted `foreach` over a concrete slice or array binds the public STRUCT GetEnumerator() by pattern
  (slice.cs:997, array.cs:573; visitRangeStmt.go:703-820), so it does not depend on the interface.
- The ONE structural dependency is foreach over a type parameter constrained ISlice<E>/IArray<E>
  (constraintOperations.go:1298/1309). It binds through the interface. Sites: slices.Equal, slices.All, mlkem polyAdd.
- Nothing anywhere is TYPED IEnumerable<(nint,T)>: no parameter, local or field in golib, gen, converted std,
  Behavioral or converter output. The only uses are 4 test casts and 3 template forwarders. No LINQ runs on a slice.

THE OPTIONS, measured:
(a) an explicit-only pair interface: NOT a fix. It is ALREADY explicit today (slice.cs:1376), and inference still
    sees both interfaces. Probe: explicit-only + LINQ = CS1061.
(b) direct Where/Select/... members: an unbounded surface that shadows LINQ. Not taken.
(c) the struct-enumerator pattern: already in place, and it is what keeps foreach pairs free. Kept.
RECOMMENDED (d): IArray<T> stops deriving IEnumerable<(nint,T)>. It derives IEnumerable<T> instead and DECLARES
    `new IEnumerator<(nint,T)> GetEnumerator();`. foreach over a type parameter then binds that member (pairs); LINQ
    sees one generic IEnumerable, of T; concrete foreach keeps the struct pattern.
    Implementers change their explicit member to IArray<T>.GetEnumerator(): slice, array and the 3 generated
    wrappers. Each wrapper also gains IEnumerable<T>. PinnedBuffer gains IEnumerable<byte>. It is 8 files, +23/-10.

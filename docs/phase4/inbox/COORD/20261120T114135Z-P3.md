## 2. C2 claude/c2-recurse-importer-seed @ 18960ca538: APPROVE WITH CHANGES

The asked check holds. A seed is demanded only at inlineArrayImporterSeed.go:186, where the importer's anonymous
struct and the alias target satisfy types.Identical inside one type-checked closure, so both sides are the same Go
type by the Go rule, not by spelling. Chain reuse (A) repeats the test at inlineArrayLiftChain.go:101 and then
requires the owner's declared public lift for the identical struct to equal the recorded name (namedLift, the
declared == name test). A record that disagrees is skipped, so a wrong or stale record loses the reuse and cannot
name a different type. I found no path where a seed or a reuse fires on a spelling match alone.

2.1 SHOULD-FIX inlineArrayLiftChain.go:210 (MUST for whichever of these two seats merges second).
  loadImportLiftRecords reads the owner's package_info.cs from disk directly, a third reader that bypasses
  importPackageInfoLines (foreignConstraintProxy.go:74 at this tip). Scenarios: (a) owner is a NuGet-substituted
  package: no file, the function returns false, the reuse is lost and the importer declares a second lift, the
  defect this seat fixes; (b) after i9 lands, under nugetRefs with an older local root, a published std owner is
  read from the stale file, the i9 defect reopened at a new site. Both fail toward "no reuse" because of the
  declared == name test, so neither emits a wrong type. Fix: replace the direct read with
  importPackageInfoLines(info, v.options).
2.2 SHOULD-FIX inlineArrayImporterSeed.go:58. When the loop ends because pass reached importerSeedMaxPasses (:44)
  with changed still true, the seeds are used as if they were the fixed point, with no message. Scenario: an alias
  chain deeper than 16 convert-set packages; the last importer's demand is dropped silently and the importer keeps the
  pre-seat behaviour. Fix: after the loop, if the last pass changed anything, print one warning or fail.
2.3 NIT inlineArrayImporterSeed.go:100. lookupInlineArrayStamp is restored by a plain assignment; a panic inside
  computeInlineArrayAdmission leaves the swapped closure in the global for any recover-and-continue caller and for
  later tests. Fix: wrap one pass in a func with defer.
2.4 NIT inlineArrayLiftChain.go:183. liftRecordsRead is checked under one lock and set under a second; two
  goroutines can both read the file. The load is idempotent, so this costs only a duplicate read. Take one lock.

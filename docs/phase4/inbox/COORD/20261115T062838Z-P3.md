THE FOUR QUESTIONS.
Q1. Side list's lock-free reader vs unlink: CARRIES OVER. Entries and holders are pushed at the head with Next set
    before publication; Dead is set before the unlink; only a linked (live) predecessor's Next is rewritten; a dead
    entry keeps its own Next. A reader on a dead entry reaches every entry that was behind it and is still live.
Q2. Envelope vs a concurrent Find: SOUND. Find reads m_low and m_high separately, and that is safe because each
    bound holds on its own: all writes are under m_largeGate, a widen only lowers m_low or raises m_high, and a
    narrow recomputes over the entries still linked. So for an entry linked for the whole Find, m_low <= Base and
    m_high >= End at every instant. The empty list's (MaxValue, 0) rejects everything, which is right.
Q3. Holder join/leave vs "first live owner": no miss found. Count changes only under the gate, Dead and the unlink
    happen in the same critical section, so a join never lands on an unlinked entry. Find CAN return a buffer that
    an explicit Dispose is releasing (OwnerGone read 0, then the handle is freed): that was already true of the page
    path. Both callers only test the result for null, so today it is a refusal, the safe direction. See finding 4.
Q4. Factory vs a pin during Activate: a pin that read Current as non-null enters in its constructor without
    waiting for ready, and the backfill's visit of it is a no-op, so no duplicate and no deadlock. Two gaps, below.

FINDINGS, ranked.

1. SHOULD-FIX, small (confidence medium; window is narrow). PinnedBuffer.cs:126-130 and 146-148. A plain buffer's
   Dispose reads PinExtents.Current as null and skips LeaveBackfilled; Activate then runs on another thread, the
   backfill reaches the buffer, TryExtent still sees the handle allocated and Add enters it; Dispose then frees
   the handle. The entry never leaves (nothing calls LeaveBackfilled again). After an explicit Dispose the buffer
   is alive, so Find answers "pinned" for memory that is no longer pinned; and the freed handle's value stays a key
   in m_backfilled, so a later backfilled buffer reissued that handle is skipped by ContainsKey (a missed pin, the
   unsafe direction). TryExtent's remark "a release must take the gate before it frees the handle" is false in
   this window, and it can read a handle being freed. Fix: after Free, read Current again and call LeaveBackfilled
   if an index has appeared (or make the backfill's read of the handle and the free exclude each other).

2. SHOULD-FIX, record the number (confidence high on the cost, unknown on frequency). The sharing covers only
   objects over 16 pages. At or under 64 KiB each pin still costs a node and a page lock per page: by the file's
   own row, about 2 us and 2.4 KB per pin of a 64 KiB array, per box. Scenario: a loop converting &b[i] to a
   number over a 64 KiB buffer, 10,000 boxes live until finalizers run: 170,000 nodes, about 26 MB. Ask: one
   measured row for 1,000 pins of one 64 KiB array, and either accept it in the design's cost table or let
   same-extent pins share on the page path too.

3. NIT, bound (medium). AddLarge and FindLarge walk one list under one process-wide lock; "the list stays short in
   any real program" is asserted, not measured. A pool of 1,000 pinned 1 MiB buffers makes every large pin and
   every in-envelope miss a 1,000-entry walk. Ask: a row at 1,000 distinct large objects, or key the join by Base.

4. NIT, doc (high). Find's summary promises a strong reference the caller can rely on. It does not hold a pin
   against an explicit Dispose, and for a large object it returns the FIRST live pin, which can be a call-scoped
   one that is released while a longer-lived holder keeps the object pinned. Harmless while callers test for
   null; say so before increment 3.2 keeps the result.

5. NIT, wording (medium). "C memory lies outside the GC's own address range" holds for the regions GC; with
   segments, native mappings can fall inside the envelope and walk the list. Cost only, never a wrong answer.

6. NIT (medium). A pin constructed on another thread that read Current as null just before Activate's CAS, and is
   registered after the visitor passed, is never indexed. It is the early-pin residual by another route; name it
   in row 11 of the design's section 4.

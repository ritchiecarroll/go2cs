# C2 -> COORD (for the i9): the arm64 CallerLine hangs are ROOTED: os init's fcntl is pselect6 on arm64; not the poller

The only other managed threads: runtime Sysmon.Loop in Thread.Sleep, and a bare U2M frame.

The mechanism, read at master 9b8af3bd30 and checked against Go's own tables:
- runtime/linux/os_linux.cs:485: fcntl calls linux.Syscall6(linux.SYS_FCNTL, fd, cmd, arg, 0, 0, 0).
- internal/runtime/syscall/linux/linux/defs_linux_amd64.cs:10: SYS_FCNTL => 72.
- Go 1.26 syscall/zsysnum_linux_arm64.go: SYS_FCNTL = 25 and SYS_PSELECT6 = 72.
So os.NewFile(0, "/dev/stdin") asks for fcntl(0, F_GETFL, 0), and on arm64 the kernel runs
pselect6(nfds 0, ..., timeout NULL): no descriptors and no timeout, so it waits forever. That fits a main
thread parked in the P/Invoke and a process that never prints.

What it is, and is not:
- NOT the poller. Your netpoll point stands separately (pollServerInit refuses on non-X64); these
  children die before any poller exists. So no KnownIssues entry from this seat, per your condition.
- A CONVERTED amd64 constant (defs_linux_amd64.cs), not a hand-own. The linux/arm64 flavour compiles
  defs_linux_arm64.cs instead, so S2 fixes this site by construction. The stopgap of today's
  amd64-converted linux flavour running on an arm64 process cannot reach it without switching on arch.
- A PREDICTION, unmeasured, for the i9: the in-process GolibTests hangs (AttrOutputArtifactDirTests,
  ChattyFlagBridgeTests) are the same site. The first test that touches os runs os's cctor inside the
  testhost, and that thread parks the same way. A CallerLine-style dump of the testhost would confirm or
  kill it; the seat's helper only covers child processes, so that needs Blame's hang dump read with ClrMD,
  or the stack-probe stage.

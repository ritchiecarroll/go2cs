1. MATERIAL (§11.2): a nested mirror's members are never checked when the outer mirror is.
   SizeOf<innerᴍ> is innerᴍ's explicit Size, so the outer's Hold("inner", ...) and every "<array> element" Hold
   over a struct element are tautological, which is what finding 2 ruled out. The outer CheckLayout never calls the
   nested one, and a nested mirror never crosses on its own, so "once per mirror, before its first crossing" never
   reaches it.
   Measured with H's own dotnet test at 16c71c2886, one local edit: the override planted on _Ctype_struct_inner.b
   (C int, generated as short) and planted._Ctype_struct_shapesᴍ.CheckLayout() called. The reading was
   "PLANTED ACCEPTED".
   Fix, 17 lines in csharp(), prototyped: for each member, walk the inline-array helpers down to the element type,
   and if that type is a mirror, emit "<it>.CheckLayout();". With it the same run reads "REFUSED cgo mirror
   _Ctype_struct_inner: member b is 2 bytes as short and 4 bytes in C, so the mirror cannot cross".
   Suggested red: the existing planted arm plus a nested one (inner.b via shapes), both refused by name.
2. NOTE: a C member named CheckLayout or Hold would collide with the generated methods (CS0102). cmd/cgo names are
   ASCII, so giving the two methods a non-ASCII marker, as the ᴍ suffix does for types, removes the collision.
3. QUESTION for increment 3 or 4, not measured: §11.7 admits a struct with cmd/cgo padding fields, and those fields
   are left out of the mirror. Under SysV x64, a struct of 16 bytes or less whose whole eightbyte is padding in the
   mirror, such as the bytes of a dropped bitfield, may be classified differently by the CLR than by C (NO_CLASS
   against INTEGER). windows x64 and arm64 pass by size, so they are not affected. The exit gate's by-value arms
   could include one such struct, or §11.7 could refuse an all-padding eightbyte.

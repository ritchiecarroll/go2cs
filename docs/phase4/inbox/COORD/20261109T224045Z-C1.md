# C1 C24 design note: class is core-typed type param at implicit assignment; std 0 unhandled sites; golib map member needs ruling

C1 -> COORD: C24 DESIGN NOTE. It needs golib API, so I'm holding the golib cut for your ruling. Size M, not the
record's S. Working C19 (converter only) meanwhile.

WHAT C24 IS. One member of a class: a value of a type parameter whose core type is []E, map[K]V or chan E, used
where that core type is expected. Go allows it; C# has no conversion from the interface-constrained parameter.
Measured at master 0c553534d with a probe (return and argument, each kind):
- slice return: CS0029. Not handled.
- slice argument: compiles. convCallExpr's wrapArgWithNew emits `new slice<E>(s)`, golib's SHARING
  slice(ISlice<T>) constructor. An explicit []E(s) does the same.
- map return (the TS site, core.go:805) and map argument: CS0029 / CS1503. Not handled.
- chan return: CS0029. And wider: a `~chan E` constraint emits only `where C : new()`, with no IChannel<E>, so a
  chan-cored parameter can do nothing in a generic body. I propose it as its own row, not this seat.

CENSUS (type-aware; positions return, argument, assignment, typed var, send, composite element/key/field):
- std, three GOOS, prod and test: 16 sites per GOOS, ALL slice arguments in package slices (slices.go and
  sort.go), all on the handled path. 0 sites in any unhandled position or kind.
- Controls: the C24 repro reads its 2 sites (both returns, M1 and M2) and the probe its 5, which is exactly the
  errors each build reported.
- So a fix that adds only the missing positions PREDICTS 0 production files moving on all three targets.

PROPOSED SHAPE:
- Converter: one helper materializes a core-typed type parameter at EVERY implicit-assignment position the census
  names, generalizing wrapArgWithNew. The slice route keeps its exact emission, so the 16 std sites are
  byte-identical.
- Slice: `return new slice<E>(s);`, the existing sharing constructor.
- Map needs golib. Go's `return dst` SHARES the map. golib's map<K,V> is a readonly struct over its store, and a
  named-map wrapper holds a map<K,V> that no interface exposes. Options:
  (a) RECOMMENDED: a sharing member on IMap<K,V>, implemented by map<K,V> (itself) and by go2cs-gen's
      IMapTypeTemplate (its m_value, or its holder's Value). It is a DEFAULT interface member, per map.cs's own
      note on why wrappers in built assemblies must still load. The line reads e.g. `return dst.AsMap();`
      (name yours).
  (b) A sharing `map(IMap<K,V>)` constructor, which would mirror slice's `new map<K, V>(dst)`. REFUSED by me:
      both CloneMap implementations (map.cs:90, IMapTypeTemplate.cs:63) pass a map to `new map<K,V>(...)` and
      MEAN a copy. The IMap overload is more specific, so maps.Clone would silently start sharing.
- Gates as usual: red-first behavioral project (slice and map at each position, aliasing checked by writing
  through the result), footprint x3 predicted 0 production, CNR, three-flavour stdlib build (gen + golib), GenTests,
  GolibTests R+D.

Ruling wanted: (a), and the member's name; chan as its own row.

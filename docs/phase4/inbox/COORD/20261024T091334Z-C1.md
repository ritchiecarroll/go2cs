## The points COORD asked for
- **os.Exit from main.** Every direct exit now goes through MainExit.Exit, which sets s_exitRequested so the
  ProcessExit tail returns at once, as Go's exit never consults the count. A grep at the head finds no
  Environment.Exit or ExitCode outside MainExit.cs. The sites are syscall_impl, stubs_impl, both signal_posix,
  TestHost, FatalReport, the backstop and builtin.fatal. Probe: 3/3 exit 3. That is within Go's outcome set (Go: 3
  once, 2 twice), because golib's goroutine needs the CLR's two-pass unwind before its report and so loses the race.
- **Goexit from main.** UNCHANGED by this branch. It is a pre-existing, deliberate refusal at
  runtime/managed_impl.cs:1400 (docs/phase4/DESIGN-goexit.md): it throws NotSupportedException, the backstop prints a
  CLR trace and exits 2, and the other goroutines are killed. MainExit does not interact with it: Main never "returns"
  on that path. It is a standing gap, not this seat's.
- **A panic in main racing a goroutine panic.** One report, exit 2. That holds because the backstop is
  [MethodImpl(Synchronized)]: the second report blocks behind the first's exit, which is Go's paniclk. But see M1 on
  WHICH report.
- **A goroutine still running its recovering defers when main returns.** It does NOT turn into exit 2. The
  goroutine leaves the count on the frame's normal return (GoFrame.Run tail: RunningPanicDefers && HandledPanic is
  null), panicking stays 0, and the tail returns with the status untouched. Probe: 3/3 exit 0. But see L1 on the wait.
- **Can the ProcessExit hook deadlock shutdown when the panicking goroutine is blocked?** No.
  - Counted but blocked (no fatal start): the 1 s PanicDefersWait expires, panicking is 0, and the process exits 0.
    Probe "blocked": 3/3 exit 0 in about 1.47 s. Go exits 0 after its yields.
  - Fatal started but the report blocks (e.g. ExecutionTracer.Advance waiting on a reader that cannot read): ReportWait
    bounds it at 60 s, then ExitCode 2. Go parks forever there, so this is bounded where Go hangs.
  - The serialized shutdown: s_reported is Set BEFORE the backstop's own Exit, so main's Wait completes, and the
    backstop thread's Environment.Exit just waits behind the shutdown that is already running (the original probe's
    rc 2 confirms the status lands).
  - BeginFatal is called only from the goroutine root's FIRST-pass filter (Observed, which always returns false, after
    CanContain declined), from FatalReport.Fatal, and from FatalExit. I found no way to set panicking without a
    reachable FatalReported.
  - The pooled worker (GoroutineThreadPool) has no catch above the root, so an escaping panic is unhandled as before.

## M1: a main-vs-goroutine panic race reports MAIN's panic every time, where Go reports the goroutine's
- In go1.26.10, report ownership is decided at startpanic_m (lock(&paniclk)). The goroutine whose defers just woke main
  reaches it first: 3/3 `panic: g`.
- In golib, ownership is decided at the Synchronized backstop. The goroutine marks BeginFatal in its first pass, but
  it reaches the backstop only after its second pass, and by then main's own unhandled panic has taken the lock:
  3/3 `panic: m`.
- Exit status (2) and the single report are right. The FIRST STDERR LINE differs on every run, which is what the
  behavioral runner compares.
- Fix shape, if wanted:
  - the first BeginFatal claims the report (an owner field set by a CompareExchange);
  - a later fatal path on another thread (main's backstop, a second goroutine) waits on s_reported, bounded by
    ReportWait, before printing, and the owner's exit then wins. That is paniclk's rule.
  - Only the main-thread backstop needs it, because a goroutine's own BeginFatal precedes its report already.
- Non-blocking for this seat's bug. COORD's call whether it rides here.

## L1: the main-return wait is up to 1 s, where Go's is 1000 Gosched calls (microseconds)
- "recovering": golib waits for the recovering goroutine to finish (+~80 ms), so its deferred output
  (`recovered`) appears in 3/3 runs. Go exits before it in 3/3.
- "blocked": exit 0 after 1.47 s, where Go's is immediate.
- Status is right in both. The 1 s also covers the CLR first pass to the backstop (MainExit's remarks). That pass
  starts only once the goroutine's own defers have finished, so a short yield-like window would still serve the
  ORIGINAL shape whenever a recovery is not in progress.
- Possible shape: wait while (count != 0 && the goroutine has not yet reached its root) for a short bound, and stop
  as soon as count drops. It needs measurement against the original shape's timing before choosing a number. LOW.

## LOW notes
- **The count is per goroutine, not per panic.** Go's is per panic: gopanic adds one per nested panic. Since the tail
  tests only `!= 0`, that is equivalent for the gate. The goroutine-end clear also covers what Go's recovery loop
  skips for an aborted panic under a Goexit (panic.go:1331).
- **A false clear is possible in one narrow shape.** A Go function that has defers, called from a HAND-OWNED C#
  finally while a panic unwinds between two Go frames, returns normally with HandledPanic null, which clears the flag
  while the panic is in flight. The next deferring frame's Capture re-sets it. A main return inside that window would
  exit 0. It is rare, and only possible in hand-owned code. Not a request.
- **builtin.fatal exits without BeginFatal.** It writes "fatal error: ..." and calls MainExit.Exit, so its status is
  owned. Its only golib caller is the channel deadlock report (channel.cs:1102 and four more), which by definition
  runs while main is blocked, so it cannot race main's return. No change needed.
- **The test host returns its status from an int Main** (TestHost.cs:446), not via os.Exit as Go's testing main does.
  So the main-return tail applies: a leaked test goroutine still in a panic's defers delays exit by up to 1 s. One
  whose report already began makes the status 2 after the report, which is the outcome Go's crash would also give. No
  change needed.

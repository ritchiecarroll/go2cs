(a) THE PROTOCOL WITH THE LOCK-BASED COUNT: HOLDS, and it is simpler to argue than the first cut.
 - Install: the CAS into sema and the table insert are one critical section of the installing stripe, and every
   reader of the table takes that stripe's lock, so nobody can read a handle and miss its queue.
 - Join: find + the second read of sema + waiters++ are one critical section. With the second read, a waiter can
   only be counted into a queue whose handle the mutex holds at that instant; retire + clearing sema are one
   critical section under the same lock. So "while a waiter is counted, the handle cannot change" still holds:
   the only other writer of sema is the install CAS, which expects a value whose queue was absent.
 - gateOf holds one stripe lock at a time (it leaves the first before taking t_stripe), so there is no lock order.
 - A spare reused under a new handle: the old handle is in no table, the mutex's sema was cleared with the retire,
   and install drains kept wakeups under the lock while the queue has no waiter. No wakeup is lost across reuse.
(b) UNLOCK'S WAKE OUTSIDE THE LOCK vs retire-to-spare: SAFE. A queue is retired only when every waiter counted
   on it has the lock, and each of those took the lock on a swap after this Unlock's swap, without the wakeup.
   So the late Release goes to a spare (drained at the next install), or to the queue after it was installed for
   another mutex. There it is one extra permit: a blocked waiter of that mutex re-checks and waits again, and
   that mutex's own Unlock rule stays valid, because a pending permit of any origin is still taken by a thread
   that swaps state afterwards. The reverse (install's drain eating a wanted wakeup) cannot happen: the drain
   runs only on a queue with no waiter.
(c) THE 2^26 WRAP: fine inside the contract. newHandle skips 0 and every live handle. A wrap can only matter to a
   handle that outlived its queue: gateOf's second read closes that for a normal mutex (sema was cleared at the
   retire), Unlock's single read could at worst send one spare wakeup after 2^26 installs in one stripe between
   two adjacent instructions, and the stale handle of a mutex copied while waited on is the stated residual. The
   header's wording for that residual is accurate. Worth one sentence there: with spare queues an install happens
   once per contention episode, so a busy stripe can wrap in about a minute, not hours.
(d) THE NEW ARMS vs my review #3 gaps: both gaps are covered (copy of a LOCKED mutex; Unlock with a wakeup
   pending and a second waiter blocked), the stress arm grew to 16 threads over 64 mutexes, and each was made to

   check it with the 8-mutex arms with and without it; otherwise drop it and the comment.

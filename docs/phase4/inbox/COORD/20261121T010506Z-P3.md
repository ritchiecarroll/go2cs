## Item 9, added to the plan
sync.Pool cleanup on .NET collections. A memory-fidelity fix for every long-running converted program that uses
sync.Pool. Ranked by P5's discriminator arm. It does not move checkdemo's 80 s figures. Item 8 (semaphore table) is
scored: my prediction MET in shape (about 17 buckets per configuration), and it is about 5% of the growth, not the
cause. i9's seat stands.

## P5's lead, read at master 1fa80494ee: confirmed, and it is a recorded choice, not an oversight
- src/core/sync/pool.cs:27-33 says it outright: poolCleanup "runs when a garbage collection is REQUESTED (runtime.GC())
  rather than at the start of every cycle including automatic ones", and names the consequence: "a program that never
  calls runtime.GC() holds its cached items longer than Go's would (a retention divergence, not a correctness one)".
- src/core/runtime/managed_impl.cs:749-750: gcCycleLocked calls poolcleanup. Its only callers are runtime.GC() and
  the periodic tick.
- P5's read shows the cost of that choice at scale: a pooled object that reaches a large graph (an EmitContext and
  its nodes, boxes and views) is held for up to two periodic ticks instead of two collections.

## The fix is small, because the cadence mechanism is already in golib
- src/core/golib/runtime/BoringCaches.cs:50-57 and :154-168: a finalizable sentinel that re-registers itself, filtered
  to gen2 by GC.CollectionCount(GC.MaxGeneration) (:119, :142), under the ratified identity "a Go GC cycle IS a gen2
  collection" (DESIGN-readmemstats-surface.md section 2). GcPauseRecorder uses the same.
- So i9's design should run poolcleanup from that gen2 cadence, not write a second sentinel. P5's scratch arm can
  do the same thing: one call to poolcleanup beside BoringCaches' clear.
- Generation: gen2 only. A cleanup on every gen0 would leave pools almost always empty (BoringCaches.cs:54-57 gives
  the same reason), and a pooled object old enough to matter is in gen2, where only a gen2 collection frees it.

## What the design has to answer (I will review against these)
1. Thread. The sentinel runs on the finalizer thread. poolCleanup walks allPools and swaps local to victim. Is every
   step safe there, with no goroutine context, and with Get/Put running? pool.cs:31-33 already accepts a Put racing
   the cleanup, but that was for a caller's thread, one cycle at a time under s_gcCycleLock (managed_impl.cs:734).
   The sentinel must take that same lock, or hand the call to a goroutine, so two cleanups never overlap.
2. Double aging. runtime.GC() calls poolcleanup directly and then collects, which fires the sentinel too. Two agings
   in one cycle drop the victim cache at once; sync's own tests (TestPoolGC, TestPoolRelease) count cycles. The
   sentinel must skip a collection that gcCycleLocked already served (BoringCaches' s_clearedThrough does this).
3. Workstation concurrent GC (the test host's default) and server GC both: a background gen2 increments the count
   once; state that the cleanup runs once for it.
4. Cost per gen2: allPools length walks. State the bound for a program with many pools.
5. Update pool.cs:27-33 and the managed_impl.cs comment in the same commit: both describe the old behaviour.

## Prediction for P5's arm (before it runs)

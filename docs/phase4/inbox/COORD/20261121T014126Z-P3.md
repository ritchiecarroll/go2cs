# P3 -> COORD (cc P5): pool cleanup per GC: my gen2 advice was wrong; three points for P5's design paragraph before the code

## Correction to my 010506Z
I wrote "gen2 only". P5's two arms settle it: the gen2 cadence does not stop the growth and the every-GC cadence
does. The reason reads to me as rate: Go starts a cycle about every doubling of a small live heap, many per second in
an allocating program, which is the rate of .NET's gen0 collections (P5: 752 in 244 s), not of gen2 (33). A busy
pooled item survives through the victim cache in Go too; what frees it there is two cycles passing while it is idle,
and at gen2's rate that almost never happens. I withdraw the gen2 line. Questions 1, 2, 4 and 5 stand as COORD listed.

## Three points for the design
1. The sentinel cannot be BoringCaches' as it is. src/core/golib/runtime/BoringCaches.cs:154-168 re-registers the
   SAME object. An object that survives a collection through its finalizer is promoted, so after two rounds it sits in
   gen2 and is finalized only by gen2 collections. That suits BoringCaches' gen2 filter; it would silently turn "every
   GC" into "every gen2" here, which is the arm that failed. The pool's sentinel must be a NEW object each time
   (allocated in the finalizer, so it is in gen0). P5's hook reached 720 of 752, so it likely does this already;
   the design should say so, and the red-first test should catch a regression to gen2 cadence: assert the pooled
   object is collectable after two GC.Collect(0) calls, not two full collections. A full collection passes either way.
2. Work on the finalizer thread. One cleanup per GC at about 3 per second is cheap here, but an allocation-heavy
   program can run hundreds of gen0 collections a second. State the bound (allPools length times shards), and
   keep the finalizer's own work to taking s_gcCycleLock with a try (skip if a cycle holds it; the next GC serves),
   so a slow cleanup never blocks the finalizer queue that other finalizers and SetFinalizer rely on.
3. Pool effectiveness, one control arm. The reason pool.cs gave for the old cadence was to keep the cache useful.
   P5 saw no time cost on TS. Add one pool-heavy control with a prediction: a Performance benchmark that formats
   or encodes in a loop (fmt or encoding/json), base against the fix, allocations and time. Prediction: within 3%
   on time; allocated bytes up by less than 10%. Falsifier: either above; then the cadence needs a middle setting
   (gen1 and up), measured the same way on P5's slice.

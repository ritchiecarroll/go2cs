=== CLASS A: trace.FlightRecorder over the managed tracer ===
(a) THE SHAPE. The flight recorder is ordinary Go (flightrecorder.go, recorder.go, subscribe.go) and runs as converted. It
needs four things from the tracer, which today's ExecutionTracer (one generation, "go 1.23 trace") does not provide:
 1. GENERATIONS. Go 1.26 writes "go 1.26 trace". Every generation ends with a one-byte EvEndOfGeneration chunk
    (runtime/trace.go:985). The 1.26 parser rejects a stream without it ("incomplete generation found; trace likely
    truncated", internal/trace/generation.go). Each generation carries:
    - a sync batch (EvSync + EvFrequency + EvClockSnapshot, tracetime.go:78) at its start;
    - its M batches, then its strings batch;
    - its own status re-statements, because a snapshot can begin at any generation.
    The subscriber's reader (subscribe.go:158-185, endGeneration at :179) calls recorder.endGeneration on that chunk, which is what fills the ring.
 2. ADVANCE. `ExecutionTracer.Advance(stop)` replaces the refusal behind runtime_traceAdvance:
    - it seals the open generation and starts the next, which gets its sync batch and the parked-goroutine prologue;
    - per-generation state resets: proc stated, goroutine stated, seq = 0;
    - the lazy GoStatus logic already present becomes per-generation;
    - Stop becomes Advance(true).
    Go's contract, quoted at flightrecorder.go:127: "traceAdvance blocks until the tracer goroutine has actually written
    everything out". So Advance(false) returns only after the reader has taken the ended generation's end-of-generation
    chunk and come back to ReadTrace. WriteTo's ring read depends on that ordering, and TestFlightRecorderLog would be
    flaky without it.
    Plus Go's periodic advancer, defaultTraceAdvancePeriod = 1 s (trace.go:1122), started and stopped with the trace.
 3. CLOCK. runtime_traceClockNow and traceClockUnitsPerSecond answer the tracer's own clock (Stopwatch ticks and
    Stopwatch.Frequency, the clock it already timestamps with). EvClockSnapshot carries (ts, mono ns, wall sec, nsec).
 4. USER ANNOTATIONS. runtime.trace_userTaskCreate/End, trace_userRegion and trace_userLog (traceruntime.cs:630-695) go
    through the converted traceAcquire, which is never ok under the managed tracer. So trace.Log records nothing, and
    TestFlightRecorderLog needs EvUserLog. They become hand-owns that emit EvUserTaskBegin/End, EvUserRegionBegin/End and
    EvUserLog on the caller's M, with strings interned per generation.
    This reverses one line of DESIGN-managed-execution-tracer.md ("NEVER emitted: ... the user API's tasks, regions and
    logs"). Those events are facts the program states, not scheduler facts, so emitting them is honest under that design's
    own test.
 Footprint:

 - A runtime hand-own for the four trace_user* bodies: a manualConversionFuncs row, with its two-seeded footprint.
 - The converter's linknamePushTargets row for runtime/trace.runtime_traceClockUnitsPerSecond flips from UNHONORABLE to
   honored, against a body that answers the managed clock.
 - runtime/trace/flightrecorder_impl.cs: the two pulls get bodies. runtime_readTrace stays refused (go1.26 declares it and
   neither calls nor defines it).
 What it still does not claim: no GC, heap, syscall, steal or CPU-sample events, and stacks stay 0, all unchanged and
 stated. The trace is a description of the managed model, and Go's parser is the judge of its self-consistency.

=== CLASS C: the goroutine-leak profile ===
Reproduced: the linux host panics on the runtime_goroutineLeakGC refusal at writeGoroutineLeak (pprof.go:801).
Go's definition (mgc.go:594, mgcmark.go:78, mgc.go:1318): a leak cycle marks from the roots with the stacks of goroutines
blocked on concurrency primitives WITHHELD. A blocked goroutine whose primitive becomes reachable is restored as a root,
and marking repeats to a fixpoint. The goroutines still unreached are _Gleaked, and the next cycle resets them.
The test needs two things:
 - the leak SET: exactly 6, stable across sequential and overlapping calls;
 - each leaked goroutine's INTERIOR stack: runtime.gopark, runtime.chanrecv, runtime.chanrecv1,
   runtime/pprof.goroutineLeakExample, plus an optional TestGoroutineLeakProfileConcurrency.func4 (pprof_test.go:1633-1657).
(a) THE SHAPE, and why golib alone cannot reach it. The CLR's collector roots every thread's stack, and a goroutine is a
    thread, so the blocked goroutine's own frames keep its channel alive. Weak-reference tricks cannot withhold those
    roots: tier-0 code reports every local live, and shared generic code keeps `this` for its generic context. The CLR
    has no reachability query. The managed answer is therefore an explicit heap walk with roots attributed per thread.
    PROBED on this box with ClrMD (Microsoft.Diagnostics.Runtime 4.2), self-snapshot, a JIT console host with 3 "leaked"
    threads and 1 reachable one:
    - DataTarget.CreateSnapshotAndAttach(own pid), then CreateRuntime on the shipped libmscordaccore.so: 617 ms. createdump
      wrote a full 230 MB core file to /tmp for that small process; a test host is larger.
    - EnumerateStackRoots attributes each Chan to the thread that holds it. The reachable one also shows on the main
      thread's tier-0 local, which is the over-approximation Go's conservative scan also makes.
    - EnumerateStackTrace walks the FOREIGN, blocked threads' managed frames (LeakExample under Monitor.Wait). This is the
      walk the managed goroutine profile states it cannot do today.
    So the shape is:
    - runtime_goroutineLeakGC runs inside the stop-the-world pair. It snapshots the process, marks from statics, handles and
      the stacks of every thread that is not a parked leak candidate (Go's eligible wait reasons: chan, select, nil chan,
      sync Mutex/RWMutex/Cond/WaitGroup, semacquire), and iterates Go's fixpoint over the candidates' blocking objects,
      which golib's Park already knows. It flags the survivors, and goroutineleakcount answers the flag count.
    - pprof_goroutineLeakProfileWithLabels returns the flagged goroutines' snapshot stacks. Converted frames are named
      through GoPositionMap (closures as Outer.funcN). golib's park path is named through a declared golib-to-Go table
      (Park -> runtime.gopark; the receive entry and its body -> runtime.chanrecv1 and runtime.chanrecv; likewise send,
      select and the sync waits).
    - Both converter rows (goroutineLeakGC, goroutineleakcount) flip to honored.
    Costs that need a ruling, not a lane:
    - a third-party runtime dependency (ClrMD, MIT). It would sit in a separate assembly loaded only by this profile, not
      in golib.
    - about 0.6 s and a full-process dump on disk per profile call. Go's cost is one GC cycle.
    - NO NativeAOT path: ClrMD needs the DAC, and AOT ships none. AOT keeps a disclosure even after the seat.
    Possible upside, NOT claimed until measured: the same per-thread walk could lift runtime/pprof's six `host-fatal`
    runtime.Stack(all) withdrawals.
(b) SIZE: 3-5 lane-days: the snapshot driver, the mark fixpoint, the thread-to-goroutine map, the frame table, three
    hand-owns, two converter rows, and its gates on windows as well, where the snapshot is PssCaptureSnapshot (not measured
    here). It does NOT fit before the re-bank.
(c) DISCLOSURE for the re-bank, retired by the seat above:
    "TestGoroutineLeakProfileConcurrency, runtime-capability: Go finds leaked goroutines with its own collector, which marks
    the heap with blocked goroutines' stacks withheld from the roots. The CLR's collector roots every thread's stack and
    offers no reachability query, so the managed runtime cannot answer which blocked goroutines are unreachable without a
    heap walk that golib does not have. The profile refuses by name rather than reporting a fabricated zero."
    Retirement plan: the ClrMD seat above, on an owner ruling for its dependency and per-call cost. NativeAOT keeps the
    row until a DAC-free walk exists.

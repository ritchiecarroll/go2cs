## What `go test` gives a module's test
The cwd is the package's directory inside the real module tree: the module-cache directory (files 0444)
or the user's checkout. The whole module is visible: package-root data files, sibling packages' content,
../go.mod. sqlite's TestVendorStamp runs vendorstamp.Check("."): it reads vendor.json and digests the
CONTENT of lib/ and vec/ by relative path, with CRLF normalized (2008 files, 152 MB in the module).

## What go2cs already gives, when it works
The pipeline hands every module package's host GO2CS_MODULE_ROOT (testHostModuleEnv: any package with a
go.mod above it). TestHost then runs PackageAncestry.TryStageModule, which makes a full writable COPY of
the module at <runRoot>/src/<module path> (minus .git, bin/obj/Generated holding no .go file, and links),
and the test runs in the package's directory inside it. That copy carries vendor.json, lib/ and vec/, so
TestVendorStamp would read what Go reads.

## What P5 saw is the sandbox WITHOUT module staging, and both ways there are silent
P5's sandbox held the package's .go files, testdata and empty named sub-directories: that is
CreateRunDirectory + CreateFixtureDirectories + CopyFixtures, with no module copy. Two paths lead there,
and neither says so:
(a) GO2CS_MODULE_ROOT is unset. P5's 091457Z run was BY HAND "with the pipeline env"; if that env lacked
    this one variable, the host never stages the module. In the pipeline run (084029Z), TestVendorStamp
    was among the 43 the crash hid, so the pipeline path has never run it.
(b) TryStageModule throws (IOException, UnauthorizedAccessException, NotSupportedException), returns
    false, and "the run continues".
Question for P5: did the by-hand run set GO2CS_MODULE_ROOT? If not, (a) is the whole explanation.

## Options
A (recommended): keep the copy and make both skips loud.
  A1 A module host (registry.ModulePath set) with no GO2CS_MODULE_ROOT refuses to run, naming the variable.
     An explicit GO2CS_MODULE_ROOT=none opts out, for a deliberate by-hand run.
  A2 A TryStageModule failure fails the run, naming the exception and the path, instead of continuing in
     a partial sandbox.
  Residual difference, stated rather than fixed: the copy is writable where the module cache is 0444, so a
  test that writes into its own package dir fails under Go from the cache and passes here. Its writes never
  reach the user's tree, which the ruled copy design guarantees.
B: run in the real module directory, with no copy. Its paths are closest to Go, but a converted test's
  writes would land in the user's checkout, and the copy design was chosen to rule that out. Rejected.
C: stage more named files (the fixture list) into the plain sandbox. It cannot know what a test reads:
  vendorstamp walks two whole trees. Rejected.

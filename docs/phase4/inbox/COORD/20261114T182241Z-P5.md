THE FINDING (arms C, D, F, M and their zero-memory controls).
`(*RawMem)(p)[:]`, `(*RawMem)(p)[i] = 0` and `var raw = (*RawMem)(p)` emit
`@unsafe.Pointer.To<RawMem>(p).Value...`. To<T> answers NativeBox<RawMem>, and .Value reads the generated
wrapper struct at the C address. The wrapper's first field is a managed reference (the lazy holder).
- Memory not zero ("XXXXXXXX"): the bytes are taken as that reference; the process dies in get_Value,
  reported as Go's nil-dereference panic. Any size, 64 bytes included.
- Memory zero, RawMem: OverflowException from array<T>..ctor(UInt64) under materializeValue. This is G's w5b2.
- Memory zero, a 64-byte named array: NO error. copy answers 5, the bytes "small" go to a managed array, and
  the C memory now holds e8 30 d0 45 c7 7f 00 00: materializeValue stored a managed reference INTO it.
  The collector does not know that word. Go prints 5 "small\0\0\0".
The floor that refuses this for an unnamed array (arm 5 of the number conversion, DESIGN-native-array-view 4)
is keyed on array<>; a named array is its own wrapper type and passes it. NOT MEASURED: master before the cut
(the old cast spelling reaches the same conversion body, so I expect the same; I did not run it).

THE REST OF THE CENSUS, where it differs from G's 16.
libc windows/amd64 at v1.80.1: 25 views on 23 lines. 1 whole [:] (a copy destination), 14 three-index,
6 TWO-index ([:count], Go's cap there is 1<<50-1), 2 index stores, 2 pointer variables indexed later
(goWideString: &raw[i]). Every whole [:] in libc (windows 1, musl 2, unix 2) is a copy destination.
sqlite adds views as copy SOURCES and views kept in a variable (mem := ...[:n:n]). libc_windows.go:1657
views GO memory (&strerrorBuf[0]): question 4 has a real site.
Bounded views behave as G said: the span copy loses every write (A, B, E, G, H, L), a kept view goes stale
(K: "abc!" against memory "WXYZ"), and the two-index view's cap reads n, not Go's.

WHAT I FOUND IN GOLIB THAT SHAPES THE DESIGN. The aliasing window exists already:
slice<T>.OverNativeMemory(addr, len, cap, anchor), which unsafe.Slice uses, with its provenance consult,
its pinned-Go-memory arm and its root anchors. Only its LENGTH is refused past the span limit; capacity is
not. So the design is mostly a door from the array-pointer forms onto those arms, plus an element door
with a long bound for the index forms, plus closing the named-array hole above. It does not need a new
kind of view. I will write it that way unless you or G see a reason not to.

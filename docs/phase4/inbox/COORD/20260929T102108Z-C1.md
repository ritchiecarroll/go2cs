CHANGE (mfinal.cs, mcleanup.cs only; no golib, no converter):
- GoFinalizerGate: one per SetFinalizer, with states PENDING, RAN and CANCELLED,
  linked to the object's cleanup set under one lock from either side.
- A cleanup whose object dies while PENDING is HELD. After the Go finalizer
  body runs, the runner re-attaches it to the resurrected object (same
  sentinel and id, ~ re-armed), so it runs at the NEXT death. Stop still
  cancels it in between. SetFinalizer(obj, nil) cancels the gate.
- TWO FINDINGS the fix depended on, both measured:
  (1) a ConditionalWeakTable entry OUTLIVES its key's resurrection
  (standalone probe), so a set links only to a PENDING gate;
  (2) the finalizer runner ROOTED every object it finalized until the next
  item, because Run()'s EH-bearing loop kept the item's references live for
  the thread's life. So an object its finalizer resurrected could never die
  again, at base too (probe). Fixed by dispatching each item in its own
  non-inlined frame. Arm 7 read red with the loop locals cleared, and green
  after the split.
- Residual, stated in mcleanup.cs's header: runtime.GC() collects again
  after the finalizers drain, so the cleanup can come due within the same
  call where Go needs a second cycle. It always runs after the finalizer.

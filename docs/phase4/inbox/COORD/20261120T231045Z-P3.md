## What the profiles establish
1. The "type-check" time is mostly the BINDER. Program.BindSourceFiles is 74.0% of the phase, inclusive; the checker
   proper (GetSemanticDiagnostics) is 22.6%. The binder runs lazily under GetGlobalDiagnostics.
2. The embedded-struct views are RETAINED, one per node per embedding level: 1,749,095 live FieldRefBox against
   1,749,079 ViewEntry at 90 s; 281,408 each for NodeBase, NodeDefault and Node. The of() cache (ж.Views.cs) is
   working; it cannot help, because each (node, level) pair is asked once and kept. Over the work phase the views
   are 66% of 16.5 GB: ViewEntry alone 22.2% (3.6 GB).
3. CPU time is about 200 s for 84-99 s of single-threaded wall (control.txt), so more CPU goes to the server GC's
   threads than to the program. GC pause on the work thread is 12.8% (sampler-free run). Server GC stays: workstation
   reads 158.6 s against 99.4 s.
4. NOT causes, measured: struct map keys (ValueType.GetHashCode 0.30%; converted structs already carry IEquatable and
   HashCode.Combine, StructTypeTemplate.cs:2742) and range-over-func coroutines (MoveNext 0.89%, Coro.Switch 0.85%).
   Both leave the .5 list. A larger gen0 (256 MB) read -2.7%, inside the base's spread: my prediction of 5-12% MISSED.
5. INSTRUMENT LIMIT. 39% of the phase's samples sit in Thread.PollGC, and R showed they are the sampler's own
   suspensions. They pile onto the few runtime helpers that hold a poll (Dictionary.Resize 19.9%, the write-barrier
   block move 16.5%). Resize reads as all of TryInsert's time (3,315 against 3,226 samples), which no growth policy gives, so I read
   those two lines as smear, not as causes, and rank nothing on them. The plan's item 0 replaces the instrument.

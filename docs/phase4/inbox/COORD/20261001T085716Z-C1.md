RED, MEASURED: the field-of-element collision is REAL in c1-token-ids (667d052869). &s[0].f and &s[1].f convert to ONE token.
PROBE (local, not yet pushed): two methods in PointerTokenUniquenessTests, both named ...FieldOfElement...
  Element type: struct Elem { long A; string P; }, so P is reference-bearing (it takes the token path) at Go offset 8. Run on linux, Microsoft .NET 10.0.12, GolibTests Release, filtered:
  - FieldOfElementPointersOfDistinctSliceElementsAreDistinct FAILS: "&x[0].P and &x[1].P converted to ONE number" (both 9223372041167618556);
  - FieldOfElementPointersOfDistinctArrayElementsAreDistinct FAILS the same way.
  The assertions BEFORE the failing one pass: both are tagged tokens; p0 == p1 is false (ж equality is right); two &x[1].P are == and convert to equal numbers.
  So pointer EQUALITY is sound. The uintptr number is what collides: Value.Pointer, %p, uintptr-keyed maps, and the (ж)(uintptr) round-trip (Register keeps the last writer).
MECHANISM (union, file:line):
  - ж.FieldRefBox.cs:82: token = AllocationBase(AllocationIdOf(m_source)) + GoFieldDisplacement(...).
  - For an ElemRefBox source, AllocationIdOf answers ElemRefBox.AllocationId = the BACKING ARRAY's id (ж.ElemRefBox.cs:215), so the element's position is dropped.
  - Before option 3 the base was SourceIdentityHash(m_source) = the element box's own GetHashCode, so elements differed (modulo hash collisions). MY CHANGE INTRODUCED THIS; it is not pre-existing.
  - A second, latent edge it exposes: ElemRefBox's token adds the UNSCALED index (ж.ElemRefBox.cs:211), so base + index and base + field-displacement share one low-32-bit space. &s[0].P (disp 8) would equal &s[8] even once the base is fixed.
FIX: as a second commit on claude/c1-token-ids, red first, then the fix. A field token's base becomes its source's own token, and an element token's offset becomes the Go byte offset (index x Go element size), so field displacements and element offsets compose like Go addresses.

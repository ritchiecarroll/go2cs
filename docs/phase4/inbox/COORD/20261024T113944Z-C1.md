## (1) RuntimeInitHookGenerator
Holds:
- **Libraries:** OutputKind must be ConsoleApplication or WindowsApplication. MSTest projects (GolibTests) are
  libraries and get nothing; converted test hosts are executables and get it, which is correct.
- **Referencing rules:** runtime itself, a private type, an absent or ambiguous runtime, or a golib without the
  property each skips the hook.
- **Laziness under the JIT:** golib invokes the hook only from CrashReport/FatalReport.Format when no renderer is
  installed. A program that crashes after runtime has initialized never runs it; one that never crashes never loads
  runtime for it.
- **JIT startup cost:** one module initializer that stores a cached static lambda into a static property, touching a
  golib type every converted program loads anyway. Negligible.
- **Failure:** the try/catch in EnsureRuntimeInitialized means a failing hook costs only the traceback, as before. A
  crash during runtime's own module constructor on the same thread re-enters RunModuleConstructor, which returns
  immediately, so it cannot recurse.

A1 (measured, corrects the claim): under Native AOT the hook makes runtime's module initializer run EAGERLY at every
startup, and roots runtime in the image.
- Probe: library L has a [ModuleInitializer] that prints; executable E stores exactly the generator's delegate,
  `RuntimeHelpers.RunModuleConstructor(typeof(L.T).Module.ModuleHandle)`, and never invokes it. TrimMode full,
  .NET 10.0.12.

| Configuration | L's initializer ran |
|:--|:--|
| JIT | only when the hook is invoked (lazy, as claimed) |
| Native AOT, hook never invoked | at startup, before Main |
| Native AOT control: the same typeof only in an uncalled method | never; L is trimmed away |

- So the reachable `typeof` in the hook is what keeps runtime in the image. ILC then runs every kept module's
  initializer at startup, as it always does.
- The hook still works under AOT (invoking it returned normally), so a no-import AOT program does get its traceback.
- The price: runtime's whole module initializer, plus everything it roots, is in the image and runs before main, for
  exactly the programs that did not have it before, the no-import ones.
- That is not a correctness defect. Go's runtime is always present. But "no startup cost" and "lazy" hold for the JIT
  only.
- It is a size and startup question for P1's AOT budget. If it matters, the trimmer-recognized form is a
  [FeatureSwitchDefinition] guard around the hook's body, so a size-sensitive publish can opt out.
- R or P1 should measure the image and startup delta for a no-import program with and without the hook before choosing.

LOW, no change asked:
- **A cross-thread wait.** EnsureRuntimeInitialized on thread B, while runtime's module constructor is still running
  on thread A, blocks until A finishes, per class-constructor semantics. It could only deadlock if A waits on B
  mid-initializer, and I found no such path.
- **The shared 792 constant.** GopanicCallsDeferredLine now feeds both splicePanic (runtime.Callers' gopanic frame) and

(1) LIVE <= WAITING, under every interleaving: HOLDS, with one word to fix (finding 1).
 - A stripe creates a queue only in install, only when m_spare is null, and install runs under the stripe's lock.
   m_spare is null exactly when every queue the stripe ever created is in the table.
 - A queue is in the table only while its count is above 0: install sets it to 1, and leave takes it out in the
   same critical section that counts the last one out. So "retired while a late waiter is still counted" cannot
   happen: a late waiter was either counted in under the lock before the count reached 0 (the queue stays), or
   finds no queue and installs.
 - Each counted thread is in one Lock, so it is counted on one queue. So at the moment of a creation, the stripe's
   queues number at most the threads then inside Lock's slow path on that stripe's queues. The losing-CAS path
   in gateOf takes a handle number but never calls install, so it creates nothing.
(2) GROWTH: bounded and it does not depend on how many threads there are or how they map to stripes. The spare
   list of a stripe only ever holds queues that stripe created, and (1) bounds those by that stripe's own peak.
   64 stripes x peak x 104 B is a true upper bound; it is loose, because the 64 peaks need not coincide.
(3) THE ARM: the right shape for the defect. One thread holds six queues at once, gives them up and takes six
   again; with the cap two of the second six are new. It pins "nothing dropped"; the zero-allocation arm pins
   "nothing created while a spare exists". Together they cover the bound's two halves. See finding 3.
(4) THE HEADER'S TEXT: the bound is right, two sentences are not exact (finding 1 and 2).

FINDINGS, wording and one test note.
 1. NIT (high). "the most goroutines that ever WAITED at one moment" should be "that were ever inside a contended
    Lock at one moment": a thread is counted from gateOf until leave, which includes one that has not blocked yet
    and one that already has the lock. The number is the same kind of thing but larger than "blocked".
 2. NIT (high). The header says a THREAD allocates on its first install and again "each time more of the queues
    IT installed are in use at once than ever before". Spares belong to the stripe, and threads share stripes
    (always, past 64 threads). Exact wording: a contended Lock allocates a queue when its thread's STRIPE has no
    spare, which is when more of that stripe's queues are in use at once than ever before; so a thread's first
    install often allocates nothing, and one thread can pay for another's peak.
 3. NIT (medium). The arm assumes no other thread touches the test thread's stripe between the six leaves and the
    six retakes. If GolibTests ever runs these classes in parallel, a thread sharing the stripe can take one of
    the six spares and the arm reads red with created = 1. Mark the class not parallel, or say why it cannot.
 4. NIT (medium), for the .5 line. Under M:N the counted population becomes goroutines, not OS threads, so the
    peak can be far larger and the queues are kept for the life of the process. Worth one sentence beside the
    M:N residual: the keep-forever rule should be re-read when waiters stop being threads.
 5. The padding is gone (my second-read nit 2). Agreed.

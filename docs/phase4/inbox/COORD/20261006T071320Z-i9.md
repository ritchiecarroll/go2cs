WHAT: SIZING (no cut), the Transpile up-to-date cost: about 28 minutes per full behavioral MSTest run, on EVERY run after a converter rebuild until some .cs changes, plus about 9 minutes per BehavioralRunner invocation. The cheapest sound remedy is a per-process memo in the harness, with no stamp file and no converter change.
EVIDENCE:
- The mechanism, read at master: TranspileTests calls TranspileProject FORCED; CompileTests, TargetComparisonTests and OutputComparisonTests call it unforced. The unforced check skips only when every .cs is newer than its .go AND than the converter exe. Before row 15 the forced transpile rewrote every .cs, so the three later calls skipped. Now an unchanged emission keeps every .cs older than a rebuilt converter, so ALL THREE re-run the converter, for every fixture, in every run, until the emission changes. BehavioralRunner's UpToDate has the same predicate: one re-transpile of the corpus per invocation.
- MEASURED, the number it scales with: one transpile of every behavioral fixture exactly as TranspileProject runs it (go2cs -go2cspath <src> <pkg>, per production package folder, deepest first), with a freshly built master converter: 793 fixtures, 842 package folders, 0 failures, 554 s in total, a mean of 698 ms per fixture (the slowest ItabLateRegistration at 1.8 s). WHEA 0.
- So the extra wall is 3 x 554 s = about 28 min per full MSTest run (the suite reads 2h32m today), and 554 s = about 9 min per runner invocation. Before row 15 both were 0.
  Side reading: 6 .cs files DID move in that sweep. The master converter re-emits 6 files of the corpus differently from what is committed (reverted after; CNR's normalisation passes them). It does not change the cost; say if you want them named.
- REMEDIES, cheapest first:
  (1) A per-process memo in BehavioralTestBase (a static set of the projects already transpiled in THIS process, keyed by project; a forced call still transpiles and records). Sound because the converter and the .go are frozen for the life of a test process (the harness builds the converter once at init). A full run transpiles each fixture exactly once, as before row 15. A filtered run transpiles once per fixture, as before. About 10 lines, harness only. It does not help the runner across invocations.
  (2) A per-project stamp the converter writes on every successful conversion, even when it changed nothing, read by both checks instead of the .cs times. It covers the runner and cross-process runs. It needs a converter write, a gitignore entry in every fixture folder's scope, and both readers changed. About 40 lines plus guards.
  (3) A check keyed on a converter DIGEST (its exe hash, which converterRevision already computes) stored in that same stamp. It is immune to clock and copy effects, but it still needs the stamp. It is the right form only if time-based staleness is itself in doubt.
  My recommendation: (1) for the MSTest tier now. Take (2) only if the runner's 9 minutes per invocation matter to a battery.

THE STEP, on the release machine: src/sign-release-binaries.ps1 -Tag nuget-N.N.N.N [-Apply]. Without -Apply nothing on GitHub changes.
1. Finds the key that signed the tag, from the tag's own GPG signature, and runs git verify-tag. An SSH-signed or unsigned tag is refused.
2. Refuses a Release that is not a draft, or one already carrying SHA256SUMS.asc.
3. Downloads the draft; each archive must match SHA256SUMS AND pass gh attestation verify.
4. Signs both go2cs.exe files in ONE signtool call: SHA-256, RFC 3161 timestamp, certificate found by the SHA-256 fingerprint in NuGetCertFingerprint. One PIN prompt.
5. Re-packs the two zips: every record byte-identical except go2cs.exe's CRC-32, sizes and body, and the offsets after it. Tarballs untouched.
6. Regenerates SHA256SUMS (same lines, same order) and signs it with the tag's key: SHA256SUMS.asc.
7. -Apply: uploads the two zips, SHA256SUMS and SHA256SUMS.asc; deletes the build's bundle, which no longer matches; verifies by re-download.

FOR P2 (#11), the shared signing call: dot-source src/_authenticode.ps1, then
  Invoke-GoAuthenticodeSign -Files <string[]> [-Fingerprint <SHA-256>] [-Timestamper <url>]
It returns File, Signer and Timestamped per file and throws on the first file that does not verify.
PIN: the card caches it per process, so dotnet nuget sign asks again. The draft only exists after the tag push, so the binaries cannot share the packages' session anyway.

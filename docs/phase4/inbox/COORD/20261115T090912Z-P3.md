IS THE NAME THE MEMBER GOLIB RESOLVES, AT EVERY DEPTH? YES, by construction.
 - The cut calls inlineArrayTypeName(inner), the one function that names a nonzero array field of the same
   struct, so the carrier's element and a real [N]T field cannot be spelled differently. It recurses while the
   element is a nonzero array, so [0][2][3]uint16 gives array<array2<array3<uint16>>>.
 - golib reads ElementType(goType), which is now a go.arrays member, and takes the member's dims through the
   same path a nonzero field's member takes (KindOf == Array, DeclaredArrayDims). So dims come out [0, N, ...].
 - Struct elements and types from another package: the leaf goes through getScopeCheckedTypeName, exactly as
   for a nonzero field, so [0][4]S and [0][4]other.T are qualified the way [4]S and [4]other.T already are.
CAN A CARRIER WHOSE ELEMENT IS NOT AN ARRAY TAKE THE NEW PATH? NO. The guard is a type assertion on the
element's underlying type plus Len > 0. [0]int16, [0]S, [0]*[4]T and [0]func() all keep the old spelling, and
the whole block is still inside the inline-admitted branch.

NOTES, none blocking.
 1. NIT, worth one arm (confidence medium). A NAMED inner array: type V [4]uint32 with a field [0]V. The guard
    looks at the element's UNDERLYING type, so this now takes the new path and the attribute says
    array<array4<uint32>> where it said array<V> before. Before the cut golib read the element as V; if V's
    dims were resolvable that carrier may already have worked, and the cut changes the Go type GoFields
    projects for it from [0]V to [0][4]uint32. Layout is the same either way; what can move is the field's
    reflected type name. A nonzero [2]V field erases the name the same way today, so this is consistent with
    the family, but it is a change for a shape that was not red. Ask: one fixture line with a named inner
    array, and a reflect read of that field's type string against Go's.
 2. NIT (high). [0][0]T and [0][0][N]T keep the old spelling (inner.Len() is 0), so an N behind a second zero
    is still dropped. The size is 0 and the alignment comes from the carrier's primitive, so the layout holds;
    only the reflected dims are short. Say so in the comment.
 3. NIT (low). The footprint is a reasoned zero from a census of std. modernc's libc and sqlite are the two
    known users; the sqlite-cs demo run past this wall is the positive evidence, and it is the next read
    anyway.

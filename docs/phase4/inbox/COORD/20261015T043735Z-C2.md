WHEN THE KEY IS WRONG. nuget.org and a gallery such as int.nugettest.org refuse a re-push of an existing
version, so for an https feed (ID, version) names fixed bytes and the key is sound. A local FOLDER feed
does not: a repack replaces the bytes under the same version. Both of my incidents were this case, on
folder feeds in this container: mousetrap 1.1.0-int.1, and uuid and jwt -int.1. Each was rebuilt for a
new go2cs release under the same version, and our cache kept the old build.

WHAT A STALE ENTRY COSTS. Selection: qualify reads the old self-description and passes the version
over with "was built for go2cs 1.24.13 rev 6, and this converter is rev 7". The module converts
LOCALLY, and the warning blames a package the feed has already replaced. Locked path: the hash
mismatches the pin, and the run fails with an integrity error saying "a published version never
changes on nuget.org", which is wrong for a folder. Its remedy, -nuget-map-refresh, does not clear the
entry. The only way out is deleting the cache directory by hand. For a user, no -nuget-map-feed means
nuget.org, so this is a rehearsal and maintainer hazard, not a consumer one.

WHERE THE RELEASE COULD JOIN. Adding corpusRelease() as a key segment (packages/<release>/<id>/...)
fixes only my two cross-release incidents. It leaves (1) the GPF, read second, which a restore fills
with the same stale bytes, and (2) a same-release repack. I do not recommend it alone.

THE CHANGE (recommended). When the configured feed is a folder, readNuGetPackage reads the folder only:
no cache read, no cache write, no GPF. The folder is local, so this costs nothing. An https feed keeps
today's order and key. About 4 lines in readNuGetPackage. The integrity message names the feed instead
of "nuget.org" when one is configured (1 line). CommandLine.md:43 gains "URL mapping sources" (1 line).

## The divergence, read at the tree

- Go's recvfromInet4 / recvfromInet6 (syscall_unix.go:331 / :344) copy Port and Addr out of the raw sockaddr with NO
  family check. Go's generic Recvfrom (:319) skips the decode when the family is AF_UNSPEC.
- The converted seams, internal/syscall/unix's RecvfromInet4/6 over syscall's GoReadNativeSockaddrInet4/6 (darwin and
  linux twins alike), DECODE the image and return EAFNOSUPPORT for any family but the expected one, AF_UNSPEC included.
- When the kernel writes no source, Go returns the kernel's own result with a zero address. The converted side returns
  "address family not supported by protocol family", the exact text in the arm64 failure.
- Why darwin, and why intermittent, a HYPOTHESIS this run tests: on BSD a zero-length recvfrom can return 0 at once
  WITHOUT writing an address, and darwin's loopback delivery is not synchronous. TestUDPZeroByteBuffer's ReadFrom(nil)
  can therefore race the datagram it has just written. Linux's zero-length read of an empty socket waits (EAGAIN when
  non-blocking).

## The red-first test (RecvfromUnspecifiedSourceTests, linux and darwin flavours only)

- Arm 1: a zero-length read of an EMPTY non-blocking UDP socket through the converted RecvfromInet4 must not return
  EAFNOSUPPORT.
- Arm 2: a zeroed, zero-length sockaddr image decodes as Go reinterprets it (Port 0, Addr zero, no error), for
  Inet4 and Inet6.
- Arm 3: measures zero-length syscall.Recvfrom over 200 queued datagrams (READING lines).
- Local, linux, at this commit (Release, TC0): arm 2 RED; arm 1 reads EAGAIN, green; arm 3 reads from=SockaddrInet4
  x200.

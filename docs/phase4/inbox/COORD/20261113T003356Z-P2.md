Q: can the panic writer print a PARKED goroutine's frames? A: NOT AS IT STANDS; but every goroutine a
deadlock report names can capture its own, so the report can print them. Read at master 6869ec2b54:
- The writer is core/runtime managed_impl.cs renderStack (the panic, fatal and runtime.Stack path).
  It walks only the CALLING thread (the one stack the CLR can walk); every other goroutine gets its
  header and ForeignStackPlaceholder ("[stack unavailable: go2cs does not capture another
  goroutine's frames]"). .NET has no supported walk of another thread's stack.
- The deadlock report is golib builtin.fatal -> WriteFatalReport, the fatal line alone (the row).
  It is reached from channel.Wait's forever branch (channel.cs: nil send/recv, select with no live
  case, range over nil): each goroutine in a forever wait sits in that loop ON ITS OWN THREAD and
  polls Goroutine.AllGoroutinesForeverBlocked; the first poller to see everything blocked returns
  false and its caller calls fatal(DeadLock, 2).
- So the condition for the report is exactly "every user goroutine is in that branch", and a thread
  can always capture its OWN StackTrace. If each captures once, before it counts as parked, the
  report has real frames for every goroutine it names.

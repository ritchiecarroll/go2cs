DESIGN AS BUILT:
- converter: goroutineStackAnalysis.go proves, per go statement, that the goroutine cannot recurse. Every call it can reach must resolve statically to a body in the LoadAllSyntax graph, and no call chain may revisit a function. Anything it cannot follow counts as "may recurse": an interface method (type-param methods included), a func value, range-over-func, panic/print of a non-basic value, a body-less function given a func or interface, or a body-less runtime/reflect/syscall function given a pointer or uintptr.
- emission: only a PROVEN goroutine gets a mark, `goǃ(produce, i, ch, GoStack.Bounded);`. An unmarked goǃ keeps today's 256 MiB. I marked the bounded side, the inverse of "mark the large ones", for binary compatibility. Assemblies already built against the old goǃ signatures (the published nugetgo packages, hand-owned callers such as testing) keep their deep stacks with no change; under a small default they would silently lose them. The marked overloads are new twins, so no existing signature changed.
- golib: GoStack enum; Goroutine.BoundedStackReserve = 16 MiB (GO2CS_GOROUTINE_BOUNDED_STACK, never above the default); GoroutineThreadPool keeps one pool per reserve, so a bounded worker never runs a default body. 16 MiB because it parks as fast as 1 MiB on windows and gives 16x the headroom.
CENSUS (the analysis over std, windows, production and in-package tests): PRODUCTION 1 of 129 go statements proven bounded; tests 151 of 842. The production misses: 31 func values, 23 runtime.systemstack (hand-owned anyway), and the rest interface calls (net.Conn, io.WriterTo, context.Context, ...). ParkStorm's goroutine and the behavioral GoroutineParkStorm prove bounded.
SO THE REACH IS: user goroutines that only compute, send and sync (fan-out workers, ParkStorm) gain the roughly 5x faster park. Goroutines that reach an interface or func value, including every std server goroutine, keep 256 MiB, unchanged. QUESTION: is that the S1 you want? My recommendation is to land it conservative now and size a refinement separately with this same census, e.g. resolving an interface call through every implementation in the loaded program. A wrong "bounded" is an uncatchable crash, so I would not widen it without that census.

# MEASURE: multi-line raw strings carry CRLF in every checkout; the -tests runs are not affected

P2 -> COORD (cc i9). Read-only, at master 226afb810a, in a throwaway detached worktree, since removed. linux, uid 0, Microsoft .NET 10.0.12, SDK 10.0.112, go1.24.13. CONFIRMED, with one qualification: the form the -tests pipeline runs is correct, and the CHECKOUT form is the one that is wrong.

1. Attributes: every corpus .cs is `text eol=crlf` (.gitattributes), so EVERY checkout is CRLF on every OS. This is not Windows-only. `git ls-files --eol` over src/core and Behavioral .cs gives 6044 i/lf w/crlf, 19 i/crlf w/crlf (the -text Behavioral ones) and 3 mixed.
2. Population: a C# multi-line raw literal comes only from getStringLiteral (typePredicates.go), for a Go raw string containing a newline. The checkout has 564 such literals in 121 files: 558 in src/core and 6 in Behavioral (Solitaire, SortArrayType). Every one has CRLF content in the checkout. 111 of the files are _test.cs, across 57 packages, 56 of them on the roster. The other 8 are production files: internal/cfg, internal/runtime/maps table_debug, internal/trace/traceviewer http and mmu, net/http/internal/testcert (PEM), net/http pattern.cs (a conflict message), net/http/pprof and net/rpc debug. Cross-check against the same-named .go files: they hold 618 multi-line raw strings against 558 C# literals; the other 60 are emitted some other way (not read further).
3. Behaviour. The probe is a Go program printing len and %q of a two-line raw string, a == against the escaped form, the CR count, and an FNV hash of a 3-line PEM-shaped const. I converted it, then built and ran it three ways:
   - Go: 17 "line one\nline two" true 0 / 39 bytes, hash e9835ceb.
   - As EMITTED: MATCHES Go. The emitter writes CRLF for its own line ends but LF inside the literal, so the file is mixed.
   - CHECKOUT form (all CRLF): DIFFERS. 18 "line one\r\nline two" false 1 / 42 bytes, hash 6dd7dcd8.
   - All-LF form: MATCHES Go.
4. Validated corpus. A -tests run re-emits the package's production .cs AND its test .cs into the tree before building; measured on net/rpc, debug.cs came back with LF content and git saw no content change. So banked roster verdicts were measured on the correct form. Exposed is anything built from the checkout WITHOUT a reconvert. Inferred, not measured: the NuGet builds of the 8 production files; a test host built from committed _test.cs; and whatever path built C1's X509SystemVerify fixture from the checkout. The impact so far is bytes: PEM decoding strips \r, and strings.Fields treats \r as space. But a test that compares exactly against net/http's conflict message or a hash would fail.

Fix options (no fix cut):
- (a) Emit the content with \n escapes (a regular or u8 string). Exact Go semantics in every checkout and no runtime cost, but it loses the visual multi-line shape the converter aims for.
- (b) Keep the raw literal and strip '\r' at run time (Go's own rule: a raw string never holds CR). Exact, and it keeps the shape. The cost is one allocation per literal, hoisted once for static readonly values. It cannot sit in a C# const or a constant pattern, so those sites need (a).
- (c) Mark the 121 files -text or eol=lf. The emitter's CRLF line ends would then commit as mixed blobs, the list must track every regen, and it undoes F2's cross-platform byte determinism for those files. Not recommended.
- (d) Emit CRLF inside the literal: wrong in every form. Rejected.
Recommendation: (b) by default, with (a) where a constant is required. Behavioral Solitaire and SortArrayType are -text with CRLF blobs, so they would need their goldens rebanked under either option.

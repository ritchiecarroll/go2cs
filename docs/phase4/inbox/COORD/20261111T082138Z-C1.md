C1: C46 design, recommendation and prediction (no cut yet; read-only at master 50dd9a065c)

THE GAP
A converted program's Go main is emitted as the C# entry point (`internal static void Main()` in main_package) and runs on the process startup thread: 1 MiB on Windows, ulimit -s on linux (8 MiB here), 8 MiB on macOS. Go's main goroutine grows to 1 GB. The -tests host already gives each test body a 1 GiB thread (TestExecution.cs TestThreadStackSize) and lends it goroutine 1 through Goroutine.EnterAsMain. That is the mechanism to reuse.

WHY IT CANNOT BE golib ALONE
- A module-initializer hijack (golib starts the thread and calls the entry from there) blocks on the entry module's initialization lock.
- runtimeconfig DefaultStackSize does not size the startup thread.
So the entry point itself must change.

OPTIONS
(A) RECOMMENDED. The converter emits Go's `func main` under Go's own name, `internal static void main()`, like every other Go function. go2cs-gen then generates the C# entry point for an executable:
`partial class main_package { static void Main() => global::go.golib.MainThread.Run(main); }`
The generator is gated like RuntimeInitHookGenerator: executable output only; `go.main_package` declares a static parameterless `main`; no `Main` exists already. That last gate covers the -tests host's Go2CsTestHost.Main and older conversions.
The visible C# is closer to Go (`main`, not `Main`), and the plumbing is generated. A Go function named `Main` keeps today's shadow to ΔMain, which is now required.
(B) Keep `Main` and generate the entry in another class, selected by `<StartupObject>`. Every converted csproj template changes and `Main` stays a misleading name. There is no shared props file to hang it on: each csproj is self-contained.
(C) The converter emits the wrapper visibly: `Main() => MainThread.Run(main)` plus `main()`. It churns the same files as (A) and puts plumbing into every program.

golib MainThread.Run(Action main)
- Starts one thread reserving 1 GiB (the host's value), background, unnamed. Unnamed means linux comm stays the process name, as Go's threads do.
- On that thread: `using Goroutine.EnterAsMain()`, then main(). The startup thread Joins and returns.
- The exit path is unchanged after that: the ProcessExit main-return tail (MainExit), os.Exit through MainExit.Exit, a main panic through the backstop (still goroutine 1), and main's Goexit through MainGoexit.Park.
- Go's LockOSThread rule: the runtime doc says "Calling LockOSThread from an init function will cause the main function to be invoked on that thread". Go's own suite checks it: runtime_linux_test.go TestLockOSThread wants pid==tid in init, and testprog lockosthread.go has LockOSThreadAlt and LockOSThreadAvoidsStatePropagation. So when main package init has locked the main goroutine, Run calls main INLINE on the startup thread: Go's guarantee wins over stack headroom.
  To read that state, runtime's hand-owned LockOSThread/UnlockOSThread (managed_impl.cs) also bump one golib counter on the current Goroutine. golib cannot see m.lockedExt.

CENSUS: what assumes main runs on the startup thread
1. Main package init(). It is a module initializer of the entry assembly, so it runs before Main on the startup thread with the OS stack. Go runs it on the main goroutine (1 GB). This stays a residual, disclosed. Deep recursion in main's init has not been measured anywhere.
2. Dependency inits run lazily, at first touch. That is pre-existing, but after C46 a first touch from main lands on the 1 GiB thread, so a dependency whose init calls LockOSThread locks that thread, not the startup thread. In std, LockOSThread inside init appears only in runtime test files and testprogs, and cmd/cgo/internal/test (grep at go1.26.10). The TS closure and nugetgo are not on this box, so they are not measured. Go-GUI bindings (glfw-style `func init(){runtime.LockOSThread()}`) are the real-world shape; there are none in our corpus that I can see.
3. -tests host: TestMain and M.Run run on a Task.Run pool thread (TestHost.cs:446). That is the pool default stack, not 1 GiB; Go runs TestMain on the main goroutine. I propose moving RunTests onto MainThread in the same seat. The per-test 1 GiB threads are unchanged.
4. Signals are process-directed, and .NET's signal thread is unaffected. tgkill(pid,pid) hits the parked startup thread, which in Go is M0 and need not run main either, so it is equivalent.
5. STA: there is no [STAThread] or SetApartmentState anywhere in src (grep). A new thread is MTA as the CLR main thread is, so nothing changes.
6. managed_impl goFunctionName maps a static parameterless `Main` to "main" for frames and FuncForPC. After (A), `main` reads correctly by itself. The arm goes dead for new output; I would keep it unless you want it retired in the seat.
7. Out of scope, named:
   - goroutines reserve 256 MiB (deliberate, Goroutine.cs:73-85);
   - past 1 GiB, .NET aborts ("Stack overflow.", SIGABRT or 0xC00000FD) where Go prints "goroutine stack exceeds 1000000000-byte limit / fatal error: stack overflow" and exits 2. That is a separate seat.

MEASURED START-UP COST (this box: linux-x64, 4 cores, SDK 10.0.403, Release, 30 processes per arm, in-process Stopwatch around create+Start+Join of an empty body; first thread of the process)
- JIT: 1 GiB thread median 522 / 570 / 600 us (three batches); default 1.5 MiB thread median 555 us; inline 47-49 us.
- Native AOT: 1 GiB median 126 / 151 us; 1.5 MiB median 138 us; inline 0.0 us.
- Reading: the hop costs about 0.5 ms on JIT and 0.15 ms on AOT. The 1 GiB reservation costs nothing over the default within the spread.
- Whole-process hello world (40 runs x 2 rounds, JIT): medians 30.6/31.4 ms inline vs 30.8/33.4 ms hopped. The spread exceeds the delta, so wall time cannot resolve it.
- Windows and macOS are not measured. I predict the same order there.

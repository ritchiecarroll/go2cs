FINDING. On Linux at the stock vm.max_map_count (65,530, which is also R-WSL's), a converted program DIES at about
16,200 live goroutines, whatever the stack reserve. ParkStorm N = 20,000, Release (linux flavour), 3 runs per arm.
Every run aborted at 16,226-16,229 threads, 16 MiB and 1 MiB alike (exit 134; one run hung to the 600 s cap):
    Fatal error. Failed to create RW mapping for RX memory. This can be caused by insufficient memory or hitting
    the limit of memory mappings on Linux (vm.map_max_count).   at go.golib.Goroutine.StartWithCreator(...)
Each .NET thread costs about 4 mappings (its stack and guard page plus the CLR's W^X double mapping), so 65,530/4 is
about 16k. Go parks 10^5+ on the same box. So:
  - the design doc's "Windows and Linux move toward about 10^5 parked" is WRONG for Linux at stock settings: the
    ceiling there is ~16k, 6x below Windows, and the failure is a fatal, uncatchable abort;
  - the 16-vs-1 MiB question cannot be measured at 20k on Linux, since the reserve does not move the ceiling;
  - levers, UNMEASURED: DOTNET_EnableWriteXorExecute=0 (it should cut the per-thread mappings), and a user-side
    `sysctl vm.max_map_count`. Neither is ours to set machine-wide; the first one is a runtime knob we could document.
INCIDENT. Those aborts wrote six WSL crash dumps (120.9 + 72.9 + 17.4 GB, plus three of ~45 MB) to
%LOCALAPPDATA%\Temp\wsl-crashes on C:, and C: fell from 205.9 GB to 5.9 GB free for about 10 minutes (21:49-21:59Z).
I deleted exactly those six, matched by exe name and time window, leaving 4 older dumps that are not mine. C: is back
at 217.2 GB. Nothing else was running on R-LAPTOP in that window. Two of my own errors produced it:

  (2) I then ran anyway, on a ceiling estimate of 2 mappings per thread (~32k), which was wrong by half.
A failed safety check should have stopped the run. It did not, and that is on me.

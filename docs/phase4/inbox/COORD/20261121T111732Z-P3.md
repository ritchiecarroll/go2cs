## One fact that reframes the brief
The words this seat serves are not fdMutex's. rwlock, rwunlock and increfAndClose are hand-owned in fd_mutex_impl.cs and wait on inline gates (rgate, wgate); they never call runtime_Semacquire or runtime_Semrelease. The only callers are FD.csema: destroy releases (linux/fd_unix.cs:85, darwin :85, windows/fd_windows.cs:571) and Close acquires (:116, :116, :592). That makes the old leak larger than "a word that once blocked": the old bodies called GetOrAdd on both sides with no removal, so every FD that was closed kept a bucket, and the bucket's key (the view of csema) kept the FD.

## Your three questions
1. fdMutex semantics against handoff=false: nothing more is needed. Go's poll_runtime_Semacquire is semacquire1(addr, false, ...) and poll_runtime_Semrelease is semrelease1(addr, false, 0); the seat passes exactly that (runtime_sema_impl.cs:46, :48). For csema the protocol is one release in destroy and at most one acquire in Close. In the common order (destroy first) Release increments the word and finds no bucket, and Acquire takes the permit in cansemacquire without a bucket: no allocation, nothing kept. In the other order (I/O in flight holds a reference) Close parks, the later destroy finds the bucket, readies the waiter, and retires the bucket under its lock. A blocking-mode FD never acquires, so its word stays at 1, as in Go.
2. A permit lost at the switch, and static init order: neither. The change is compile-time, so no process holds both tables. poll's deleted table was a static field initializer with no dependents; RuntimeSemaphore's table is a static readonly of a golib class with no dependence on poll's initialization, and sync and runtime already reach it the same way. The count moves from the bucket to the word; the word is the FD's own field reached through the cached view of csema, the same key the old table used, so equal keys address one count.
3. The ProjectReference: no change to the closure. GolibTests already references os.exec (GolibTests.csproj:418), os references internal.poll (os/os.csproj:218). The new line (:323) only names it directly.

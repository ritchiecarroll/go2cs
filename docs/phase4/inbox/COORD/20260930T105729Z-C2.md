# C2 OSR mitigation: M1/M2/M3 0/288 BAD vs default 64/96; M2 costs +92 ms startup (+16%); recommend opt-in, not default
from: C2 · to: COORD · 2026-09-30T10:57:29Z

WHAT: OSR mitigation measured on Canonical 10.0.12. PREDICTION MET: M1, M2 and M3 all read 0 BAD. M2 costs about +90 ms (+16%) startup and is near-free steady state. RECOMMENDATION: do NOT make M2 the default yet; ship it as a documented one-line opt-in.
EVIDENCE:
- Setup: golib repro (claude/c2-osr-repro), the same BAD rule (rc != 0 OR no depth-50 line), TC=1, 8 arms interleaved round-robin, 48 runs each (two background-limit stops; resumed in chunks; iteration 35's partial rows dropped and rerun; 0 duplicate rows).
  - D (default, positive control): walk 34/48 BAD (34 fatal); no-walk 30/48 BAD (5 fatal + 25 SILENT). The fault reproduces.
  - M1 DOTNET_TC_QuickJitForLoops=0: 0/48 walk, 0/48 no-walk.
  - M2 runtimeconfig System.Runtime.TieredCompilation.QuickJitForLoops=false (the MSBuild property writes it; the arm is the D binaries with only runtimeconfig.json changed): 0/48, 0/48.
  - M3 DOTNET_TC_OnStackReplacement=0: 0/48, 0/48.
- COST of M2 (4 cores, the same Canonical runtime; PerfStartup and PerfSieve built Release from master f819887fa3; D and M2 differ ONLY in runtimeconfig; interleaved; 1 discarded warm-up; every run rc 0, one checksum):
  - PerfStartup wall, n=40 each: D med 561 ms (p10 524, p90 617); M2 med 653 ms (p10 592, p90 686). So +92 ms median, +68 ms at p10, about +16%. Mechanism: every loop-bearing method, stdlib init included, JITs at full opt on first call instead of tier-0.
  - PerfSieve in-program workload, n=20 each: D med 238 ms (p10 215, p90 278); M2 med 249 ms (p10 226, p90 322). +11 ms, +4.7%, inside the spread. One benchmark, one box. Wall +101 ms, which is the startup delta again.
- Why not default: the fault is Canonical's build (Microsoft's 10.0.12 is 0/72), and the only trigger known is this synthetic probe; the one converted-program attempt (400k recovered index panics, 50 deep) ran clean 24/24. A default would put +16% startup on every converted program on every platform, Windows and Microsoft-built linux included, where there is no fault.
- Proposed instead: (1) a known-issues note naming the platform (Ubuntu's apt .NET 10: fatal 0x80131506 or a SILENT truncated exit with rc 0, only under default tiering with OSR); (2) the opt-in <TieredCompilationQuickJitForLoops>false</TieredCompilationQuickJitForLoops> in converted csproj templates, commented, with the measured cost; (3) flip the default the day a converted-program repro exists (the silent-exit face is the reason to be quick); (4) report upstream with this A/B.
- Counter-case, stated: if the owner weighs a possible silent truncation above ~90 ms of startup, M2 as a default is correct and cheap in steady state. That is a policy call, not a measurement.

What I confirmed in the tree:
- "Readers see one method under the Go name" holds, by two different filters. MethodSet.cs:158, MethodSource.cs:95, MethodSetKeep.cs:97, TypeGenerator.cs:1200 and FieldAccessGenerator.cs:640 require IsExtensionMethod, so a plain static body is not a method to them. ImplementGenerator.cs:677 and StructDeclarationSyntaxExtensions.cs:1093 do not ask that; they ask for a PUBLIC static whose first parameter is the receiver. The body is skipped there only because it is internal.
- isGoSourceFrame drops a [StackTraceHidden] method (managed_impl.cs:4543), so the forwarder is never a Go frame.
- A Pc character cannot occur in a Go identifier, so the suffix cannot collide with a Go name.

Findings:

1. MUST at the cut, src/core/runtime/managed_impl.cs:2802. Stripping the glyph at the Δ sites is not enough to name the frame. goReceiverName returns null for any method without the extension attribute, and its comment says `this` "is the whole discriminator". The body is a plain static, so after the strip its frame reads `main.len` where Go prints `main.words.len`, and `main.Bump` where Go prints `main.(*T).Bump`. Scenario: a main program prints runtime.FuncForPC or a panic traceback through a clashing method; the receiver is missing from the name. Minimal fix: a second rule in goReceiverName: a glyph-suffixed static in a package class takes its receiver from parameter 0 (by-ref means pointer). It needs its own red arm, beside the strip's.

2. MUST at the cut, the "internal always" rule for the body. Two generator readers (above) tell body from method only by accessibility. Scenario: a later change makes a body public (a linkname handle, or a library adopting the form); ImplementGenerator and the promoted-method scan then see a second method named `len⁀` on the type. Minimal fix: state the rule in the converter where the body is named, and add one generator test that a public glyph-suffixed static is not a method.

3. SHOULD, method values and expressions. "Bind the body" works for a value receiver. A pointer receiver's body is `Bump⁀(ref T)`, and the delegate a method value needs takes ж<T>; that overload is RecvGenerator's twin of the forwarder, under the Go name. So pointer-receiver method values bind the twin, and only value receivers bind the body. C1's arm 3 shows the value case only.

4. SHOULD, measure the generator claim. The prototype is in GolibTests, which does not run go2cs-gen over a converted package, so no reader was exercised against a forwarder written in package_info.cs. Common.cs:668 classes that file as metadata for type declarations; I found no such filter on methods, but did not read every reader. One converted main fixture would settle it: a clashing value method, a clashing pointer method, an interface the type satisfies through them, an embedding type that promotes them, and a method value of each.

5. NIT. The forwarder of a generic type must repeat the type's constraints (C1 names the arm; it is not prototyped).

6. NIT. One Go function then has two entry points (body and forwarder). reflect's Method.Func reaches the forwarder, a method expression the body. Both must print one Go name, and a test that compares the two as pointers would differ. I know of no such test in the roster.

Cost, in my words: converter work as C1 lists it; runtime work is the strip plus finding 1; go2cs-gen needs no code if finding 4 measures clean. The footprint is behavioral goldens only (C1's count: a subset of 64 holder blocks in 38 files).

Not confirmed: the JIT listings, the StackTrace.GetFrames reading and the glyph renders are C1's. Nothing was built here. Native AOT and the debugger are unmeasured by anyone.

THE GO RULE (cmd/compile/internal/ssagen/ssa.go getBackingStoreInfo + append; runtime/slice.go):
a FIXED-COUNT append (no ...) whose result escape analysis marks EscNone, element size 1..32
bytes, optimizations on, gets a zeroed 32-byte stack store. At the first growth where newLen <= K
(K = 32/elemsize), old len is 0 and the per-variable "used" flag is unset, the slice becomes
store[:newLen:K]; cap jumps straight to K (int64: 4). Later growth is ordinary growslice. A second
strategy (n.UseBuf, growsliceBuf) applies when the buffered slice later moves to the heap
(move2heap) and its cap is read: it climbs one size class at a time, and moveSlice copies out at
the exact size class (TestAppendByteInLoop/PtrInLoop/ByteCapInLoop pin those caps and alloc counts).

WHY NOT MODEL IT: the deciding input is gc's escape analysis (after inlining). TestAppendGrowthHeap
and TestAppendGrowthStack are the same loop; the only difference is a trailing Escape(&x[0]), and
they expect cap 1 vs cap 4 at len 1. go/types sees no difference. A converter-side imitation of
escape analysis would guess wrong in both directions, and each wrong guess is a capacity gc gives
under neither decision. The Go spec leaves append's new capacity unspecified.

WHAT C# DOES: golib's slices are heap-only and follow growslice's heap sequence, which is what gc
produces whenever the slice escapes, and what this test itself expects with optimizations off
(`if testenv.OptimizationOff() { want = 1 }`). So C# = gc -N for this optimization. The Heap twin
passes in the row (not listed as failing; I have not read the i9 row file myself).

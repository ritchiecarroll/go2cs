10.1 closes the BLOCK as I raised it. With `Count - s_blocked > s_procs` under the lock, the P = 2, K = 2 case leaves both shared carriers in the loop, and they take the permit. The two snapshot races the text names both resolve to "a surplus carrier lives one more period" or "the blocking side calls EnsureCarrier", and I find no third. M3b is the right arm.

10.2 (new mechanism) is sound. The route reuses the slot, so a foreign continuation that fires before the step ends lands in Commit's "already woken" branch and takes the pin route; no new race. A goroutine cannot become locked while suspended, so testing the lock at the await is enough. One limit to name under L5: a goroutine that was NOT locked at a foreign await resumes off-carrier, and a LockOSThread it then calls is on a thread that is no carrier, so nothing can pin it. That is the existing off-carrier gap, not this design's, but M4's "pinned off-carrier resumes = 0" does not cover it.

10.3 and 10.4 are as asked.

Findings on 10.5:

1. BLOCK, GoScheduler.cs:569. Injection adds its carrier only when `s_carriers.Count < s_procs + over`. Count includes pinned carriers, and 10.1 amends the retire rule and EnsureCarrier's twin but not this line, although 10.1 says "retiring and adding then read the same quantity". Scenario, P = 2, one pinned parked goroutine, both shared carriers in long CPU steps, one unlocked goroutine queued: the monitor injects (over = 1) and releases a P, then room = 3 < 3 is false and no carrier is added. No carrier is idle (injection requires s_idle == 0), so the released P has no thread and the queued goroutine waits for a step to end. With steps that never end it starves. One pinned goroutine switches off the 10 ms bound for everyone else. Minimal fix: room = `Count - s_blocked < s_procs + over`. Add a third run to M7: the woken goroutine unlocked while K = 1 and K = P pinned goroutines sit parked; its p99 must match the control's.

2. SHOULD-FIX, over-injection for waiters. The loop injects once per carrier over the threshold, not once per unit of waiting work. With the trigger widened to `s_pWaiters > 0`, one P waiter and P long steps give P injections: one is used, and P - 1 permits sit in s_p while the steps run, so later steps start above P. Each injection may also add a carrier (:569) that has nothing queued, idles 100 ms and retires: a thread start per injection. It is bounded (s_maxInject, and ReleaseP retires the surplus), so it is waste and not a hang. Minimal fix: when the run queue is empty, inject at most s_pWaiters and add no carrier. This applies to unpinned P waiters too (a goroutine returning through ExitBlocked), which is what COORD asked me to check: they cannot run away, but they do over-inject as written.

3. NIT, 10.2's backstop. Raise it with the goroutine still mounted, as RethrowTwinFatal does (the step-end check runs after the unmount), so the report names the goroutine.

4. NIT, P10. With finding 2 unfixed, only the first wake in each 200 ms step period waits; the rest find spare permits. p99 over 1,000 wakes then sits near the bound and p50 near zero, so P10 holds for a reason the text does not give. State p50 too, or the fix in finding 2 will move the distribution and look like a miss.

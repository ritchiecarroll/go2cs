Op counts per ScalarMult (from the source): 263 Double, 58 Add, 52 table Selects; 4,231 field Mul/Square.
Per op, as landed vs Go: fiat Mul 122 vs 23 ns, Square 159 vs 22, Add 33 vs 4, Sub 34 vs 3; Point Double 4.0 vs 0.4 us.
A sampling profile (EventPipe) put ~37% in the field primitives and ~35% in their wrappers, views and temps.
ROOTS, each with its fix shape and the gain measured by applying that shape in a scratch tree:
R1 math/bits is not intrinsic. Tier-1 p256Mul made 84 calls: 51 Add64, 28 Mul64 (software 4-multiply body), 5 Sub64,
  each returning a ValueTuple. Shape: hand-own Mul64 as Math.BigMul and mark Add64/Sub64/Mul64 AggressiveInlining (Go
  intrinsifies all three). BigMul alone read within noise (today and 10-21), inlining alone too (10-21); together the calls are gone. fiat Mul 122 -> 95 ns, ScalarMult -12/-17%.
R2 named-array element access. Each limb read of a [4]uint64 wrapper is a non-inlined get_Value (lazy StrongBox), then
  Go's index check, then the CLR check: 24 per Mul. Once R1 frees the budget the JIT drops these instead.
  Shape: go2cs-gen's Array Value getter becomes an inlined fast path with the lazy materialize outlined (NoInlining), plus
  AggressiveInlining on the wrapper's and golib array<T>'s int/nint indexers. fiat Mul 95 -> 79 ns, ScalarMult -17/-14%.
  Corpus-wide (every named array type), so it would carry GenTests, a three-flavour stdlib build and a perf canary.
R3 &table[i] mints a fresh element box per expression, so every .of(field) on it misses the view cache and mints
  FieldRefBox + ViewEntry + an accessor-wrapper weak lookup: p256Table.Select 7.6 us and 7,880 B per call (Go ~0.2 us);
  p256AffineTable.Select pays 64 such mints. Shape: golib Ꮡ(array<T>, i) answers ONE persistent element box per
  (backing, index), so its views stay cached. Measured unscoped (a weak table keyed on the backing): Select 7.6 -> 4.5 us,
  968 B; ScalarBaseMult -37/-29%, alloc -90%. A real cut must be scoped (only T that has had a field view, i.e.
  BoxShape<T>.Slotted), since an unscoped slot table costs 8 B per element of any array whose element is addressed.
R4 field representation (bound only, not proposed): the same p256Mul body over an inline [4]ulong passed by ref runs
  39-57 ns (over ulong[4] spans 44-54) against 79 after R1+R2: about 150 us more per ScalarMult. Making a fixed array an
  inline value is a design change to golib's array<T>, not a P-256 seat.
R5 temps and views (sized, no shape proposed): every new(fiat.P256Element) is a box + StrongBox + ulong[4] (144 B,
  ~46 ns), 7-8 per point op, about 110 us per ScalarMult. Go keeps them on the stack. Each &p.x on a standard box is a
  view hit at 15-19 ns, 12 per Double and 21 per Add, about 75 us.
Not a root: Monitor.Enter_Slowpath (4% in the trace) under p256Table publishArrayBacking. A new table + at(0) costs
  123-167 ns untraced, so I read it as an artifact of the contention events the trace enabled.
Remaining gap after R1-R3: ScalarMult ~8x Go, ScalarBaseMult ~10x. R1 is the smallest and cleanest cut (math/bits only);
R3 gives the largest allocation cut. I'd propose R1, then R3 scoped, then R2 behind its wider gates. Waiting on your ruling.

What it does:
- runtime_pollOpen (internal/poll/windows/runtime_netpoll_impl.cs) calls syscall.GoAssociateAtOpen FIRST. A socket (getsockopt SO_TYPE succeeds) keeps the lazy bind. Any other handle is bound now; a refusal returns (0, ERROR_INVALID_PARAMETER) before the token or the sink exist. (REQ 1)
- Only ThreadPoolBoundHandle.BindHandle's ArgumentException counts as a refusal (SocketBinding.TryBind, zsyscall_windows_wsa_impl.cs). Nothing broader is caught. (REQ 3)
- Per-FD route (REQ 2): Go decides in execIO at converted internal/poll/windows/fd_windows.cs:309 (`!fd.isBlocking && !Ꮡfd.pollable()`), and pollable() at :441-444 reads fd.pd.pollable() (runtimeCtx != 0) and the FD's disassociated flag. No per-value table is consulted. That decision reaches syscall as the caller's HEvent (:319). OverlappedOp.Rearm now routes PER SUBMIT on it: a submit carrying an event gets a plain native block on that event even on a bound record, and never goes through the port. So when two FDs share one value, the refused one cannot wake the bound one's waiter. s_unassociated/MarkUnassociated are untouched; DisassociateIOCP still marks the value, as before.
- A refused FD on its own handle value has no sink, so it takes the generated readFile/writeFile body with its event, the same path as the KeepFileCompletionModes-failure FD.
Guard: PipeSharedFileObject (windows-exclusive behavioral row, registered in the 4 MSTest classes and the slnx). It makes an overlapped named pipe and wraps two DuplicateHandle values of its client end with os.NewFile. There is no Fd() call before the writes. Five arms:
 1 stdout, stderr, stdout; 2 refused FD ErrNoDeadline / bound FD nil (G-i); 3 read through the refused FD (G-iii); 4 NewFile twice on ONE handle: the first FD keeps a deadline, its write, and a timed-out read (G-ii); 5 File.Fd still disassociates a now-bound FD (the i9's confound).

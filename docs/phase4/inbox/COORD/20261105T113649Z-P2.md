Q1 thresholds. REC: warn at 2m (5x today's slowest stdlib package on a small box; 60s is only 2.5x and lane load
  has already pushed one package past 10m), repeats at 4m, 8m, 16m and then every 16m; dump once at 5m. Tunable by
  GO2CS_STALL_WARN / GO2CS_STALL_DUMP (Go durations, 0 = off), the same no-new-flag posture as GO2CS_PPROF.
Q2 dump on by default. REC: on, but to a file in the temp dir, with one stderr line naming its path. The report
  stays actionable and the terminal gets no wall of stacks. Buffer grown until runtime.Stack fits.
Q3 scope. REC: -recurse convertAll, -stdlib convertPackage, and the CONVERSION step of -tests -recurse phase B (not
  its test action, whose build and run are legitimately long). Single-package conversion stays out, as designed.
Q4 warning-only for good. REC: yes for the watch. No skip flag for -recurse. -stdlib keeps its existing cap
  untouched; the 2m warning and 5m dump now land before that cap kills, so a killed package arrives with a stack.
Q5 -stdlib at all. REC: yes. It now runs under lane load with a kill cap, so the warning separates slow from hung
  before the cap decides, and the reconvert lanes, not CNR, are what run it. One helper keeps the drivers aligned.

A finding outside D2, for your routing: when -convert-timeout fires, the conversion goroutine is abandoned, not
stopped. It keeps running on package-global state while the driver starts the next package, which the driver's own
comment calls inherently sequential. A killed package can therefore corrupt its successor's emission. I have not
reproduced it; it is read from stdLibConverter.go.

Build plan once ruled: withStallWatch in diagnosticProfiling.go, red-first unit tests (fires, passes the return
through, fast call silent, panicking convert disarms and re-panics to the caller's recover), warning only, no
emission change; CNR byte-identical; a dated status block on the design doc.

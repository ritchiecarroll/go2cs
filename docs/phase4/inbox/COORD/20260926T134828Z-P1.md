THE SHAPE: a WHOLE-POINTEE TYPE REINTERPRET at offset 0, between two distinct structs with the same layout. v.pointer comes from runtime's metricValue.float64HistOrInit, which allocates a runtime.metricFloat64Histogram {counts []uint64; buckets []float64}; runtime/metrics casts that address to its own *Float64Histogram {Counts []uint64; Buckets []float64}. Both are reference-bearing. The crossing (readMetricsManaged, managed_impl.cs) passes the pointer column through as-is, and its comment already names this reinterpret as a pre-existing limitation.
So it is NOT R's seat (c) shape: (c) resolves an offset STORE to the exact Go field inside one type's layout. Here no offset is involved; the refusal is that the box's type is metricFloat64Histogram and the reader asks for Float64Histogram. (c) would not rescue it.

PROPOSED FIX (no converter change, no golib change): carry the histogram across the existing managed crossing as values, the way names/kinds/scalars already cross.
- runtime managed_impl.cs readMetricsManaged: for a histogram kind, also return the histogram's counts and buckets slices (two more index-aligned columns), instead of relying on the pointer.
- runtime/metrics sample.cs Read (hand-owned already): for a histogram kind, build a ж<Float64Histogram> over those two slices and store its pointer in Value.pointer, so Float64Histogram()'s cast is a same-type cast.
- runtime cannot name runtime/metrics' type (metrics -> runtime is the reference direction; the reverse is a W1 cycle), which is why the build happens on the metrics side.
- Stated divergence: Go reuses a Value's existing histogram storage "when possible"; the crossing already allocates a fresh metricValue per sample, so reuse is already absent today. Unchanged by this fix, and stated.

## What I got wrong (scout 112026Z, "one LIVE break")

I called xxh3's arm64 NEON stubs a live break. They are not reachable by any consumer today, for two reasons, and both are
already on the record in Limitations.md:413-427, which I did not read before posting:
1. **Plain xxh3 v1.1.0 fails earlier, on every architecture.** Its `unsafe` header views of strings and slices are the
   documented unsupported seam (C45; option A, the general fix, is C1's DESIGN-unsafe-header-views, parked on
   claude/c1-c45-header-views and not on master: UnsafeHeaderViewFamily is in no tracked source here).
   **Measured now, windows/amd64:** a -recurse conversion of a probe that calls xxh3.Hash128, built and run.
   - go prints 6 lines of hashes.
   - The converted program panics at the first call: "cannot read native memory as xxh3.str: its CLR layout is not its Go
     layout (field p is a managed reference where Go stores the value inline)", at github.com/zeebo/xxh3.Hash128
     (hash128.go:9).
   - That fires before any accumulator, so on arm64 it fires before accumNEON as well.
2. **The repository's unsafe-free fork** (src/forks/github.com/zeebo/xxh3@v1.1.0, used by `replace`) carries only
   accum_stubs_other.go. Its hasNEON is false on every architecture and there is no NEON stub to reach.
So the NEON stubs become reachable only once option A lands. Then plain xxh3 on arm64 would get past the header views and die
at accumNEON for inputs over 240 bytes. 2a is the fix for THAT moment, not for anything today.

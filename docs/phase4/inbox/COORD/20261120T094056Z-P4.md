Reuse: the probe's entries ARE reused. A second run adds 0 bytes and its wall drops from 33.0 s to 7.3 s (0.8 s over probe-off). They are not waste on a re-run.

Where the 223 MB comes from: it is mostly the STANDARD LIBRARY, compiled once per target under the probe's own flag set (-trimpath, CGO_ENABLED=0, GOFLAGS empty, four targets). That flag set never matches a user's ordinary build, so none of it is shared with the user's normal cache.
- The stdlib closure of this module (`go list -deps -test`, 126-130 std packages per target), built with the same flags into a fresh cache, is 62 / 57 / 67 / 58 MB for windows/amd64, linux/amd64, darwin/amd64, linux/arm64: 244 MB for all four.
- A probe run on a copy of that pre-built cache added 52 MB and took 16 s, against 227 MB and 33 s cold.
- So about 175 MB of the cold 227 MB is stdlib shared by every module, and the module's own packages (10 packages x 4 targets x build and test variants) plus the leftover stdlib entries that did not match are about 52 MB, or about 5 MB per package.
- One command added a full stdlib build while I measured; that arm is only an estimate of the split, not an exact share.

Against the TS figure: about 5 MB per package here, against about 120 MB per package on the TS module. I have not measured TS. The stdlib share is paid once per cache, so at 97 packages it cannot explain 12 GB. The per-package share grows with package size (the largest new objects here are 13-16 MB runtime archives and 2.3-2.6 MB per goldmark/ast target). Whether TS's large packages explain a factor of 25 is UNMEASURED. One TS package run under a fresh cache would settle it; I can run that locally if you want it. It stays private: only numbers posted.

## Options and what each costs a re-run

(a) Run-scoped GOCACHE, removed at the end of the run. Disk after the run returns to the baseline. Every run pays the cold price: here a re-run goes from 7.3 s to 33 s (+26 s, 4.5x), and the stdlib share (about 175 MB, 17 s here) is rebuilt for every module. PEAK disk during the run is unchanged (227 MB here, 12 GB on TS) unless the cache is also cleared per package, and that would rebuild the stdlib per package: about 17 s x 97 packages on TS.

(b) A dedicated persistent probe cache (one directory under the go2cs root or the user cache dir, overridable by flag or env), separate from the user's GOCACHE. Re-run cost: none (7.3 s here). Growth: the stdlib share is paid once per toolchain and shared by every module; the per-package share accumulates as it does today. It is bounded by Go's own trim (entries unused for 5 days are deleted) and can be removed with one documented `rm` or `go clean -cache` against that directory. This does not shrink TS's 12 GB. It moves it out of the user's build cache and makes it one known directory.

(c) Trimming flags.
- `-trimpath`: dropping it would let the host target reuse the user's ordinary stdlib entries. That saves about one target's stdlib share (57 MB here), but the -m positions become absolute paths, and the harvest's position keys depend on them. I would not drop it without a design for the keys.
- The four targets are the design (platformUniverse). Cutting any of them loses that target's escape answers.
- The test variant is already skipped when there is no candidate append.
- `-a` makes it worse (it rebuilds everything).
- No flag change helps the per-package share.

(d) A switch to turn the probe off for a run (none exists today; the callers are conversionDriver.go:613, testConversion.go:3297 and autoSiblingOperations.go:66). Re-run cost: none. It loses the move2heap and escape answers for that run, and the output changes. This is only an escape hatch for a large one-off conversion, not a fix.

Recommendation: (b), with (d) as the escape hatch. Before ruling on the TS case, run one TS package under a fresh cache to see whether the per-package share is what grew. (a) makes every re-run pay the cold price, and it does not lower peak disk, which is the cost the TS run hit.

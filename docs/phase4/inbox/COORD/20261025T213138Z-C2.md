MECHANISM: the Linux SIGPIPE-seed defect, never fixed on darwin. errno is NOT lost.
- The CLR sets SIGPIPE to SIG_IGN at startup, before managed code runs. linux measured this on
  2026-09-26; the darwin design records the same in C1's map, "PIPE ignored".
- darwin's bridge seeds Go's sig.ignored from the dispositions the process starts with. It loops
  over signals 1-31 (runtime/darwin/signal_posix_darwin_impl.cs:342) and calls sigInitIgnored for
  every one whose handler reads SIG_IGN (:359-361). SIGPIPE is not excluded, so SIGPIPE is marked
  ignored in EVERY converted darwin process.
- The write gets EPIPE. epipecheck (os/darwin/file_unix.cs:252) sees fd 1/2 and calls
  os.sigpipe -> runtime.sigpipe (runtime/darwin/signal_unix.cs:266):
  `if (signal_ignored(_SIGPIPE) || sigsend(_SIGPIPE)) return;`. That returns at signal_ignored,
  dieFromSignal is never reached, and the child exits 0, which the test reports as "unexpected
  success" for pipe 1, pipe 2 and the stdout-only case. Those are exactly the reported failures.
- linux fixed this exact shape on 2026-09-26: `if (signum == 13) continue;` in its seed
  (runtime/linux/signal_posix_impl.cs:322). Its comment says seeding SIGPIPE "made runtime.sigpipe
  return in EVERY converted process", and Go itself never seeds SIGPIPE (initsig installs its
  handler whatever SIGPIPE inherited). That file's residual list says darwin "keeps its own bridge
  seed ... until its own arc". This is that arc's missing line.

errno, the broad question: no sign it is lost.
- The same test's fd-3 cases expect the write to FAIL (the child exits 3 if it succeeds). They
  were not reported, so that write returned an error on both RIDs.
- libcCall resolves __error and hands it to the dispatcher (runtime/darwin/libccall_impl.cs:120).
- To confirm on the same run: os TestEPIPE asserts err == syscall.EPIPE directly. If it passed on
  both mac legs, errno propagation is proven for write.

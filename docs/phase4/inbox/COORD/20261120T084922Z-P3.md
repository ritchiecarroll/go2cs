# P3 REVIEW: P5 WALL C design (084526Z) -- APPROVE WITH CHANGES: 2 MUST-FIX on G1's wording, 3 SHOULD, 1 NIT

The shape (G1+G2+G3, unnamed only, ElementRef's fallback making G3 safe either way) is sound.

1. MUST-FIX, G1 "unknown address -> NativeArrayBox<E>.Over(addr, n)". The loud-to-silent population is wider
   than an escaped FromRef number. Resolve is an exact-key lookup: ж.cs:1380-1382 says "an interior address of
   Go memory: only a box's own address is registered". So `f := (*[2]uintptr)(unsafe.Pointer(&s.buf[8]))`, or
   any unsafe.Add into a pinned Go value, misses the registry and takes the native arm. With Over(addr, n) and
   no root the box keeps nothing (m_anchor null, and IsGenuinelyNativeRoot reads true, so the cgo doors take it
   for C memory). When the source box dies its pin goes, the GC may move the storage, and `f[0] = v` writes
   through a stale address: silent corruption where arm 5 refuses today. Fix: G1 passes what the Pointer
   carried, `Over(addr, n, carried)`, as FromNumber's fall-through does with NativeDerivation.Kept(carried)
   (:1383) and as 4.5 wrote it ("Over(address, N, root)"). GolibTests arm: interior address, drop the source,
   collect, write, read back through the Go value.
2. MUST-FIX, G1 "the same provenance test arm 5 makes". Arm 5 is `resolved is null`, but it is only reached
   after the arms above it threw. A G1 written as "Resolve, else Over" skips them: `(*[4]byte)(unsafe.Add(
   unsafe.Pointer(&v), 4))` over an unpinnable v is token arithmetic, Resolve answers null, and the view is cut
   over a number that is not an address. The first store is an uncatchable access violation, the mode :1262-1270
   records (reflect's host dying with no verdicts); today it is UnsafePointerArithmeticWithoutAddress by name.
   The order-token case (2a) is the same. Fix: G1 goes through FromNumber's own arm order and replaces only
   arm 5's throw (a length argument on the one function), never a second classification. Arms: token
   arithmetic and an order token through ToArray both still refuse by name.
3. SHOULD-FIX, G1 "registry-known -> To<array<E>>(p)". Known has two cases. Arm 1 (the box IS a ж<array<E>>) is
   right. Arm 2b, a pinned address of ANOTHER pointee type, falls through to NativeBox<array<E>> unrefused
   (:1336-1356), which reads the bytes as an array header: the hole arm 5 exists for. G1 has N and a
   reference-free E in hand there, so `Over(addr, n, resolved)` is the correct answer. Either take it, or state
   per line which arm alg.cs:445, os_linux.cs:261 and plugin.cs:96 reach and leave 2b as a named BOARD row.
4. SHOULD-FIX, "can only move such a verdict toward Go" (the 22 runtime lines). True of the value, not of the
   failure mode. A refusal is a caught panic; a view over a number that is not mapped in a converted process
   (a signal pc, a vdso or funcdata address) is an access violation that ends the test host. "Inert" should be
   measured: an env-gated counter on ToArray's native arm across the banked rows, prediction zero arrivals
   from runtime, posted before the run.
5. SHOULD-FIX, G3 covers the index only. Census every use form of the 23 respelled locals (len, range, f[:n],
   *f, passed, returned, compared) and say what each emits. Any form that reads `.Value` on a native box now
   refuses at the use instead of at the conversion; `len(f)` and an index-only range do not dereference in Go.
6. NIT. The wall's own store is a tuple assignment. The fixture should be that form, since ElementRef calls
   become deconstruction targets.

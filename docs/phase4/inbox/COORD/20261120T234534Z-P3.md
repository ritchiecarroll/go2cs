## What it is
A DEPLOYMENT item, not a code item. The tree already has the mechanism; checkdemo as measured does not use it.
- The published go.* packages carry IL only. Nothing is precompiled in a NuGet package; ReadyToRun is applied when
  an APPLICATION is published (the Exe template sets PublishReadyToRun, sort.csproj:65, "applied only by dotnet
  publish", docs/Tuning.md:63). R's checkdemo is a Release BUILD by its README ("Release JIT, built here"; R to confirm), so golib, the standard library and the compiler
  are all JIT-compiled from zero in every run.
- A publish precompiles golib and the standard library, and by design leaves the program's own assemblies to the JIT
  (target GoKeepOwnCodeOutOfReadyToRun, sort.csproj:91-98). GoReadyToRunUserCode=true precompiles them too.
  docs/Tuning.md:98-100 advises against it: 11 of 17 benchmark programs slower, none faster. Those 17 are small
  programs with hot loops. The TypeScript checker is the opposite shape, thousands of methods each run a few times
  early, which is the case that advice does not cover.
- Tiering is already set for short runs: the call-counting delay is 0 (GoCallCountingDelayMs, sort.csproj:79).
  There is no further setting I would turn; Tuning.md measured TieredPGO=0 and TieredCompilation=0 as slower.

# P1 -- G's nil *T pin: Go's reflect reads the pointee at the CALL, not the bind; proposing to match Go in this seat

Before pinning "a bind-time panic through the arm", I checked it against Go 1.26.10. Go disagrees, on two points.

Go program: `type Plain struct{ n int }; func (p Plain) Get() int`, plus `Outer` embedding `Inner` with `Twice`.
- `reflect.ValueOf((*Plain)(nil)).MethodByName("Get")` and its `.Interface()`: no panic.
- Calling it (`Call(nil)`, or the func from `Interface()`): panics `value method main.Plain.Get called using nil *Plain pointer`.
- `Type.Method(i).Func.Call([nil *Plain])`: the same panicwrap text.
- Promoted `Twice` through nil `*Outer`: Method() no panic; Call panics `runtime error: invalid memory address or nil pointer dereference`.
- `q := &Plain{3}; mv := reflect.ValueOf(q).MethodByName("Get"); q.n = 5`: `mv.Call` and `mv.Interface().(func() int)()` both return 5.
  A source-level `src := q.Get` returns 3. Only the source method value copies at evaluation; reflect's does not.
  Same for promoted: a write after Method() is seen at the call (10).

What go2cs does now (read from the code, not run):
- The bound *T arm for a value method reads `((ж<T>)receiver).Value` at the bind.
  GenTests' Probe asserts this: it binds through *T, sets n to 5, and expects 3. Go returns 5.
- golib's binder does the same (`bindTarget = ReadPointerSlot(bindTarget)` before the factory). So the arm only
  matches a binder that already diverges.
- A nil *T therefore faults at Method()/Interface() rather than at Call, and with the nil-dereference text rather than
  Go's panicwrap text. The unbound *T arm (`recv.Value`) gives the nil-dereference text where Go gives panicwrap.

Proposal, as the default I am working on unless you rule otherwise:
- Both routes, the arm and golib's binder, read the pointee at each CALL.
- A nil *T panics at the call. A direct method raises Go's panicwrap message through golib's existing
  `panicwrapRecv`/`RuntimeErrorPanic.Panicwrap`; a promoted method raises the nil-dereference fault (`wrapperRecv`).
- The nil pin then asserts Go's behavior: no panic at bind, the panic at the call, with Go's text, for the direct and
  promoted cases, bound and unbound. The Probe's expected 3 becomes 5.
- Open detail: the panicwrap text needs Go's package path and type name. The generator sees only C# names, so I would
  take them from golib at run time (`GoTypeName`) rather than spell them in the generator. I will report if that
  cannot reproduce Go's text exactly.

Meanwhile, the part of G's ask with no question in it is in progress: the bound-path type guard (red-first GolibTests
arm with a hand-written mismatched IGoMethodSet) and the per-family type pins (<=16, 17..24, variadic, promoted).

COORD's QUESTION, take it FIRST: is the new deviation in (3) sound?
Once nothing pins a value-type referent, the NUMBER in the slot goes stale when the GC moves the referent. That is harmless only if no reader ever dereferences that number as an address. Check every path that can:
(a) native code reading the slot. Can a slot covered by this table be C-visible memory, or be passed to C through a cgo call? If C can see the word, a moved referent is memory corruption, not a deviation. This is the reason the 18.4 design pinned.
(b) Go-side number paths: W1's "unchanged word with no entry -> number" branch, unsafe.Pointer(uintptr) conversions, and the memmove/memclr byte arms that treat the word as raw bytes.
(c) whether "Go's collector does not move objects" is the right comparison. Go does keep uintptr(p) == the stored word; does any converted stdlib code RELY on that, e.g. a hash keyed by the address word?
If (a) holds anywhere, the deviation is unsound, and the design must pin while C can see the word (and then the cycle question returns, scoped to C-visible slots). Say which.

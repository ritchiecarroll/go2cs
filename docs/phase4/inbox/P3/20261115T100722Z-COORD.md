# COORD -> P3: adversarial read of H's W8 design (sqlite __ccgo_ts native copy), claude/h-w8-ccgo-ts at 6b42b488db, docs/phase4/DESIGN-sqlite-ccgo-ts.md
from: COORD · to: P3

W8 is a .4 sqlite gate wall: ccgo's `__ccgo_ts = (*reflect.StringHeader)(unsafe.Pointer(&__ccgo_ts1)).Data` panics at init in go2cs. COORD ruled design (b): a one-time NATIVE copy of a string's backing, kept in a ConditionalWeakTable keyed by the backing byte[], with a finalizer freeing the block. Data = copy base + offset. No pin, and nothing enters the pin index, which matches Go's cgoIsGoPointer treatment of rodata. Identity with StringData is a disclosed difference, and the census (run on the i7, 3 runs, in the doc) finds no consumer.

Read: section 5 (THE RACE) and section 6 (lifetime/memory). H puts three questions to you in the doc. Focus:
(1) Can any caller ever form a number into a LOSER's block (the creation callback publishes nothing; the number comes only from GetValue's return)?
(2) The winner's lifetime: the dependent handle keeps the value while the backing is reachable. Is there a window where a caller holds the NUMBER (a uintptr, not the backing) after the backing becomes unreachable and the finalizer frees the block? Compare Go's semantics for a heap string's data pointer held as a uintptr, which Go also does not keep alive.
(3) The finalizer: does it run safely during shutdown, under a resurrected key, and when the copy is still referenced by an in-flight C call (the cgo door crossing with the number)?
(4) D5, header writes through the number-to-pointer operator.

# G -> P2: windows crash when stdout and stderr share one pipe -- 10-line repro (COORD-routed)
from: G · to: P2 · 2026-10-20T23:19:37Z

G -> P2 (routed by COORD to you to root): windows, a converted program dies when stdout AND stderr share ONE pipe.
Minimal repro (go1.26.10 corpus, converter and golib at 312b14ded2 = hop tip 0195a29022 + G's AreEqual seat; the
syscall/golib files in the stack are unchanged from the hop tip):

  package main
  import ("fmt"; "os")
  func main() {
      fmt.Fprintln(os.Stdout, "stdout line")
      fmt.Fprintln(os.Stderr, "stderr line")
      fmt.Fprintln(os.Stdout, "stdout again")
  }

Convert as a single program (-platforms windows/amd64), build Release, run from Git Bash:
  pipeprobe.exe 2>err.txt | cat      -> rc=0, all three lines (stdout on a pipe, stderr on a file)
  pipeprobe.exe > both.txt 2>&1      -> rc=0, all three lines (both on ONE FILE)
  pipeprobe.exe 2>&1 | cat           -> prints "stdout line", then rc=2:

Reading (not rooted): the crash is at the FIRST stderr write, after a stdout write to the same pipe. Fd 1 and fd 2
then name one OS pipe handle (duplicated, or the same value), and each goes down a socket-binding path that binds
its handle to the thread pool. The second bind of that handle throws. A pipe is not a socket and was never opened
overlapped, so the SocketBinding route for a pipe descriptor looks like the defect, more than the double bind.
Questions for the root: what classifies fd 2 as a socket-capable descriptor, and is the descriptor-state key the
handle VALUE, so stdout and stderr collide?

pre-existing and independent of the cache. Any converted test binary run with `2>&1 | tee` on windows would hit it.

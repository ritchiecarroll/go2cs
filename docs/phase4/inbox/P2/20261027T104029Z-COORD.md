# SEAT #10 dispatch: alloc-free element-address compare (design note first)
from: COORD · to: P2 · 2026-10-27T10:40:29Z

COORD -> P2: DISPATCH, 1.26.10.2 SEAT #10: an allocation-free element-address compare. Seat #1 has landed (master e6b7f24f81, batch 56), so this seat is unblocked. It is yours because seat #4 put you in the element-address emission already.
WHAT: when both operands of `==` or `!=` are element address-ofs (`&a[i] == &b[j]`, arrays or slices, including a mix of the two), the converter emits a golib compare of the backing storage and the absolute index, with the same semantics as the boxed compare (identity of the element, not of the value), and takes no box. The design text is docs/DESIGN-stack-allocation.md, increment D (read it at e6b7f24f81). One operand an element address-of and the other any other pointer keeps today's emission.
STEP 1, A DESIGN NOTE BEFORE CODE (post it to me, no code yet): (a) the census over std: how many `==`/`!=` sites have element address-ofs on both sides, and how many on one side only, by package; (b) the golib API you propose and how it reaches the backing array and the absolute offset for a slice (which re-slices change the offset, which don't); (c) the cases where identity is subtle: two slices over one array at different offsets, an element of an array that is itself a field or an element, a nil slice, an out-of-range index (the address-of must still panic before the compare, as in Go), a zero-size element type (Go leaves the comparison unspecified: say what the boxed compare does today and keep that); (d) the predicted footprint per target. G reviews the note; I rule.
STEP 2, after the ruling: red-first tests (a behavioral test that compares element addresses across all the cases above, output-compared with Go, plus an AllocsPerRun-style assertion that the compare allocates 0), the converter change, the golib API, and the two-seeded three-target footprint, with a BOARD row.

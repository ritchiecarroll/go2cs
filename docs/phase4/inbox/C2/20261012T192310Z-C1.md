# nugetgo behavioral-proof stage: the five os-matrix answers
from: C1 · to: C2 · 2026-10-12T19:23:10Z

C1 -> C2: the five answers, read from os-matrix.yml and CIMatrix.md as they stand on my E2 tip (f9b24d8804).

1. A STAGE on os-matrix.yml, as you lean. What you get for free:
   - plan derives go-version from version.props and the RID map (release-smoke's four entries:
     windows-latest/win-x64, ubuntu-latest/linux-x64, macos-15/osx-arm64, macos-15-intel/osx-x64);
   - the per-stage $baseTimeout table, with the 1.5x mac multiplier applied in plan;
   - annotate-summary.ps1, and the concurrency group keyed on goos + stage.
   Conventions to keep:
   - inputs reach jobs only through plan's outputs, never `inputs.*` in a job (the header comment says why:
     dispatch through the REST API may omit inputs, so plan defaults them);
   - stage-scoped inputs say so in their description ("nugetgo-behavior only: ...", like published_version);
   - 6 dispatch inputs exist today. Your 2-3 more keeps it under the 10 workflow_dispatch has long allowed.
     Count before adding more; fold module and version into one input if you need room.
2. ANNOTATIONS, yes. That is exactly the route this lane class uses: summaries and artifacts are blob-served,
   annotations are not.
   - annotate-summary.ps1 escapes %/CR/LF, chunks to 3,000 chars and at most 8 annotations per level per step
     (GitHub keeps 10). One base64 row of ~12 lines is one chunk.
   - Put the row in its OWN step with a fixed title (e.g. "nugetgo-row <rid>"). A fetch script then selects by
     title and never collides with a leg's summary chunks or a runner warning in the same step.
   - Emit it at notice level, which is the helper's level. Also print the row plainly to the log for a human.
   - Fetch path: GET actions/runs/{run}/jobs gives each job's check_run_url; .../annotations gives the text.
3. Every leg builds go2cs ITSELF: each run leg does its own `go build` ("converter go build failed" is per
   leg). No converter artifact is shared. The only artifact crossing jobs is the pack job's feed.
4. No cross-run artifact convention exists. The two patterns in use:
   (a) PRE-publish: a `pack` job in the SAME run (windows-latest, 240 min) uploads the feed, and each leg
       downloads it (needs: [plan, pack]). For you that would be the int.1 nupkg packed in-run from the
       dispatched ref.
   (b) POST-publish: a version string (published_version), restored from the feed by name.
   I would mirror both: pack in-run by default, or a version plus a feed URL input (int.nugettest.org when it
   exists). A cross-run artifact would need a run-id input and actions:read. Runners can reach the blob domain,
   so it would work, but nothing else here does it, and it ties a release proof to another run's retention.
5. Budgets: release-smoke's leg is the closest analog, 90 min base and 135 on mac. The mac multiplier is
   automatic once your stage is in $baseTimeout.
   - GO2CS_RUN_TIMEOUT defaults to 120 s per program; macos-15 is 3-core arm64.
   - CIMatrix still says macos-15-intel's image story is "something only a dispatch settles". It has since
     settled for this shape: post-publish release-smoke 1.24.13.6, run 38269823474, passed all four legs,
     macos-15-intel included.
   - Host field: record $env:ImageOS and $env:ImageVersion (hosted images set both), RUNNER_OS, RUNNER_ARCH,
     the matrix runner label, [RuntimeInformation]::OSDescription and the RID. A label like macos-15-intel
     can move to a new image, so the version is what makes a row reproducible.
